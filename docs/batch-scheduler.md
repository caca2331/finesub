## 与 batch 模式的分工

**batch 与单文件现在走同一条路径**——从 2026-08-30 起这句话是字面意义上的：
`finesub.pipeline` 是唯一入口，一个源就是 N=1 的一项，同样经过 `scheduler.py`（`run_batch`），
只是每个 bin 一个 worker、reporter 与失败呈现换成前台档位（进度原地重绘、失败打栈、写 run 日志）。
asr bin 固定为 1，每个文件独占整个 profile 的 shard/separator 宽度。

| 场景 | WT 并发来源 | 每任务 worker |
| --- | --- | --- |
| 单文件 | shard 级（本文） | 生产缺省 `task_workers`（≤ profile 上限） |
| 多源批处理 | 同上 | 同上（asr bin = 1） |

### 为什么反转了原来的设计（2026-07-30）

原设计是「asr bin = `wt_instances`，N 个文件各占一个 WT 实例、每个文件 `worker=1`」，理由是
显存包络相同、且每个 batch 产物都走 `worker=1` 的逐字节一致路径。反转的原因是**内存**：
那种做法把 N 个文件的非模型状态同时压在一个进程里，而 8GB 档**单个文件**就已实测越预算
（分离阶段 7.79GB / 上限 8GB）。当时「内存」只是没量化的担忧，现在是实测事实。

**代价要如实记账**：

- **长文件几乎无损**。别拿 1.1–1.2× 去对比文件级并行——那是**端到端**数字，含可修复的加载
  错峰与配平失准。WT 自身的 2 路并发效率是 1.42×（见「损失分解」），与文件级并行的差额
  远小于端到端数字的暗示。
- **代价集中在短文件**：防碎片阶梯会把它们挡在单 worker，文件级并行则不受此限。阈值同期
  由 300s 降到 150s 正是为了压住这一项（见「Worker 数量」）。
- **batch 产物不再保证与 `worker=1` 逐字节一致**。契约本就只保证 `workers==1` 一致；实测
  `w=2`/`w=4` 与 `w=1` 完全相同，但那是实测而非承诺。

原「搁置项」里的跨任务共享池因此也失去了动机：队列尾部只剩一个长文件时，它现在本来就用
满整个 profile。

### llm bin 的并发语义（2026-08-30 更新，task-parallelism plan W5）

llm bin 不再固定为 1：`--max-parallel-tasks` 是准入旋钮（默认 2——这是偏好不是待标定项，
owner 2026-08-30 裁定不做标定实验，选值指引见 `manual/agent.md`「同时运行的 agent 数量」）。此前记录的「唯一硬约束是限流器（进程内无锁状态）」经核查**只对跨进程成立**
——`ModelRateLimiter` 每个 read-modify-write 都在 `RLock` 内、实例是进程单例，本就为并发调用
设计；真正跨进程会盲计的只有 RPM/TPM 滑窗。知识库侧：SQLite store 有跨进程写锁
（`<knowledge_root>.lock`，超时 90s，进程内引用计数共享）与 CAS，进程内并行 task 在
per-root 有序单写者队列里排队（plan W2）；**别的进程持锁时 apply 跳过应用、保留提案、
不推进 chunk ledger、只打 `knowledge-locked` 告警，靠重跑捡回**——最坏结果是延迟入库，
不是损坏（细节见 `docs/knowledge.md`）。调度：同 `group` 的任务严格提交序串行，组间 LPT；
组间先比 `priority`（manifest 行键，大的先跑；同时作用于 ASR 优先队列——LLM 那头单给优先级
感受不到，ASR 才是长杆），再比 LPT。实际派发顺序写进 batch-status（`llm-scheduled` 事件）。**运行中可加任务**（2026-08-30）：
`--manifest` 批在运行期间轮询 manifest 的**追加行**（append-only，只读带换行结尾的完整行，
写到一半的行等下一轮；坏行告警跳过），新任务进 batch-status 的 `added` 事件；批在「全部已知
任务完成且最后一次**确定性**轮询无新行」时退出，之后追加的行由下次运行按 resume 接手。
「确定性」是退出判据的一部分（2026-08-30 复审）：轮询有三态，未完成的尾行（新追加、尚无换行）
与读取失败（半个多字节字符导致的解码错误是常见的一种）都返回 `settled=False`，不能与「确实
没有新行」混为一谈——否则恰好在那一刻跑完的批会把正在写入的那行甩给下次运行。连续
`INTAKE_UNSETTLED_POLL_LIMIT`（3）次未确定后仍会告警退出，避免一行永远写不完时挂死批。
启动读取只做**一次**（`manifest_snapshot`）：解析与 intake 游标必须来自同一份快照，否则
在两次读取之间追加的行会被记为已消费却从未构建，本次运行永远不会跑它。

**运行期的队列面（2026-08-31）**：有批次 id 的运行在 `out/batch/<id>/` 下发布 `queue.jsonl`
（运行器写：每项一行 + `_state`，行本身是合法 manifest 行，可回喂续跑）并读 `control.jsonl`
（用户只追加：加任务 / `{"item":...,"priority":N}` 插队 / `{"item":...,"drop":true}` 撤掉）。
**两份文件各一个写者**——单文件双写者会被编辑器的「写临时文件再替换」静默清掉运行器的更新。
控制面走的是 intake 那口轮询，所以「追加行加任务」是同一套机制。改优先级会**重排 ASR 队列**：
PriorityQueue 按入队时的键排序，而值得插队的项恰恰都是已经在排队的。已开始的项不抢占。
`queue.jsonl` 随运行结束保留，它就是这次运行的记录——**没有常驻队列，所以「不想续跑」不需要
任何撤销动作**。

那一面的四条硬要求（2026-08-31 复审补全）：

- **`_state` 必须真的分档**。`ItemResult.status` 从准入到终态一直是 `pending`，拿它当视图等于
  「没有任何东西在跑」；`ItemResult.stage` 记当前 bin，`view_state` 把 `status + stage` 映射成
  queued/running/…（映射住在**运行器**里，视图只是渲染）。`drop` 因此能区分「还没轮到」与
  「下载了三分钟」，两阶段之间仍可撤——那正是省下 ASR 的时机。检查与置位同在 `forward_lock` 内，
  否则会出现「告诉你还在排队」与「worker 刚开跑」的交叉。
- **撤掉要能穿过一次回喂**。丢弃与「被 Ctrl-C 跳过」都落在 `skipped` 上，而回喂时 `_state` 会被
  剥掉：不区分的话，用户特意撤掉的项会在下一次续跑里复活。视图写 `_state: dropped`，三条读入
  路径（启动解析、manifest intake、控制面）统一跳过它；`_settled()` 因而把「只剩被撤掉的项」
  当作跑完。
- **发布必须串行，而且渲染也要在锁内**。每个 worker 都发布，共用一个临时文件名：交错写入之外，
  后一个 `os.replace` 还会撞上已被移走的名字。但只锁写是不够的——一个 worker 先渲染出正文，
  intake 线程随后准入新任务、发布并**提交游标**，那份旧正文最后才拿到锁、把新任务抹掉：游标说
  这行消费过了，视图里却没有它，这是续跑唯一救不回来的状态。渲染进同一把锁，最后写的人就是最后
  读的人，而它读到的状态只会更新（状态只前进、item 只追加）。join 之后**无条件补发一次**——
  被中断结束的运行恰恰是最可能被人回来续跑的那一批。
- **游标不得越过一次失败的发布**。`_publish()` 返回是否落盘，`commit` 只在落盘成功后调用。
  发布失败只是告警（视图不是活儿），但它同时是续跑读的东西，所以「准入了但没记下来」必须重读
  而不是退休。**关键在于这个缺口活得比开出它的那一轮长**：读游标在「行交出去」时就前进了，
  持久游标要等效果落盘——所以要补这个缺口的，恰恰是后面那些**自己没带新内容**的轮次。因此
  判据不能是「这一轮有没有带东西」（那会让下一轮空轮询把失败的那条退休掉），而是由来源在
  `consumed != recorded` 时**持续提供 commit**；两者齐平时给 `None`，安静的批就不会每 tick
  白发布一次。
- **一条坏指令只坏它自己**。`{"priority": "high"}` 的 `int()` 此前在 intake 线程的保护块之外，
  异常会带走那个线程——而它是唯一能准入新任务、也是唯一能结束增长型批的线程，于是后续追加全部
  石沉大海、批次还报成功。每条 action 各自 try。

**不用记 id 的续跑（`--resume-batch`）**：`queue.jsonl` 与它描述的产物同住（CWD 相对），这对文件
本身是对的、对「找回它」毫无用处，所以每个批在数据根留一份**指针**（`batches.json`：批次 id、
queue 在哪、cwd、收尾状态）。不带 id 取最近一个没跑完的（`running` 也算——被强杀的批根本没机会
写收尾）。三道拒绝：**超过 7 天**（打印带 id 的命令，交给人决定；给了 id 不受年龄限制）、
**那批还在跑**、**那批的 cwd 不是这里**。后两条与「有多明确」无关，因此**给了 id 也拒**：前者是
两套 worker 写同一批产物，后者是 `out/` 与相对路径都相对当前目录、续跑既找不到上半场也会把下半场
写到别处。判活用的是运行期自持的 `out/batch/<id>/.batch.lock`（`finesub_bootstrap.locks`），
进程怎么死都由 OS 释放——同一把锁顺带挡住了「同一个 `--batch-id` 并发跑两次」。

**续跑保留批次身份**（2026-08-31 复审）：同 id、同目录、同 `queue.jsonl`/`control.jsonl`、同注册表
行、同一把锁。此前续跑会铸一个新 id，于是那把锁锁的是**新批**、收尾写的是**新行**——两个进程用
不同 `--batch-id` 续同一份旧队列会双双判活通过，而旧行永远停在 `unfinished`、被下一次无 id 续跑
反复挑中。因此 `--batch-id` 与 `--resume-batch` 互斥（那正是"岔成两批"的入口）。两处随之而来：
续跑**不挂 manifest intake**（那份"manifest"就是本次运行要改写的视图，轮询自己写的文件正是双写者
错误），新任务照旧走控制面。

**续跑时显式给的选项盖过记录值**（`explicit_row_keys`，2026-08-31）。视图里的行是完全物化的
merged options——那是对的，否则续跑会因为这次没打 `--language ja` 而悄悄换配置；但代价是记录里
钉着 `device: cuda`、`gpu_tier: entry` 这类**机器相关**的值，而续跑往往正发生在机器出过事之后。
判据必须是「命令行上出现过没有」而不是「值等不等于默认值」，所以用同一个 parser 把 defaults 换成
`argparse.SUPPRESS` 再解析一遍 argv。只作用于续跑读进来的启动行：manifest 行与控制面行仍然
「行覆盖命令行」，那是用户自己写的东西。覆盖会被重新发布进视图，因而是粘的。`--stage` 前进会让
已 done 的项获得新阶段（raw-srt 之后要花 LLM 配额），启动时明说复活了几项。

**控制面的游标是持久的，并且在指令生效之后才推进**（`.control-cursor`，`IntakePoll.commit`）。
一版更早的写法是续跑时把已有行整片标记为已消费——那把「盘上有这行」当成了「这行已经生效」，
而进程完全可能在用户追加之后、下一次轮询之前被杀，那条任务/drop/优先级就永远丢了。commit 由
runner 在 actions 应用完、items 准入（因而已发布进视图）之后调用，所以剩下的窗口只有「发布到写
游标」之间：那一刻重放会撞上 claims 本被拒并告警，而不是静默丢工作。

注册表 `batches.json` 是**全机唯一一份**，键是 **(cwd, batch_id)** 而不是 id：默认 id 只是秒级
时间戳、显式 id 常常是 `nightly` 这种词，两个目录很容易撞——撞掉的那一行意味着那个批
`--resume-batch` 再也找不到。写入是跨进程锁内重读—合并—原子替换，临时名带 pid；实测无锁时 6 个
并发登记只活下来 1 条。不带 id 的续跑只在**本目录**的批里挑（别处的批在这里本来就跑不了），
没有本地候选但别处有时会告诉你 `cd` 去哪。

⚠ **搬走一个工作目录就等于注销它名下的全部登记行。** 键里的 cwd 是绝对路径，没有任何东西会跟着
改：2026-09-04 把四个 worktree 从 `../asr-playground-<topic>` 搬进 `.worktrees/<slot>` 之后，
`batches.json` 里 32 行的 cwd 与 `queue` 全指向不存在的路径（那次全是 `finished`，所以没丢东西）。
产物还在槽里的 `out/batch/<id>/`，失联的只是那份指针——所以**搬槽之前先把没跑完的批跑完**，或者
接受它此后只能靠手工进那个目录找。这与上面那条撞键是同一个后果，只是触发方式相反：撞键是两个
目录抢一行，搬家是一行的目录没了。

续跑一个**只剩被撤掉的项**的批（上一次跑在撤掉最后一项之后被杀）不按「没有输入」报错——那会让它
永远停在 `running`，每一次不带 id 的续跑都再挑中它、再返回 2。但也**不在原地直接标记 finished**：
那条快路既跳过了控制面（那里可能还躺着一条上一次没来得及消费的任务），又会在**没持 `.batch.lock`**
的情况下改注册表。它照常走带锁的正常流程，只是起始项为零：一次 intake 轮询之后自行收尾。

**产物唯一性**：每一道准入（启动项、运行中追加的 manifest 行、URL 下载解析出真实路径的那一刻）
都过同一本 `OutputClaims`：比对最终 SRT 与 LLM 产物目录两个写入根、路径按大小写归一，撞了就拒。
没有它的话，两项算出同一路径时后一项会按「产物已存在」跳过全部阶段、拿着前一项的字幕报成功。
URL 那一刻只让该项失败，不拖累整批。

**失败与重试**：失败的**阶段**默认重试 1 次（`--retry-failed`，0 关闭）——重试的是阶段不是整项，
它前面的产物已在盘上、本就会被跳过，所以只赔失败的那一段。捕获面是 `BaseException` 而不是
`Exception`：非 Exception 的错误（库里抛出的 `SystemExit` 之类）此前会终结 worker **线程**，而
asr bin 只有一个 worker，队列随即填满、整批卡住——**一项可以失败，一个 bin 不可以丢 worker**。
它按普通的单项失败处理、**不停批**：`sys.exit()` 在 worker 线程里本来就只结束该线程，把它当成
全局停止信号等于让一个库调用取消掉其余任务；真正的用户中断走主线程那条路。

**中断语义**：Ctrl-C 一次 = 不再派发新任务、等在跑的阶段收尾；**再按一次直接抛出**结束进程
（worker 是守护线程，产物按存在性续跑）。第二次不能再吞——统一入口后单文件前台跑也走这条
路径，吞掉就等于一个数小时的 ASR/LLM 阶段无法中止（2026-08-30 复审）。

reference_ingest 的批**不带 group**（owner 2026-08-30）：与其它批同样的调度，任务的 LLM
阶段可以重叠。放弃的是「后一条任务的纠错能读到前一条刚提交的词条」——素材通常互不相关，
这点顺序不值它的墙钟。
