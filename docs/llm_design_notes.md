# LLM 纠错与翻译：架构意图与设计决策

本文取代原《LLM 纠错与翻译架构 RFC》（`llm_correction_translation.md`），只保留**意图、取舍与决策记录**——即"为什么长这样"。现行行为以 [`llm_harness_behavior.md`](llm_harness_behavior.md) 为准；知识库见 [`knowledge.md`](knowledge.md)；prompt 组装见 [`llm_prompts.md`](llm_prompts.md)。已实现的原始设计稿与实验日志在 `docs/archive/`（在 `dev` 上被跟踪，但不随仓库发布）。

## 背景与目标

最初的单次 prompt 试图一步完成：理解整段直播、搜索背景、修正 ASR 误听、译成轻小说风格简中、排版并输出 SRT。真实需求全覆盖，但一步到位有结构性问题：

- 职责过多：资料收集、听音纠错、翻译、排版、格式化混在一起，错误难定位。
- 预算不稳定：长音频下输入、检索资料、思考、输出都可能同时逼近上限。
- 输出脆弱：直接产出完整 SRT 易出现编号缺失、时间轴错乱、中途截断；截断后"继续写"极易重复/漏段。
- 无法学习：任务中发现的术语、误听模式、风格问题没有结构化沉淀。

因此拆成可测试、可预算、可回滚的多阶段架构：

```text
stable.json 渲染的 raw CSV + 原始音频
  -> 窗口规划（边界同时供背景调查分窗标记）
  -> 准备任务（一条对话：请求批 → 本地搜索代理 / 知识库回填 → context pack）
  -> 听音纠错翻译（每窗一条对话：请求回合 + 本地搜索回填 → 交付；注入建议链）
  -> 本地校验 + SRT 渲染
  -> 可选：任务反馈采集 -> 统一知识更新
```

核心分工原则：**模型只负责"提出 query / 提出 proposal"，harness 负责"执行检索/写入并注入结果"**——因为 gemini-3.x 免费层不开放 `google_search` grounding（实测立即 429），也因为本地执行可预算、可重试、可审计。

其他贯穿性取舍：

- **CSV 而非 SRT 作为模型输入/输出载体**：`global_id|local_start|duration|gap|text` 一行一条，比 SRT 省去序号+时间戳的 token 开销，且时间轴由本地按源序号回填，模型永远不产出时间戳（insert 行除外）。
- **音频用原始音频而非 `*-vocal.flac`**：保留游戏声、角色语音与分离算法可能损伤的语音细节；时间轴仍来自 VAD-ASR。
- **截断只拆窗，不"续写"**：输出超限把窗口对半拆成重叠半窗重试；多轮补写在长输出下不可靠。
- **格式错误同窗重试、供应商错误不缩窗**：503/timeout/限流是 provider 层问题；缩窗只响应输出上限。
- **prompt 缓存友好**：system 只放稳定要求；user 先背景资料后动态 payload，易忘要求放尾部 recap。

## 从角色链到任务组路由

模型选择自 model-routing v2 起按**任务组 × difficulty → 预设绑定 → 模型组**走；现行配置与
用户入口见 [`manual/model-routing.md`](manual/model-routing.md)，运行细节见
[`llm_harness_routing.md`](llm_harness_routing.md)「模型事实、池与路由链」。历史上曾按
`audio_multimodal` / `general_capable` / `lightweight(_multimodal)` 四个角色映射到固定链，
native search 另有一条 2.5 Flash 覆盖链。v2 把角色降级为 artifact 标签，并把 native search
改成选中组内的 per-call 能力过滤；组内无 native 成员即报错，不做静默兜底。

### 模型路由 v2 的持久决策

下面只保留仍约束后续演进的决策；实施顺序、备选方案和逐提交记录已移入本地 archive。

| 决策 | 长期理由 |
| --- | --- |
| **事实归 catalog，编排归 config** | 模型能力、限额、provider 方言是可验证事实；任务优先级、模型顺序和档位绑定是用户策略。把两者混在一张表里会让换模型等同于改程序。 |
| **一行事实代表一个可调用的 `(provider tier, model)`** | 同一名义模型在免费/付费 tier 的 context、quota、工具开放情况可能不同，不能按模型名去重。 |
| **新增事实不会自动上线** | catalog 只回答“能不能调用”，只有显式进入模型组并被预设绑定后才有流量，避免一次资料补录改变生产行为。 |
| **任务组取代固定角色链** | `correction-*`、`research`、`knowledge` 的质量门槛和失败代价不同；共享一个 general 链会让无关会话互相牵制。 |
| **模型组是有序 fallback，不做打分选模** | 顺序是用户的显式成本/质量选择；能力档 `capability` 只做咨询性告警，绝不进入路由决策。 |
| **difficulty 选择格子的模型组、prompt 变体与 thinking，也定走几个 pass、不写 `--diarize` 时开不开裁判、pass 3 的 `auto` 与风格（见[三个 pass 的决策记录](#三个-pass-的决策记录2026-10-1517) D1、D2 与 [efficiency 档与 `basicA` 的决策记录](#efficiency-档与-basica-的决策记录2026-10-2411-05)）** | 它不改变窗口几何，显式从 quality 切到 intermediate 后才能复用已完成窗口；组内 fallback 也不再偷偷换 prompt 档。 |
| **未绑定 difficulty 向上回落** | `efficiency → intermediate → quality` 先在同一预设内找，整组未绑定才借 default；这样只写关心的格子即可，又不会因为省略低档而意外换到另一套策略。 |
| **规划按整个模型组的保守包络** | 发车前不知道最终由哪个成员应答，所以输入/输出上限取组内最紧者，`token_scale` 取最大且不低于 1.0；宁可多切窗，也不能让 fallback 成员接到装不下的窗口。 |
| **窗口下限闸门比声明的两列，不比规划包络**（owner 2026-09-03） | 规划要保守地估**总量**，所以包络从上下文窗口里扣掉输出；闸门问的是**形状**——这个成员收不收得下够长的输入、写不写得出够长的答案。两边都够、而总和超过上下文窗口，是正常模型的形态（Haiku 4.5：200000 进 / 64000 出 / 窗口 200000），拿包络去卡会把它判死。代码里是 `group_declared_minima` 与 `group_planning_envelope` 两个方法，别合并成一个。闸门只扫**被 preset 用到的模型组**、不扫 catalog——`gemma-4-31b` 只做联网检索、不在任何组里，扫 catalog 会误伤。 |
| **catalog 里的 194000 不一律是厂商值** | 它恰好等于已删掉的旧 harness 输入上限，所以带它的行都有「填了默认值」的嫌疑，2026-09-03 逐行裁过，三种情形各不相同：免费 Gemini ×7 是**有意取的速率近似**（`tpm=250000` 下一次 194000 的请求已占 78%，规划更大的窗只会换来 429），不为它改代码；agy 的 Claude 保持 194000（当时是 Opus 4.6，2026-10-03 起是 Opus / Sonnet 5.5 两行）是因为**没人核过 agy 实际透传多少上下文**，它不是厂商数；`local-conversational-agent` 同值但理由不同——附着的对话式 agent **本来就没有厂商数**，填 harness 默认值是可以理解的占位；付费 3.5 Flash Lite 当时的 194000 是**误填**，已改为 1048576。改这些行之前先分清是哪一种。限流器**不拦**超额的单次请求（`rate_limit.py` 里 TPM 判断带着 `and active_events`，窗口为空就放行），拦的是供应商 429。 |
| **native search 是调用能力，不是独立角色** | 同一任务组只在本次调用要求联网时过滤 `supports_native_search` 与 target 工具声明；过滤为空即报错，不暗中换组或降成外部搜索。 |
| **一个媒体开关，纠错窗是唯一读媒体的任务** | 2026-08 曾拆成 `correction_media` 与 `planning_media` 让查询轮单独看音视频；查询轮并入窗口任务后（2026-09-09）只剩纠错窗读媒体，`media=text` 就是纯文本强模型处理音视频素材的路径。 |
| **自定义 provider 第一刀只支持纯文本** | OpenAI-compatible 与 Anthropic 方言先统一文本、thinking、usage、拒答和错误分类；音视频需要逐方言验证编码与计费，不能把附件静默丢掉。 |
| **同名覆盖不重写已完成历史** | 用户可整体覆盖打包的 fact/group/preset；routing digest 用于配置审计和新调用，不作为已提交 stage/window 的失效键。恢复只由源结构与存档可解释性决定。 |
| **优先模型是绑定上的 overlay，不是第二个候选来源** | `[llm.preferred_targets]` 把一个 target 前置到已解析的模型组上，而不是往路由层塞一条新的候选来源——policy 当年就是因为「绑定说一套、policy 悄悄再前缀一套」才被削成纯闸门。前置而非替换同样是有意的：纯文本的自定义 target 替换掉整组会让带媒体的调用无处可去，把媒体能力留在后面才是可路由的。前端偏好因此不需要自己的通道，写配置即可。 |
| **routing digest 不做三拆（2026-08-12 判定不做）** | 曾计划拆成 selection / envelope / advisory，让恢复层区分「选谁」与「按什么预算切窗」。审计后没有消费者：L3 整体豁免 `execution_identity`，调查产物早就跨模型组复用；窗口体检要的是 `ModelLimits` 的数值本身，不是 digest；`session_input_hash` 整包吃 `execution_identity`；`advisory_digest` 已经把分数与显示名摘了出去——有用的那一半已经做完。`llm_local_agent.md` [§11 安全、readiness 与 executi…](llm_local_agent.md#11-安全readiness-与-execution-identity) 的方向也是**扩充** execution identity（driver/toolset/sandbox/知识写策略），不是拆它。 |

## 输出预算公式的推导

预期输出估算仍为 `k × c × csv_tokens`，其中 `k` 是用户的 `--output-scale`。旧六档 preset
最初把系数拆成“基础翻译 + 思考 + 检索 + 媒体”几个经验项；开关化与 model-routing v2 后，
当前实现保留这个加法结构，但直接按正交开关计算：

```text
c = 2.0(纠错与翻译本体)
  + 1.5(统一思考项)
  + 1.0(retrieval != none)
```

媒体曾经各占一项（audio +0.5、video +1.0），2026-09-30 删掉（owner）：剪辑只占输入，而实测的输出长度
主要随模型本身与推理强度变化，开关上的加项解释不了它。
difficulty 不再进入 c：它只选择模型组、prompt 与 thinking。这个决定让“切到 intermediate 继续”
不会改变窗口计划，代价是旧 `text-low` 对应的 efficiency 锚点从实测 c=2.0 提到 3.5。系数不按开关组合逐个标定
（owner 2026-09-30）。

**实测倍率**（2026-09-04）：56 个纠错窗、14 天、按模型分桶量了「回复正文 token ÷ 窗口 CSV token」，
中位 **2.03**、p90 2.54，倍率随窗口增大而下降，全程 `output_limited = 0`；CodeBuddy 四个模型 n=6 合计 2.29。
复算方法：分子取回复正文的 token，分母取 `input_components.csv_input_tokens`。⚠ 分子不能用 `usage.output_tokens`
——Claude 系 CLI 与 agy 报的是会话累计值，所以 agent 路径上产物里的 `observed_coefficient` 不可用。要再动预算，
应按模型与推理强度分，而不是按开关。

窗口约束 `k×c×csv_tokens ≤ 0.9×output_limit − 5000`（=53,982 @65,536）反解出 k=1 时每窗 CSV token 上限：

| 代表组合 | c | 常规窗上限 | 快速模式全量上限 |
| --- | ---: | ---: | ---: |
| text + none（含 efficiency） | 3.5 | 15,423 | 12,122 |
| text/audio/video + local/native | 4.5 | 11,996 | 9,428 |

历史注记：该公式取代了更早的 `csv×5 + 10k` 启发式；旧 mm-med 的有效窗口约放大 80%
（6000→10,796 csv tokens，按当时含媒体项的 c=5.0）。默认的质量护栏 `max_window_subtitle_tokens`（10,000）
比上表多数格都紧，常规窗实际多由它定。仍开着的测量记在 [`llm_followups.md`](llm_followups.md)，不再从历史计划稿推断。

## 知识库行文法 v3 的决策记录（2026-08-29）

（计划正文蒸馏后归档在维护者的本地归档里；现行为见

### 界面回到 md 的样子，存储没有回去

v3 的界面（`## 节` + 每行一条 + `[标记]`）几乎就是 2026-08-22 之前那套 markdown 知识库的
样子，而且更简单：没有三段/五段歧义，没有冒号语义，没有 `sep`。这是有意的——**行文法是
人和模型的界面，存储模型是机器的界面，两者本来就不该长得一样**。界面收敛回去，不等于
SQLite 白换：

| 能力 | md + 内嵌 git | node 模型 | 兑现了吗 |
| --- | --- | --- | --- |
| 行级身份 | 一行的身份就是它的文本，改文本＝断历史 | 每行一个 `local_id`（UUIDv5），改写不改身份 | 已兑现：`@k` 句柄、evidence 挂 `(node, field_path, value_hash)`、redirects/canonical 合并全靠它 |
| 并发写 | 整树重写 + 文件锁，冲突靠文本 merge | overlay + 按实体 CAS 一次，stale intent 分类进 apply report 的 `conflicts` | 已兑现 |
| 事务粒度 | 一次 apply 一个 git commit | 一个 chunk = 一个 `rev`，read-your-writes，重跑按材料 hash 幂等 | 已兑现 |
| 匹配索引 | 别名/误听只能是文本 | `items` 是独立行，带 `exact_enabled`/`fuzzy_enabled`/`min_mora`/`requires_subject_context` | 已兑现 |
| 投影分离 | 只有一份文本 | 同一份数据渲染成完整/部分预览，可按命中裁剪、按节裁剪、带或不带句柄 | 已兑现 |
| 查询 | 全文扫 | 「哪些 term 没有证据」「rev 7 时这一行的别名集合」是一句 SQL | 部分（`verify` 在用） |
| 行级可见性 | 无 | `maturity` + `visibility` | **未兑现**：只有一个用户 |
| 时间旅行 | 文件级可以，行级不行 | 任意 rev 的整库快照，revert 是补偿事务 | **未兑现**：几乎没用过 |

### owner 的明确要求（原话锚点，防漂移）

以下是 owner 的决定，不是推断——要动这些结论需要重新确认：

| # | 决定 |
| --- | --- |
| 1 | **丢弃全部中间态 SQLite，直接从老版 md 重导**；开发期实验库一并删除。存量损坏不单独修数据，随重导消失 |
| 2 | 标记用**方括号** `[自称]`，不用冒号——冒号从此没有语法作用 |
| 3 | **`fact` 不是独立 kind**，它是 note/term 行前的一个标记 |
| 4 | **section 不需要 tier**：完整预览全渲染（空节也渲染，模型才知道有这个节），部分预览空节不渲染 |
| 5 | **不要 optional 标记**（细化为：登记与 core 是两件事） |
| 6 | 命名用**完整预览 / 部分预览**，不用「维护/注入投影」 |
| 7 | **完整预览要渲染 label 的 `note`** |
| 8 | `说话风格` **并入** `特点`；`重要经历` **退休** |
| 9 | `自称` / `他称` / `粉丝名` **迁入 `频道用语`**，用术语行 |
| 10 | `人际关系` 采用**术语四列格式**，并且**可共享**（内容是粉丝面通称，不是法定姓名） |
| 11 | `所属` 降级为**无标记 note** |
| 12 | **`[音色]` 只含声线与发音**（额外用途：多模态模型据此区分说话人）；**方言与语种归 `[语体]`**（文字线索） |
| 13 | **`[人设]` 只含外貌之外的设定**；新增 **`[外观]`** |
| 14 | `[本名]` = 源语言全名 / 中文定名 / 英文定名（源语言定名已是英文则留空）；**读音归 `[别名]`** |
| 15 | 加一个**兜底节**吸收无处安放的内容（定名 `待归类`，非空即出信号） |
| 16 | **preset TOML 是唯一真相源**，模版与 prompt 结构说明都由它生成 |
| 17 | **`core` 不配任何提醒机制**——空槽本身就是提醒。留空不是待办：更新时证据不足就不填，这是正常状态，不需要被追踪、清零或 dismiss |

### 根因：一个正则回答两个问题

旧文法让**同一个正则**同时回答「这行是什么 kind」和「它的字段怎么切」，而作者写下这行时
本来就知道答案。于是 `《崩坏：星穹铁道》` 里的冒号把散文切成 `fact`，`说话风格` 那一节
`kinds` 含 term 却因为 `line_form` 单选永远解析不出术语行。v3 把这两个问题拆开：**标记是
显式的**（方括号，作者说了算），**kind 由行体形状定**（≥4 段竖线 ⇒ term，恰 3 段 ⇒ 报错，
其余 ⇒ note），`body_kinds` 是集合而非单选。猜错也只是猜错标记，不会改 kind、不会改内容。

### 不做的事

- **不修存量损坏**（2 条空 desc、1 条反向 misheard、2 个畸形 fact 节点）——随重导消失，
  不值得单独补数据。
- **不保留向后兼容**：v1/v2 术语文法与 `archive` 五段文法只在 Phase A 出现一次，转换完即删；
  `rendered/` 的文法升级收割路径随之退休。
- **不动 `translation/`（⚠ 2026-09-02 那两份台账已退役，见 [`knowledge.md`](knowledge.md)
「两个翻译台账（已退役，2026-09-02）」；本条记的是当时的取舍）**：`common-mistake.md` / `good-example.md` 仍在 node 模型之外。

## 共享上下文与 prompt 迭代的方向

### 可维护的 Shared Context

把调查 context pack 从"一次产出、只读注入"升级为全 session 可见、模型可增删改行的共享上下文。**评估结论：暂不做**——与现有 advice ledger（逐窗累积、全会话可见、8k 上限）功能高度重叠，且行编辑协议给每个 session 增加新的解析失败/重试面，显著复杂化 resume 与 `-a`/`-b` 半窗重试的确定性重建。**触发条件**：8k advice 台账在长任务中证明不够用（后期关键上下文被挤出、模型频繁重申旧建议）时再实现。

协议草案要点（届时参考）：harness 注入带行号的 `<shared_context>`；模型输出 `<shared_context_update>`（`change/insert/add/remove <行号>`）；一个 update 块内行号冻结、执行完统一重排；`_commit_window` 时应用并把快照写入 window cache 以保证 resume 确定性等价。

### Prompt/harness 自我迭代

prompt 迭代由 `tools/session_replay` 的受控重放驱动（见 `docs/prompt-iterate.md`）：冻结上游注入物、只换 prompt、用 benchmark 评分与逐行抽查看模型真实反应，据此改模板。知识更新（`finesub.llm.knowledge.update`）不再生成 `<harness_notes>`——该职责已完整移交给 session replay。人工审阅 replay 产物后手动改模板，绝不自动应用。长期方向可借鉴：

- [DSPy GEPA optimization](https://dspy.ai/getting-started/gepa-optimization/)：样例+metric 搜索 prompt 变体（离线 optimizer）。
- [OpenAI Working with evals](https://developers.openai.com/api/docs/guides/evals) / [evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：先定义 eval 再迭代；LLM-as-judge 需人工校准防漂移。
- [TextGrad](https://arxiv.org/abs/2406.07496)：让模型对系统组件输出反馈，再转成修改建议。

## 口语颗粒（语气词/填充/结巴）的取舍指导

（prompt 侧落点：出厂默认风格的 `[语气词]`（`style_factory_default_v1.md`）为压缩版，用户的风格可以改写它；本节为完整判定
框架与依据。相关机制：`discard|` 显式丢弃、中央合并规则、stabilize 的
「高度疑似语气填充词」确定性 drop。2026-07-20。）

### 为什么需要一套次序

直播切片字幕的两个目标天然拉扯：**可读性**（每条字幕的阅读时间预算有限，垫词挤占
正句）与**人设保真**（VTuber 切片的核心价值是人，口癖、犹豫、破音是身份的一部分——
删掉口癖等于给主播消音）。任何「一律删」或「一律留」的规则都会在其中一端翻车，
所以取舍必须是**判定次序**而不是词表。

### 判定次序：先问是不是内容，再问怎么处理

**第一问：它是内容吗？——是则保留（允许整形），判据任一即算：**

| 判据 | 例 | 说明 |
| --- | --- | --- |
| 情绪载体 | 「うわぁ、ほんとだ、翼みたい!」的うわぁ | 惊叹/哽咽/兴奋的发声是情绪本体，不是包装 |
| 性格口癖 | 主播标志性口头禅 | 知识库为口癖立词条；口癖是身份，不因「无信息」删除 |
| 笑点/包袱 | 试名失败连环「ユミ、ユメ、や、ミ……あ、だめだ」 | 整段结巴就是内容本身，一个都不能少 |
| 对话功能 | 应答 うん→嗯、惊叹 えっ?→诶？、呼名 レミ! | 这些是台词；短≠可删 |
| 叙事悬停 | 「ママが新しい髪型に…」被打断 | 欲言又止的省略号承载信息；被插话打断的续句各自独立保留 |

**第二问：不是内容，是机械噪声吗？——是则压缩（保意图、去机械性）：**

- **口吃 repair**：保留一次重复——「ち、違うよ」→「不、不是的」。一次口吃有表演
  价值；机械多次（「や、や、や、やばい」）压成一次「呀……好险」。判据：重复次数
  超出表演需要的部分是发音机制产物，不是表达。
- **false start + 改口**：保留改口结果；false start 只有带情绪/喜剧价值才保留
  （试名段保留，普通说错重来则删）。
- **句中垫词**：なんか/こう/あの 位于句中时多数删。依据：中文对应垫词（「就是说」
  「那个」）的语用频率远低于日语，逐词对应会造出原文没有的啰嗦感——这是语言差异，
  不是删减。
- **压缩的形态优先级**：能**并入邻句**优于删除——孤立垫词行（0.3s 的「えっと」）
  并进后句（「呃……好像是咩咩的」）既消除闪现短行、又保住犹豫感。oneshot 的
  10,11 即此示范。次序：能并则并 → 并不了再看第三问。
  （合并受中央规则约束：≤2 连续源；唯一的例外见下面[三源「filler 三明治」合并特例](#三源filler-三明治合并特例已实现capable-档-v49basic-保持严格)。）

**第三问：压缩/并入后还有残余信息吗？——没有则丢弃：**

- 纯 floor-holding 的孤立垫词行（前后紧接正句、自身无情绪色彩）；
- 无语义感叹转写（喘息、干笑填充）；复读幻觉串（ルビルビルビルビ）；
- 套话幻觉（ご視聴 家族）走幻觉处置，不属本节。

### 三条结构性原则

1. **丢弃≠抹除**：取舍只发生在终稿层，整行丢弃要写 `discard|<源序号>` 显式点名——
   「丢弃」的真实语义是「不进 SRT」，原 ASR 行仍在 `-stable.json` 里，人工核对与
   知识更新都还能看到原文。
2. **「不译某词」与「丢弃某行」是两个层级**：尾助词（ね/よ/さ/かな）通常不译、
   语气助词并进语气（「〜じゃん」→「……啊」）都是翻译常规，不需要任何丢弃授权；
   反方向同理：中文有自然对应的颗粒（えっと→那个/呃、まあ→嘛）照译，出厂默认风格
   `[语感]` 的「轻小说感 + 可爱感」本身依赖这些颗粒，不要为了「干净」除净。
3. **拿不准往保留偏**：删错人设颗粒不可逆且伤害核心价值，多留一个语气词只损失
   一点阅读预算——不对称性与 M.2（错并不可逆、漏并可恢复）同构。conf 与 note
   是表达不确定的正道，不是删除的理由。

### 与管线其他层的关系

- stabilize 的「高度疑似语气填充词」drop（低 conf + 短 + 能量正常）在**上游**先删
  一批明显噪声——本节次序作用于**存活到 LLM 层**的颗粒，两层判据独立、不重复。
- 本节第一问的「对话功能」判据同时约束 stabilize 侧未来的规则收紧：应答词
  （うん/はい）即使极短也不应被确定性规则误删。

### 三源「filler 三明治」合并特例（已实现：capable 档 v49；basic 保持严格）

v48 把合并硬上限收到 ≤2 连续源（依据：gap 自适应上游在解码时带音频证据做同句拼接，
位置优于 LLM 的文本级判断；3.5 生产 run 三源使用率仅 5/499，其中还混有不当的两句
合一）。唯一无法被 ≤2 上限等价表达的真实场景是 **filler 三明治**：
`正句碎片 + ≤3字纯语气词/口吃碎片 + 正句补全`——「丢中间再并两边」不可行（合并要求
连续源序号，丢 23 并 22,24 等于在源序号层撒谎），只剩「拆两行」或「丢 filler」，
前者伤并读流畅、后者伤犹豫感。

设计约束（v49 时缺一不可；第 2 条的机器闸门现已不在，见那一条）：

1. 判据必须模型可本地核查：被吸收源为 **≤3 字纯语气词/口吃碎片**（覆盖 えっと/なんか；ちょっと=4 字被拒）、跨度 **≤4s**、
   合并后 **≤16 字**（不适用 36 字放宽）——数字+类别门，不用「同一句」类判断词
   （v47/48 实证：判断词是弱模型漂移的裂缝）。两个数现在是 `prompt_constants` 的 `sandwich_max_seconds`、`sandwich_max_chars`，
   随任务的长度比例缩放，只在 pass 2 的分组版里写；融合单 pass（capableC）一条最多并 4 行，三明治只是其中一种，
   按普通门槛走、不另设更严的长度（[`llm_prompts.md`](llm_prompts.md)「模板清单（按用途分组）」源数一条）。
2. **validation 机器闸门**：v49 时 validation 手握源文本，三源行合法 ⇔ 中间源源文本加权
   长度 ≤3。2026-07-20 起合并源数上限改为只告警（`output_protocol.py` 里标着 EXPERIMENT 的那段），
   三源及以上的行都不再被拒，三明治也就没有机器闸门了；三个 pass 的 pass 1 分组仍按
   「中间源 ≤3 字」放行三源（`grouping.py`）。
3. **仅 capable 档**；basic 保持 1:1+词中接回，不给例外。
4. oneshot 同步一个正例 + 一个反例（中间源为 3 字实词 → 拒绝），防例外泛化。

（原定按审计证据阈值触发；按用户决定于 v49 提前落地 capable 档，validation 同时补上合并源连续性硬校验。）

## `同时` / `换回` 的决策记录（2026-10-30–31）

云端转写（MOSS Pro、35t）给出的几个说话人同时说话时，各自的行在时间上重叠；从此行可以按说话人（分组键 `line_speaker`）重叠，纠错的 `turn` 列多两个值。现行行为见 [`llm_harness_behavior.md`](llm_harness_behavior.md)「Prompt 信息」「窗口拆分」「三个 pass」「说话人裁判」，用户向说明在 [`manual/joint-asr.md`](manual/joint-asr.md)。重开下面任何一条之前先读它的理由。

| 决策 | 理由 |
| --- | --- |
| 只看分组键：同一个键的行不重叠，不同键的可以；没有键的行彼此算同一个键 | 本地链路的行没有键，只有一组，每一处按键算的量都退回原来的值，本地产物与 prompt 逐字节不变由构造保证，不靠「本地的行不重叠」（Whisper 的缺陷会让它们重叠）；另有一个带缺陷重叠的本地样例钉住 raw SRT、纠错输入、切点、合并行时间与 final SRT。云端任务里没有键的行（模型补写、裁判补出的）自成一个键：没人说它是谁，不当成任何人。本地任务唯一的键是叠拉道（坍缩行压到下一行上的那一段，[`asr-stabilize.md`](asr-stabilize.md)「坍缩行」）：它不是说话人，所以有它时没有键的行仍是同一组，说话人裁判也照旧按声学讲轨号 |
| `同时`：换人的接缝里，本行开始时此前另一个键的行还没说完（owner 2026-10-30：「我看不到把它保留的坏处」，不做 A/B） | 模型从开始秒与时长也看得出，但一个值说清「这一行与别人的话同时」，合并规则也不必知道是谁 |
| `换回`：没被盖住，往前找到同一个键的上一行 p 不是紧挨着的上一行，而中间每一行都在 p 说完之前开始——被插话的人接着说（owner 2026-10-30 提出）。宽的定义（回到前面说过的任何人）不用 | 两人一问一答时几乎每次换人都会是宽定义的「换回」，标了等于没标；窄定义下它说的是「这一行和插话之前那一行是同一个人，但中间隔着别人」，正是模型最容易去并、又不能并的那一处 |
| 两个值都隔开两行，跨过它们的合并与跨 `换人` 一样只告警 | 它们都是换人；只告警是三个 pass 的决策记录「只告警」那一行的规则。被别人隔开的同一个人的两行不并：合并源必须连续 |
| 键不同且时间重叠的两行之间总是换人，单 pass 与三个 pass 共用 `line_groups.at_once`，不管标签与裁判怎么说（owner 2026-10-31）；`换回` 不因此改变 | 裁判把附和改到长句那条轨上时，`同时` 不该被抹掉；`换回` 只细分换人，被插话的人是不是同一个仍听标签与裁判 |
| `gap` 钳到 0，不放开负数，也不改成「这一行之前没人说话的时长」；2026-11-07 起方向改成 `max(0, 本行开始 − 上一行结束)`，与 pass 1 一致（owner：「方向我没有异议」） | 键不同的重叠，`line_groups.at_once` 已把接缝强制标成换人（单 pass 与 pass 1 的 `three_pass._different` 都这样），不会被合并；同键的缺陷重叠与叠拉道钳成 0，读成「没有停顿」，对合并判断正是事实。负数会被合并规则读成「更近」；改成「之前没人说话」时，同一个人附和之后又接着说，他自己的停顿被别人的话盖住，诱导错误合并。pass 1 的负数一并钳 0（peer review 与 agent 都推荐，owner 当时不确定）：它的 prompt 从没解释过负数，同键重叠里「负数 = 另一个人」也不成立。`gap` 本身留着（A/B 之后 owner 2026-11-08 定，见[纠错输入 `gap` 方向的决策记录](#纠错输入-gap-方向的决策记录2026-11-0708)） |
| 纠错输入不带说话人列，只给接缝（owner 2026-10-30） | 2026-10-08 让纠错多写一列说话人之后，同一个人被切开的句子也不合并了；合并要的只是接缝 |
| prompt 里不用「重叠」一词 | `fragment_window_overlap_v1.md` 里它专指窗口之间重复包含的行 |
| 带键的任务每一窗都解释这两个值，单 pass 的合并规则、合并行检查与最后提醒写成「换人」「同时」或「换回」（owner 2026-10-31） | 只在窗里出现时才写，一个任务就有最多四份系统 prompt（这段说明在系统 prompt 靠前），并行跑窗时只先暖了一份，其余几份的窗同时没命中前缀缓存；冷读又发现最后提醒只写了「换人」。代价是没出现这两个值的窗多带几句用不上的话 |
| `换回` 的说明写「与插话之前那一行中间隔着别人的行」，不写「不相邻」 | 冷读里「不相邻」被读成时间上不挨着：插话很短时两行在时间上恰好接上，前提看着不成立，禁令就容易被忽略 |
| 被盖住的行之前不切窗（纠错窗、对半拆、裁判的半窗），句末标点也不例外；全被排除才强切 | 切在附和之前会把它和它嵌在里面的那句长话分进两个窗；`is_reasonable_boundary` 见到句末标点就判可切、不看停顿，所以要显式排除 |
| 窗口终点、音频片段终点、裁判录音终点与合并行的终点取另一个键里最晚的结束 | 最后一行可能是嵌在别人长话里的附和，按它的结束截，片段会截掉那句长话的后半段 |
| 裁判的声音样本不挑与别的键时间重叠的行 | 一段样本里有两个人，音色就会误导 |
| 三个 pass 拼回原始行时合并行不重算时间（`grouping.expand_sources`） | 只有 pass 1 把两个键并成一组、又有后面的行嵌进第二个键的话里、pass 2 还跨换人并了它们时，cue 才比按原始行算的早结束一点；罕见、后果轻，重算要把原始行带进每一窗的提交 |
| 裁判 prompt 里讲轨号来源的措辞按行选：云端任务的轨是转写模型的说话人 | 原来的措辞讲声学层「把声音相近的人并进一条轨」，对云端标签不成立：MOSS Pro 常把一个人拆成几个标签（一集里 12 个标签对 4 个人），错多在换人前后（紧挨换人的行对 85.9%，话轮中间 94.3%，见 [`diarization-findings.md`](diarization-findings.md)「换成一体的转写 + 分人模型」） |

## API 调用改流式的决策记录（2026-10-22–23）

所有 REST 生成调用（Gemini、OpenAI 兼容、Anthropic、检索里的 Gemma4）走 SSE，拼回非流式的响应形状。现行行为见 [`llm_harness_behavior.md`](llm_harness_behavior.md)「重试与拼接」与 [`provider-adapters.md`](provider-adapters.md)；探针的逐项读数与各家文档的出处在维护者的本地报告里。改动类别是 A 类（执行形态）：模型、输入、算法不变，验收是解析正确与运行完整，没做质量 A/B。重开下面任何一条之前先读它的理由。

| 决策 | 理由 |
| --- | --- |
| 全部走流式，不留关掉的开关；个别自部署端点不认 `stream_options` 时按服务商单独处理（owner 2026-10-22） | 目的是看得出服务端还活着；两条传输路径并存要双份维护与测试 |
| 软超时按**静默**计（从请求发出或最后一个字节算起，任何字节都重新计时），到点在同一个 key 上发一个备份请求、原请求不断；硬超时 = 180 s + 上限 ÷ 25 tok/s，软超时是它的一半（owner 2026-10-23） | owner 的本意一直是软超时就重试、只是不打断原请求：等着几乎不花钱，多开一条能分出「只是写得慢」还是「调用出了问题」。流式之后静默比总时长更说明问题，所以改按静默计；两个时长都减半（软 = 原软超时的一半，硬 = 原软超时），Gemma4 的固定硬超时 1200 s 也减到 600 s。出字之前的静默分不清在思考还是已经死了（Anthropic 多数新模型默认 `display: "omitted"`，每个思考块只流一个空 `thinking_delta`；OpenAI 推理模型的思考对 API 不可见），所以静默只发备份、从不断开原请求 |

## 付费 API 前缀缓存的决策记录（2026-10-24）

直连付费 API（OpenAI 兼容、Anthropic；Gemini 只动记账与 seed）的调用让一条 run 共享的开头按缓存价计费，任务报告分出缓存写入。现行行为、各家机制与验收读数见 [`provider-adapters.md`](provider-adapters.md) [缓存](provider-adapters.md#缓存)，那里已写的理由（尾部断点只给有下一轮的调用、自动判断端点认不认路由键、Gemini 不走先暖闸门、没做的几项）这里不重复。除 seed 一项外都是 A 类（调用方式与记账）。重开下面任何一条之前先读它的理由。

| 决策 | 理由 |
| --- | --- |
| Anthropic 断点用默认的 5 分钟，不用 1 小时档（owner 2026-10-24："我认为5分钟的足矣"） | 串行窗口之间隔的是一次调用的时长（一两分钟）；1 小时档写入 2 倍、5 分钟档 1.25 倍。出现超过 5 分钟的窗间空档（等人、等 API）再议 |

| 先暖闸门等第一个请求**结束**才放行，各家一样，不按 Anthropic 的「首个流事件就可读」提前放（owner 2026-10-24 维持） | 少一种时机、少一套测试；只影响并行预设，每个前缀多等一次调用的时长。默认思考的模型（DeepSeek V4.1 Flash、Haiku 5.5）一次调用可达几分钟，这一等也随之变长；「目录没法声明「关掉思考」」那条做完后再看要不要让 Anthropic 在首个流事件放行 |
| seed 只在原样重问时追加，首轮与修复轮不带；轻 B 类，不单独做质量对照，看验收里的校验通过率（owner 2026-10-24） | 首轮带 seed，修复轮重发的首条 user 就和首轮对不上，Anthropic 的断点整条错开。验收里 Gemini 前后各一次，纠错调用 5 对 6、每边 3 窗，看不出变差 |
| 回填逐字不改 | 核过：请求轮回复、修复轮上一版答案都回填 `result.content`（去掉思考部件后的回答），前缀本来就对得上 |

| 验收每家一次；DeepSeek 只跑改后并行、Anthropic 只跑完首窗，都不补（owner 2026-10-24） | DeepSeek V4.1 Flash 与 Haiku 5.5 不发思考参数时默认思考，把 32k 输出用光：DeepSeek 一次花 2.19 元，串行对照里修复轮会被截断重问淹没；Haiku 等目录能声明关掉思考再补（`llm_followups.md`「目录没法声明「关掉思考」」） |

## 出厂默认风格的决策记录（2026-10-31–11-04）

纠错与校对 prompt 里原来写死的风格倾向（译文自然、不加注、语气词的取舍、意译适度、语序、口语译法、圈内借词）抽成一套随程序包发布的出厂默认风格。现行行为见 [`knowledge.md`](knowledge.md)「style 类别」里出厂默认风格与已有风格的迁移两条、[`manual/knowledge.md`](manual/knowledge.md)「出厂默认风格」；验收的逐项读数在维护者的本地报告里。

| 不按 `[标记]` 覆盖（owner 2026-10-31） | 出厂默认的标记一增删、拆分，覆盖就漏；复制之后也不需要 |

## 字幕长度档位的决策记录（2026-11-04–05）

## 纠错整窗错位的决策记录（2026-11-05）

3.5 Flash Lite（efficiency 档的生产纠错模型）常在中途漏掉或并掉一个源、编号照常往下数，之后一大段行写的是别的源的话，结尾缺源；
修复轮只补结尾就过了校验。现在校验检出这种错位、送回修复，现行行为见 [`llm_harness_behavior.md`](llm_harness_behavior.md)
「重试与拼接」的「整窗错位」与两档重试；读数（误报与漏检、Flash Lite 的修复重放、全部运行的修复轮）在维护者的本地报告里。
重开下面任何一条之前先读它的理由。

| 决策 | 理由 |
| --- | --- |
| 比纠错原文与源文本的字符相似度（规范化后 `difflib` 的 ratio），不比 `start` 列 | 各个变体都有纠错原文；`start` 只有 `basicA` 有，照编号顺序抄 `start` 的回答也躲得过 |
| 判错位看**连续 5 行**跑偏，不看整窗比例（owner 2026-11-05：「修法和门槛可以按照你的设计」） | 字符相似度单行很吵（假名改汉字、听错的词改掉），但只零散出现：没错位的回答里最长连续 3 行（日语 1854 份里 6 份；另有一份连续 6 行只像 2 个不同的源，见下面「不同」一行）。比例认不出只占 2–3% 的局部错位；连续 4 行只剩一行余量，连续 6 行漏掉 5 行的段 |
| 整窗找最像的别的源，不只找前后几个 | 只找前后 8 个源时，Flash Lite 跳过一长段（偏移 23–117 个源）的错位在重放里「修好」交付了，仍有 164 行错着 |
| 连续段要像至少 5 个**不同**的源 | 整窗找之后唯一多出的误报：一个反复出现的词被改成 ASR 在别处的写法，连着几行都像同一个源；真错位每行像的是不同的源 |
| 同一段内容出现两次（副歌、固定口播）、模型照另一次改对的误报不挡 | 试过「被像的那个源，回答里它自己那行也这么写就不算」：真错位的段尾、往回错一行的段首也是这个形状，会切掉一行、留下错的；跳过一段又接回原编号的整段被挡。误报的代价是多一次修复轮，已有数据里没见过 |
| 错位那一段的行当没通过，补丁还是整份由现有的覆盖门槛定（「乙」，owner 2026-11-05），不一律整份重写 | 局部错位（5–10 行）只补那几行；过半的自然走整份。Flash Lite 的整份重写自己约 15% 会出错位，一律整份要多冒这个险 |
| harness 不自己按相似度把行重新对齐 | 起点那个源的话已经丢了，仍得问模型；判错时还会把对的答案悄悄「修」成别的错 |
| 两档重试用尽仍错位就停下报错（owner 2026-11-05：「两档重试都用完了，仍然有问题，那就停下报错，这个没有问题。」） | 与别的校验失败一致，不交错位的字幕；续跑只重做这一窗。按现在的默认值最终会停下多少没量过（重放只走了旧预算的第一档：5 轮后 36 条里 1 条没过） |
| 两档重试默认改成同一会话修 3 次、换 2 次全新会话（owner 2026-11-05），每窗最多仍是 12 次调用 | 全部记录过的运行里，第一档第 1 轮 129 / 166 通过、第 2 轮 15 / 38、第 3–5 轮合计 3 / 57；接连失败的修复 107 / 139 次与上一轮错误一字不差。卡住时换全新会话才打断得了，多一次换会话比第 4、5 轮值 |
| 错位的错误写出起点那个源自己的话、并说不要就写 `discard`；多抄一格 `duration` 时点名那一格（owner 2026-11-06「确认的话就直接修掉」） | 两种都是模型照着只说「哪里不对」的错误原样重犯到用尽重试：一句被当成套话略掉却不写 `discard`、每行照抄输入的时长。点明之后重放里卡住的三个现场 9 遍都第 1 轮改对 |
| 不给 Flash Lite 缩小窗口（owner 2026-11-05） | 修复轮在重放里 36 条链改对了 35 条，缩窗改的是 efficiency 档的窗口规划，影响面大得多 |

| `--llm-proofread auto` 不跑校对 | 校对 prompt 写的是日语原文对中文译文，在只纠错上没量过；显式 `on` 照跑并告警 |

## 纠错窗口字幕上限的决策记录（2026-11-07–08）

质量护栏 `max_window_subtitle_tokens`（每窗 `<asr_result>` CSV 的 token 上限，现行行为见 [`llm_harness_behavior.md`「窗口拆分」](llm_harness_behavior.md#窗口拆分)第 4 步）默认留在 10,000，不改小（owner 2026-11-08）。依据是一次 10,000 对 5,000 的对照，逐项读数在维护者的本地报告里；还开着的测量在 [`llm_followups.md`](llm_followups.md)「纠错窗口字幕上限的别的大小与别的素材」。

| 决策 | 理由 |
| --- | --- |
| 默认不从 10,000 改成 5,000 | 两个约 9.1k–9.5k token 的日语对谈切片，同一段按一窗与两窗跑：读者盲判 capable 三家（agy Gemini 3.8 Flash、CodeBuddy DeepSeek V4.1 Flash、Codex GPT-6.1 Sol，三个 pass 的前两个）「10k 好 : 5k 好」合计 47 : 50（p = 0.84），6 格 3 : 3 分边，第二个读者在它判的一半格上也打平；按行真值数的跨人合并与 pass 1 误标，两个切片方向相反、合计相近（单遍，没量噪声）。5k 的调用数翻倍（常用 11 份源整源规划 34 窗对 69 窗），折成成本 capable 是 1.25–1.81 倍，多出的输入是每窗重复的固定部分（system、背景、词条、台账）与跟着翻倍的说话人裁判窗，每多一次调用也多一份输出（含思考），DeepSeek 的增加全在输出。看不出质量收益，就推荐省的那臂 |
| 不按档位或模型给不同的上限 | efficiency 档（GPT-6 Luna、3.5 Flash Lite 的 `basicA`）也看不出差别，两档方向不相反；分开给值要新写代码，没有读数支持 |
| 小窗跨窗接力的代价这次没看到，重测时仍单列专名跨窗一致 | 5k 比 10k 多 5 条前后译法不同，跨切点的全是称呼的尾巴（10k 也有同类的 1 条），唯一一条真专名不一致在同一窗内；准备任务的整集专名表每窗都拿到，这一项量的主要是表外的名字，小窗的代价可能被低估 |

结论的范围：每格一遍，两个切片都是普通对谈；主尺子（DeepSeek 读者）没过试跑抽查，owner 决定照用、配行真值的程序尺与第二个读者；约 97 处判了输赢，比约 59 : 38 小的差别看不出。说的是这个范围里看不出差别，不说 5,000 在别的素材上一定不更好。

## 纠错输入 `gap` 方向的决策记录（2026-11-07–08）

纠错窗 `<asr_result>` 与只读前文、知识更新 `<raw_csv>` 的 `gap` 从「本行结束到下一行开始」改成「上一行结束到本行开始」，与 pass 1 同义（csv-v111）；现行行为见 [`llm_harness_behavior.md`](llm_harness_behavior.md)「Prompt 信息」。三臂 A/B（生产 / 换方向 / 去掉 `gap`）的读数在维护者的本地报告里。重开下面任何一条之前先读它的理由。

| 决策 | 理由 |
| --- | --- |
| 方向是上一行结束到本行开始（owner 2026-11-07「方向我没有异议」） | 一行的其余格子（`turn` 的换人 / 可并 / 同时 / 换回）都说这一行与上一行之间的接缝，合并也总是「这一行并进上一行」；只有 `gap` 说下一道接缝，prompt 要反复教「与前一句的间隔看前一行的 gap」，冷读第三、四轮都在改写这句。末行的假 0 没了，换成首行留空，而没有规则会把行并进首行。单 pass 与 pass 1 的形状判据合成一份 |
| 与上一行重叠记 0，pass 1 也钳 0（owner 2026-11-07「都按推荐」） | 全仓一个定义。键不同的重叠接缝，`line_groups.at_once` 已强制标成换人，不会被合并；同键的重叠（Whisper 缺陷、叠拉道）里「负数 = 另一个人」不成立，保留负数等于教错读法；pass 1 的 prompt 本来也没解释负数，从开始与时长仍看得出重叠。代价：裁判判轨号时少一个显眼的信号（云端任务里重叠的两行本来轨号就不同） |
| 窗口首行的 `gap` 留空，即使前面有只读前文 | 行不能并进前文，首行的停顿用不上；空着也不会被读成「没有停顿」 |
| 用户产物 `*-annotated.csv` 的 `gap` 翻成同一方向；知识更新的 `<final_csv>` 删掉 `gap`（owner 2026-11-07「都按推荐」） | 全仓只剩一个定义，annotated.csv 的 `gap` 程序里没人读；`<final_csv>` 已有开始、结束秒，知识更新没有规则读 gap |
| 采纳换方向（owner 2026-11-08） | A/B 在三种生产形态（capableC 单 pass、三个 pass 的 pass 2、`basicA`）上没触发预先定的退化门槛（读者逐处判显著偏生产且多数格偏生产；长停顿合并、反向尺、词中接回越线多 ≥3 条且 ≥50%；交不出的窗更多），也没看到读错方向的痕迹（读错方向会留下的错并与漏并都不比生产多）。依据 owner 2026-10-12：逻辑对的改动不比原来差就保留。代价：每格一遍、4 个窗，读者有偏生产的迹象（按格 7 : 1，p≈0.07，一大块来自一格），按行真值的跨说话人合并也比生产多；这些不到门槛，记作没站住的「不比生产差」 |

## 纠错窗口拼接改成 core 归属的决策记录（2026-11-08）

相邻两个纠错窗口在重叠区上都有回答。拼接从最新优先（重叠区用后一个窗口的回答）改成 core 归属：每个源段用它所在核心区（窗口去掉重叠前缀）的那个窗口的行，重叠区留前一个窗口的，接缝从重叠区起点挪到切点（现行行为见 [`llm_harness_behavior.md`「重试与拼接」](llm_harness_behavior.md#重试与拼接)）。提议来自 2026-11-05 全仓审计。先做了验证，判打平；owner 2026-11-08：打平就采用更符合直觉、更合理、更优雅的设计。逐项读数在维护者的本地实验记录里。

| 决策 | 理由 |
| --- | --- |
| 改成 core 归属 | 质量打平：连续性只靠输入，两条规则能在已记录的回答上精确重放。16 份素材、34 个接缝（2026-08—10 的 capableC 单 pass 回答），CodeBuddy DeepSeek 盲判两版：core 胜 9、最新优先胜 8、平 17，偏好均值 +0.03，按素材整块的 95% 区间 [−0.12, +0.27] 跨 0，排除了 core 明显更差，没排除 core 略好。读者标的重复或遗漏最新优先 1 处、core 2 处，都在某个窗口自己的行里；机械覆盖两边都没有丢行与重复。判了输赢的 17 处逐条读过，差别散在整段重叠区，是两次独立回答的措辞、断句与 ASR 纠错不同，没有一处是接缝本身造成的。设计上 core 更顺：窗口规划特意把切点对齐到句末或 ≥ 0.8 s 的停顿，最新优先却把缝放在重叠区起点这个没挑过的位置；每个源段归一个窗口，与说话人裁判「纠错窗的核心行就是一个裁判窗」（[`llm_harness_behavior.md`「说话人裁判」](llm_harness_behavior.md#说话人裁判--diarize-judge-text--judge-audio)「窗口」一条）同一个划分；拼接从认领、回填、恢复三步缩成一个闭包，知识更新给成品行找窗口也改成「第一个含它的窗口」，与拼接一致 |
| 跨过切点的行仍要一条规则，伸出窗口起点的旧行仍会重复 | 新窗口能把重叠区末行与核心区首行并成一行，审计说的「跨界行自然不存在」不成立，所以保留闭包：这样的行整行归新窗口，与它相交、整行在窗口内的行一起改归。回放里新窗口跨过切点 0 次（切点在句末或停顿，合并很少跨它）；旧行伸出窗口起点（上一窗口跨过重叠起点合并）在最新优先下也是 0 次 |
| 不需要改 prompt，重叠区照旧由两个窗口各答一遍 | 两条规则下拼接都只是丢掉其中一份；prompt 说 `<asr_result>` 每一行都要输出，仍然成立。量级：生产尺寸的窗口（上限 10,000 token）一集常只有一两个缝，重叠区约占 1–2.5% 的行 |
| 不改成「窗口尾部带只读后文、重叠区不再重答」 | 它能删掉重叠区的重复回答与 `grouping` 里切重叠的那段，但生产尺寸下只省重叠区那约 1–2.5% 的行的重复回答；而它给每个窗口多一块要读的输入，重叠行也从「要答」变成「只读」，模型的输入整体变了，掉不掉质量要真跑纠错才知道。改成 core 归属之后，纠错切点前的几行最终没看过后文，说话人裁判窗却带着切点后 30 秒的后文，两边不再对称；core 臂里前一个窗口对重叠区的回答没看过后文，仍与最新优先打平，只弱支持它不掉质量，说明不了值得这些代价 |
| 不让后一个窗口按需接管切点前几行（owner 2026-11-08 按推荐） | 想补的是跨切点的语序调整与连贯译法：前一个窗口没看到切点后的行，切点前的译文可能和后一窗口的接不上（同一句评价说两遍、宾语接不上动词）；并成一行的情况闭包已经接住。做法是重叠区最后至多 3 行由后一窗口判断要不要写成 `take`。两轮读者测量（150 个接缝，同一批）：总是接管 3 行只是把接缝往前挪，修好与弄坏的接缝错差不多；在 0–5 行里替每个接缝挑最好的接法（上限），能修好的 9.3%，其中真由接缝造成的只有 4.7%（全在一份素材的 3 个切点，都在 3 行内修好），另一半是前一窗口自己几行的措辞运气，后一窗口看不到前一窗口的译文，拿不到。收益至多这 4.7%、错都很轻，而代价落在每个有重叠的窗口上：认出重叠行、记住它们默认用前一窗口的版本、对最后几行做一次判断，输出契约（违反就整窗重做的那一节）多一种行类型，弱模型多一种进修复轮的错法；为一个多数窗口用不上的情形加一项人人要做的判断，会分散模型的注意力，与 capable 去辅助列、`basicA` 去三列、纠错去推理块的减负方向相反。注意力的代价没量过 |

结论的范围：只有 capableC 单 pass、csv-v104 之前的回答，没有 efficiency 的 `basicA`、没有三个 pass 的 pass 2，也没有 `resume` 与 `pseudo-conversational` 两种会话形态（窗口 k 看得到 k−1 的回答，它对重叠区的改写现在整份丢掉）；不少运行的窗口上限是 800 token，比生产密；每处只判一次，读者噪声没量。

重开条件：run-audit 或人工审在成品的窗口缝（切点处）上反复看到半句、重复或遗漏；或者窗口上限明显缩小、缝变密（[`llm_followups.md`](llm_followups.md)「纠错窗口字幕上限的别的大小与别的素材」），这时在新回答上重跑一次回放对照，补上 `basicA` 与 pass 2。只读后文那一条：拼接代码又要修 bug，或窗口明显缩小时再看。按需接管那一条：同样的条件下切点处的错明显变多时，它就是现成的修法（上限 3 行），先用回放上限读数估收益，再真跑纠错量模型能拿到多少、整窗守规有没有变差。

## 连不上的 host 与离线 tokcount 的决策记录（2026-11-09）

起因：大陆用户没有本地计数器时退到 Gemini `countTokens`，Google 被墙时每次调用都重试、等满超时，什么都不打印。owner：要的不是绕开墙，而是第一次失败就说出原因、同一进程不重付同一笔等待、网络或代理恢复后不用重启（用户看到明确的提示会自己挂代理）。现行行为见 [`llm_harness_behavior.md`「连不上的 host」](llm_harness_behavior.md#连不上的-host)、[`download-routes.md`「1. 路线解析」](download-routes.md#1-路线解析)、[`manual/model-routing.md`「走代理：`[api] proxy`」](manual/model-routing.md#走代理api-proxy) 与 `tools/tokcount/README.md`。重开下面任何一条前先读理由。

| 决策 | 理由 |
| --- | --- |
| tokcount 内嵌词表、在 CI 里编，完全离线（owner：本机不装 Go） | 旧版首次运行从 `raw.githubusercontent.com` 下 4.7 MB 词表，被墙时启动 21 s 后失败。计数只取决于 go-sentencepiece 与词表，去掉 genai 依赖后与旧版逐位相同（1600 段真实文本、750 万 token，0 处不同） |
| 按 `(host, 路由)` 判定连不上，不按 IP / 地区预判 | 要请求第三方服务，挂了 TUN 或系统代理时会误判；连接阶段失败才是直接证据。路由进键，换了代理立即重新尝试 |
| 一串失败持续满 30 s 才判定，相隔 60 s 以上重新起算；不跨进程记 | Wi-Fi 闪断、一次 DNS 失败凑不满；一个进程跑完整批，每个进程最多付一次发现的代价，记下来还要处理过期 |
| 判定之后生成调用与上传仍每次试一次、不重试，不跳过 | 它们没有替代品；跳过会让恢复慢到一个探测间隔（计划第 2 版一度这么写，peer 指出后改回） |
| countTokens 与检索除探测外跳过；同一 host 一次最多一个探测，名额由拿到探测的调用方在结束时让出 | 它们有替代品（启发式、下一家）。按请求记录认不出哪个是探测：gemma4 的探测是别的线程上的对冲请求，同期别的请求失败也不说明探测结束了 |
| 能单独设 connect 时限的地方统一 15 s，countTokens 5 s、Exa / Tavily 10 s（owner：能区分 Google 自己的错误和被墙就降，不只 Google） | connect 时限只管服务端开口之前（TCP、代理的 CONNECT 回话、TLS），服务端的任何回答都在它之后，所以分得开；分不开的只有「路通但握手慢过 15 s」，那照常重试、连续 30 s 才判定。45 s 时一次被墙的上传实测静默 169 s。拆不开 connect 的 35t Live websocket 与 urllib 调用不动 |
| 代理接了连接却不回 CONNECT 算连接阶段失败，等回话用 connect 时限（owner 按推荐） | httpcore 用读超时等这个回话：生成调用要等到硬截止，结束时是 `ReadTimeout`、不算连不上。按 CONNECT 请求本身认，不按事件先后（`https://` 代理先有自己的 TLS 握手）；httpcore 的结束事件不带请求，凭开始时留下的状态认 |
| 连接失败不进 combo 冷却、不计入连续超时 | 冷却写进 `.state`、跨进程生效，拿它记「连不上」会让下一个进程也只看到 `cooldown until …`；两次连接超时曾触发连续超时中止、切断整条候选链 |
| 不再支持 SOCKS 代理（owner） | 以前文档推荐，实际缺 `socksio` 依赖、每次调用都报错，装上之后握手又不带超时。`[api] proxy` 写 `socks5://` 直接报错，说改填代理软件的 HTTP 端口 |
| tokcount 下载不走大陆镜像、不记下载失败（owner 补充后撤掉） | 下载失败本来就打印、不静默，只在那行补一句「可能需要代理」 |
| tokcount 不留 `-model` 参数的兼容代码（owner 不要兼容代码） | 后果只是旧分支配新二进制时退回 countTokens |

重开条件：有用户报告路通却被判连不上，或 15 s 在正常的代理线路上不够；或出现需要跨进程记住判定的场景。

## 模型 catalog 格式与 target 的决策记录（2026-11-09）

catalog 从 PSV 换成 TOML，覆盖按键打补丁，一个模型一个与它同名的 target，搜索能力单独一个键 `supports_native_search`，自己接的 API 端点也能用供应商的搜索；现行行为见 [`manual/model-routing.md`](manual/model-routing.md)（「自己的端点联网搜索」一节是供应商搜索）与 [`provider-adapters.md`](provider-adapters.md)「实现契约」。重开下面任何一条前先读理由。

| 决策 | 理由 |
| --- | --- |
| 换成 TOML，每个模型一个表、只写和默认不同的键，值带类型 | 出厂表 25 列，大多数行只有几格不取默认，备注没处写。没选「PSV 加一列装 `键=值`」：小语言里再套小语言，同一件事两种写法，表还是宽的 |
| 用户覆盖按键打补丁，写 `""` 取加载器默认 | 以前整行替换、没写的列回默认，是因为 PSV 的空格分不清「没写」和「要默认」；整行替换让改一个数的人得抄齐 25 列，出厂值以后改了也跟不上 |

## 三个 pass 不合成一个 agent 任务的决策记录（2026-10-25–30）

## 纠错与准备任务几项不改的决策记录（2026-08-15–10-03）

### prompt 里不告诉模型保留数下限 `KEPT_FLOOR`（owner 2026-10-03）

只有大段唱歌、噪声的长窗会碰上，碰上了修复消息会说原因；写进 prompt 就是每个窗口常驻一条规则，还可能让模型为过线留下本该丢的行——下限是合理性检查，不是目标。现行的下限见 [`llm_harness_behavior.md`](llm_harness_behavior.md)「保留数下限」。

### fast 单窗为选风格多开的请求回合保留（owner 2026-10-03）

触发面很小、额外成本不多，从设计一致性考虑也不动。这个回合组装上的矛盾（要选风格时最后提醒仍写「直接交终稿」）按 prompt 缺陷修，与此无关。

### 开了反馈采集的准备任务在同一次输出里交 `context_pack` 与 `task_update_feedback`，不拆（owner 2026-10-03）

首轮 prompt 冷读把它列为设计疑问，owner 判不改；当时没有记下更多理由。

### 知识校验一次调用的规模不改（owner 2026-10-03）

verify 一次核实整批 claim，不改；真实大批量 run 出现失败再看。（同一条裁定里的说话人角色层 2026-10-09 已删，由说话人裁判替代。）

## 实测沉淀的 harness 原则

这些经验已固化为当前实现，改动时不要回退：

- 单靠"允许合并短片段"的 prompt 不够，模型会保守逐段输出；须在 prompt 中给清晰正反例，而不是 harness 提供本地合并候选。
- `finishReason=STOP` 不代表内容可靠：本地 CSV 解析、超长字幕检查、源序号覆盖检查缺一不可。
- SRT/CSV token 计数必须含结构开销；只算文本会严重低估窗口预算。
- 免费层 prompt 输入实测约 195k 报错——以 194k 为安全基线，而非官方 1M 上限。
- 采样默认显式 `temperature=1.0`；校验重试逐次 −0.01 并换 seed；`top_p`/`top_k` 不设。
- **Sticky retry 宜短、退避宜长（2026-07-29）**：观察发现 Gemini 即使返回 5xx，也会占用日额度；
  同 key sticky budget 从 7 降到 3，退避基数从 0.5s 提到 4s（`4×2^attempt`）。PerDay strike
  仍要连续 3 次才日封，但去掉「首末跨度 ≥5 分钟」门槛——在更短 sticky 预算下，反复 PerDay
  的 key 应更快轮换，而不是为 flicker 等待跨度。失败/重试的 HTTP 尝试同样计入本地 RPM
  （`note_request`），与 provider 侧按次计数对齐。
- **组合临时冷却（tier+model+key）**：某组合在一次 `chat_complete` 内耗尽 sticky retry（仅
  可重试错误）后，写入 `.state` 的 `combo_cooldowns`。**0–20 分钟**直接 skip（立刻换链上下一
  组合，不 sleep）；**20–120 分钟** probe 阶段 sticky retry=0（只打 1 次 HTTP），成功则清除，
  失败则重置冷却起点；**≥120 分钟**自动清除。与 daily-exhausted 独立。
- **test_profile（gemini 3.1 flash-lite）是优化基准，不是打折的近似**：harness/prompt 以
  「gemini 3.1 flash-lite 的 capability 能完成主要任务」为目标打磨（基准钉在这个具体版本，
  不随 flash-lite 档位的代际更替漂移）。它跑不好的地方默认按 prompt/harness 待改进处理，
  不要归咎模型；产线模型只是额外裕度。审计/评测报告注明所用模型是为了对照，不是为了给失效开脱。
