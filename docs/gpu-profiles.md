# GPU 档位标定

> ⚠️ **2026-08-02 起 ASR 固定单 worker**，`ResourceProfile.wt_instances` 已删除；
> 只有分离器实例数还随档位变。按档位缩放 WT 的那部分实测移到了「WT 并发」一节，
> 并在那里标成历史记录。

本文记录 `src/finesub/speech/runtime/resources.py` 各档位的依据。
原始标定 2026-07-28，机器为 RTX 5060 Ti 16GB，PyTorch 2.9.0；**换卡后于 2026-09-01 在
RTX 5070 Ti 上复测过当时的三档（`entry`/`standard`/`high`）预算**（见下「2026-09-01 复测」，
结论：分离器曲线未变，GPU 侧余量很大，RAM 才是贴得近的那一个）。指标为
`torch.cuda.max_memory_reserved`，不含桌面等其他进程的整卡占用。

⚠ 后来加的两档**没有各自的标定，也不需要**：`standard_large_vram`（2026-09-02）的
worker 数与 `standard` 相同、显存要求与 `high` 相同，两个数都已在上面那次复测里；`cpu`
（同日）不用 GPU，没有显存要求可测。**下面每一处「三档」都是那次复测的口径，不是现行
档位数**——现行是五档，见「最终映射」。

> ⚠️ **档位说的是「你这张卡属于哪一档」，它的显存数字是要求**——而且要求的是
> **空闲**显存，不是卡的容量。桌面、合成器和驱动本来就占着一部分；把卡的容量当成
> 要求，正是「我的卡有 8GB 所以装得下」变成 OOM 的那条路。
>
> 卡的标称容量只在一个地方出现一瞬：`tier_for_vram` 拿驱动报的容量减去
> `reserve_for_capacity()` 估算空闲量，然后拿它匹配档位。之后再没有任何地方见到它。
>
> **0.5.0 起档位是名字而不是数字**（原来是 `--gpu-budget-gb 4|8|12|16`）。数字本身就是
> 歧义的来源：「8」既读得通「我的卡有 8GB」，也读得通「只准用 8GB」，而两种读法
> 选出的档位相反。名字没有这个二义，代价是要把要求写在名字旁边——`--help` 和桌面下拉
> 里每一档都带着它的空闲显存/内存要求。
>
> **不存在软上限**，也不打算做：CT2 遇 CUDA OOM 是进程级 abort（同样的理由见
> `ASR_DECODE_BATCH_BY_TIER` 的注释），一个兑现不了的上限比没有更糟。
> 所以选项的默认值是 `auto`——直接问驱动。

## 最终映射

| 档位 | **需要空闲显存** | 内存要求 | WT 实例数 | Separator 实例数 | Separator BS | `auto` 从多大的卡选中它 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `cpu` | **—**（不用 GPU） | 8GB | 1 | 1 | 1 | 无 CUDA 设备 |
| `entry` | **3GiB** | 8GB | 1 | 1 | 1 | <8GB（有卡但小，或本 build 认不出这张卡） |
| `standard` | **6.5GiB** | 8GB | 1 | 2 | 1 | 8–11GB |
| `standard_large_vram` | **10GiB** | 8GB | 1 | **2** | 1 | 12–23GB |
| `high` | **10GiB** | 8GB | 1 | 3 | 1 | ≥24GB |

最后一栏是**派生的**，不是配置：`auto` 把驱动报的容量减去预留再匹配前一栏，然后在
`standard_large_vram` 处封顶——理由见下。

### `cpu`：档位是策略，不是能力（2026-09-02）

`cpu` 档说的是**「这次运行不使用 GPU」**，而不是「问过 GPU，答案是不行」。两者的区别是
这次拆分的全部意义：

- **策略**（`TierSpec.gpu` / `ResourceProfile.gpu`）：准不准用。整个 run 一个答案。
- **能力**（`device.cuda_usable()` 等）：这一步用不用得上。**按后端、按阶段各问各的**。

拆开之前，无 CUDA 的机器被塞进 `entry`，于是它的产物上写着「3GiB 显存预算」——一份它
从来没有过的预算；而显存告警得靠一条硬编码的「除非没有 CUDA」分支才不误报。现在两者
都是自然结果：`gpu=False` 的档没有显存要求，告警直接返回。

⚠ **`auto` 落到 `cpu` 的判据是「驱动报不报得出 CUDA 设备」（`device.cuda_device_present()`），
不是「torch 用不用得了这张卡」。** 一张老到本 build 没有 kernel 的卡**仍然落 GPU 档**
（`entry`）：另一个后端——有自己 arch 列表的 patched CTranslate2——可能还跑得动它，而把
torch 的判断折进档位，等于替所有阶段一次性决定了这件事。那正是
[stage-device-plan.md](plans/stage-device-plan.md) 要拆掉的混淆。

✱ **策略必须真的到得了权重。** 分离器不走 `resolve_device`，它自己问 `cuda_usable()`，
所以 `run_vocal_separation` 把意图、策略与能力**折叠一次**（`--device` 的请求 ∧
`resource_profile.gpu` ∧ `cuda_usable()`；2026-09-02 复审补上第一项——此前 `--device cpu`
管不到分离，`--gpu-tier standard --device cpu` 仍先在卡上分离）
再往下传，`_build_separator` 收到的是决定而不是半个问题。一个到不了这里的 `cpu` 档只是个
标签——`test_the_cpu_tier_reaches_the_weights_even_when_the_card_works` 用**能用的显卡**
钉住这一条（卡是好的、`cuda_usable()` 为真，仍必须落 CPU），删掉那次折叠它就红。

**`--gpu-tier cpu --device cuda` 直接报错**：两者没有同时成立的读法，静默选一边就是下一个
静默错配。检查放在 `pipeline.py` 的 `_pipeline_kwargs`——那是唯一分得清「用户要了 cuda」
和「签名默认是 cuda」的地方（键只有被真的设置过才会进 kwargs）。反方向不用查：GPU 档
加 `--device cpu` 是寻常的「这次把卡让出去」。

### `standard_large_vram`：把「多少 worker」和「多少显存」拆开（2026-09-02）

**Separator 实例数不再随显存单调**，这正是这一档存在的理由：那两个数字回答的是不同的问题。

- **实例数是吞吐取舍**：E7 的 worker 阶梯把峰值定在**两个**，三个实测更慢。
- **显存数字是预算**，而花它的是第二模型裁判：编译解码步要求 Whisper 池之外还有
  **3.5 GiB 空闲**（`COMPILE_MIN_VRAM_GIB`）。

旧表把两者绑死，于是一张 12–16GB 的卡只能二选一：要么拿 `standard` 的两个 worker 但把
显存预算限死在 6.5，要么拿 `high` 的预算却附带一个更慢的第三 worker。代价落在裁判身上——
large-v3 级模型在 `standard` 上只剩 6.5 − 3.82 = 2.7 GiB，**够共驻但不够编译**：

| 模型 | `--asr-decode-batch` | `standard` | `standard_large_vram` |
| --- | ---: | --- | --- |
| `large-v3-turbo` | 1 | cuda 4.43，可编译 | cuda 7.93，可编译 |
| `large-v3-turbo` | 8 | cuda 3.52，可编译 | cuda 7.02，可编译 |
| **日语微调 / large-v3** | 1 | cuda 2.68，**只能 eager** | cuda 6.18，**可编译** |
| **日语微调 / large-v3** | 8 | **cpu**（放不下） | cuda 4.22，**可编译** |

拆开之后，12GB 起的卡拿到 `high` 的预算而没有 `high` 的第三个 worker。**`high` 本身没变**，
仍然只在卡报 ≥24GB 时由 `auto` 放行，手填始终可用。

⚠ **两档的 `usable_gib` 相同（都是 10.0），所以表的顺序有语义**：`tier_for_vram` 取
**最后一个**放得下的档，再被上限压回 `standard_large_vram`，所以 `standard_large_vram`
必须排在 `high` 之前。测试钉着「按要求非递减排序」这一条。

内存那一栏各档相同，但**不是因为 RAM 与档位无关**——2026-09-01 的复测证明它是相关的
（见下）。它保持 8 是因为那是一条**违规告警**、没有任何东西按它预留
（`resource_limit_violations`），而且最坏的 `high` 档也只用到六成。

### 2026-09-01 复测（RTX 5070 Ti，700 秒合成素材）

`pytest test/test_resource_budget_pipeline.py --run-heavy-resource -n 0`，
`RESOURCE_TEST_SECONDS=700`（300 秒 worker 阶梯要求素材过 600 秒才够到 3 个分离 worker）。
本机换卡后原标定（5060 Ti，2026-07/08）需要复核，这是那次复核。

| 档位 | 分离器 peak_gmem | VAD-ASR peak_gmem | GPU 阈值 | **peak_mem** | RAM 阈值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `entry` | 2.26 | 0.87 | 3.00 | **2.43** | 8.00 |
| `standard` | 2.88 | 1.55 | 6.50 | **4.00** | 8.00 |
| `high` | 3.51 | 2.22 | 10.00 | **4.81** | 8.00 |

三点结论：

1. **分离器与 5060 Ti 的 eager 曲线一致**（旧值 2.26 / 3.17 / 3.64），换卡没有改变形状，
   所以 E7 关于「2 个 worker 是吞吐峰值」的结论仍可沿用。
2. **GPU 侧远没吃满**：最坏的 `high` 只用到 3.51/10。`entry` 是唯一贴着阈值的档
   （2.26/3.00 = 75%），也是唯一一档现在就抓得到显存回归的。
3. **RAM 才是贴得近的那一个，而且它随档位涨**（2.43 → 4.00 → 4.81，对应 1/2/3 个
   分离 worker——每个 worker 都在主存里握着自己那块音频）。`high` 已经用到 8GB 的六成。
   **要收紧预算，应该先收 RAM 而不是显存**，且 RAM 那一栏该按档分开。

⚠ VAD-ASR 那一列也随档位涨（0.87 → 2.22），但 ASR 恒定单 worker、按理不该随档变。
最可能的解释是分块规划与 worker 数联动（块数 = 轮数 × worker 数）导致分离产物的块边界
不同，进而改变了 VAD 区间与 ASR 分组。**未确认**，收紧 GPU 阈值之前应当先弄清它。

### 为什么没有 4 个分离 worker 的档

（说的是 worker 数，不是档位数——档位现在有五个。）曾有一个 16GB / 4 实例的 `max` 档，
**0.5.0 移除**。理由不是它多余，是它**更慢**：
[`separator-optimization.md`](separator-optimization.md) E7 的 worker 阶梯把吞吐峰值
定在**两个** worker（AOTI 1.098×、eager 1.048×），3 个降到 1.061×/1.046×，
4 个再降到 1.050×/1.029×。而且 4 worker 只在音频 **≥15 分钟**时才够得着
（worker 数 = `min(档位实例数, floor(时长/300)+1)`），那恰好是差距最大的区间。
一个要多占显存、换来更慢的档位不是档位。

3 实例那一级**保留**：E7 的结论出自单张卡，而 worker 数与分块规划绑定
（块数 = 轮数 × worker 数），再往下砍会移动产物边界，换来的收益还没人在别的卡上量过。

默认档位是 `auto`（0.5.0 前是固定的 `4`）。实例数采用固定硬件档位策略：4GB 为 1，每增加 4GB
各增加 1 个 WT 和 separator 实例。显存容量在常见产品线上也近似代表 GPU
算力等级，因此映射不再取本次 RTX 5060 Ti 跑分的局部吞吐最优点。混合 profile
批处理的 WT 数取其中最小值；Whisper 模型加载仍逐个执行，加载结束后推理并行。
Separator 的 `batch_size` 在当前依赖中无效，固定为 1；“实例数”指并行处理的
独立音频块数。

单个文件实际创建的 separator worker 数为
`min(profile separator instances, 文件块数)`；每个 worker 至少取得一个块。
短音频只有一个块时直接走当前线程，不创建多余线程池。

## `auto` 怎么定档（0.5.0 起的默认）

`--gpu-tier auto`（省略该选项时同义）走 `device.total_vram_gib()` 读整卡显存，
再由 `tier_for_vram()` 定档，两步：

1. **先四舍五入到整 GiB**，还原「盒子上印的那个数」。驱动报的从来不是标称值——本机
   RTX 5070 Ti 16GB 实测报 **15.92 GiB**，12GB 卡也只报 11 点几。直接向下取档会把
   每张卡都降一级，白白少一个分离器实例，而且**输出里没有任何提示**。这正是 `auto`
   要消灭的那种静默错配。
2. **再减去预留**（`reserve_for_capacity()`，见下），然后取能满足的最大档。少了这一步，
   10GB 卡会去匹配 `high` 的 10GiB 要求——拿一份从来不存在的余量去开三个实例。
3. **最后在 `standard_large_vram` 处封顶**，除非卡报 ≥24GB（见下「`auto` 的上限」）。


### `auto` 的上限：最高只到 `standard_large_vram`

**有余量不等于该用。** `high` 跑三个分离 worker，而 E7 的 worker 阶梯把吞吐峰值定在
**两个**——三个是实测更慢的。所以让 16GB 卡从 `auto` 拿到 `high`，等于因为卡更大而
换来一次更慢的运行，那正好和档位的用意相反。

`auto` 因此在 `standard_large_vram` 处封顶，**只有硬件报 ≥24GB 显存才放行 `high`**：
到那个尺寸，问题已经从「快不快」变成「放不放得下」。`high` 始终可以手填。

⚠ 封顶档 2026-09-02 从 `standard` 抬到 `standard_large_vram`：**「有余量不等于该多开
worker」不蕴含「有余量也不该花」**。压在 `standard` 等于连显存预算一起扣掉，而那份预算
唯一的花家是裁判，跟 worker 数无关。

这条上限只会**往下压**，不会把小卡抬上去。

### 显存不够时的告警

两个 GPU 阶段各自在拿到 profile 之后、干活之前，拿 `device.free_vram_gib()`（驱动报的
**当下空闲**）和所选档位的要求比一次，不够就打一条 `gpu-vram-short` 警告。

**只告警，不降档也不拒跑。** 两条理由，第二条是决定性的：

- 档位决定分离 worker 数，worker 数决定分块规划，所以中途改档会**改变产物边界**——
  同一个文件会因为「当时还开着什么」而产出不同的切分。`auto` 之所以读**容量**而不读
  空闲，就是为了让它的答案稳定；活数字不该从这里绕回来变成决策。
- **不够 ≠ 跑不了。** `entry` 实测峰值 2.26GiB，要求写的是 3GiB，略低于要求的卡照样能
  跑完不少素材。拒跑会拿走本来能成的运行。

**判据与位置对 `auto` 和手填完全一致**：一张 6GB 卡手填 `standard`，和另一张卡经
`auto` 落到 `standard`，在同一处得到同一句话。用户点了名要某个档位，欠他的是**事实**，
不是替他改主意。

已在最小档时不会建议「改用更小的档位」——那句话在最需要出路的场合毫无用处；那时只留
「关掉占显存的程序」和 `--device cpu`。

没有可用 CUDA 设备时**不告警**：那台机器在 CPU 路上，`resolve_device` 已经说过一次了。

没有可用 CUDA 设备时回落到最小档 `entry`，且**不额外告警**——`resolve_device` 已经每个阶段
警告过一次 CPU 回退，再说一遍只是换个说法重复。

### 预留曲线：`容量 / 8 + 0.5`

预留随卡变大，因为卡上本来就跑着的东西也随卡变大：更大的卡通常意味着更大的桌面、
更多显示器、以及一个更舍得缓存的驱动。固定值要么对 4GB 卡太阔绰，要么对 24GB 卡
太吝啬。

两个常数不是拟合出来的，是**选来让曲线正好穿过档位表**的：

| 卡的容量 | 预留 | 估算空闲 | 选中 |
| ---: | ---: | ---: | --- |
| 4GB | 1.00 | **3.00** | `entry`（要 3） |
| 8GB | 1.50 | **6.50** | `standard`（要 6.5） |
| 12GB | 2.00 | **10.00** | `standard_large_vram`（够 `high`，被上限压住） |
| 16GB | 2.50 | 13.50 | `standard_large_vram`（同上） |
| 24GB | 3.50 | 20.50 | `high`（上限在此放行） |

前三行的「估算空闲」与档位要求逐位相等（第三行随后被 `auto` 的上限压回 `standard`，那是另一回事）——这正是把它写成规则而不是第四列的意义：
同样那三个数，但现在它延伸到了表里没写过的卡。所以匹配用 `<=` 而非 `<`，
否则每张标称卡都会掉一档。

**它是探测余量，不是对真实占用的核算。** 进程内没人知道真实占用。实测对照
（RTX 5070 Ti，桌面空闲）：驱动报总量 15.92 GiB，`mem_get_info` 报当时实际占用
**1.24 GiB**，而公式假设 2.50 —— **偏保守 1.18 GiB**，这是安全的那个方向
（估少了空闲只会掉一档，估多了会 OOM）。而且对照是在桌面空闲时取的：真开着浏览器
或游戏时占用会高得多，所以 2× 的余量并不夸张。

## WT 并发（历史记录：WT 曾按档位缩放）

> ⚠️ **本节描述的设计已经不存在。** 2026-08-02 起 ASR 固定单 worker，`wt_instances`
> 已删除，档位只缩放分离器实例数。保留它是因为下面的显存曲线仍是有效实测，换 GPU 或
> 重新考虑 ASR 并发时要回来读；**不要据此推断现行行为**。

模型为 `large-v3-turbo`。生产加载路径在 CPU 上**直接以 FP16 构建**模型，
LayerNorm 参数保留 FP32，再迁到 CUDA；单实例显存峰值 2.17GiB（活跃 tensor
2.00GiB）。发布的 checkpoint 本就是 FP16，而 `Whisper(dims)` 按默认 dtype 构建，
所以原来的 `whisper.load_model(...).half()` 路径会让 FP32 模型（3.2GB）与
checkpoint（1.6GB）同时驻留、再额外分配一份 FP16 副本；直接建 FP16 把**加载瞬时
RAM 从 5.10GB 降到 3.57GB（−30%）**——两条路径各在独立进程测两次，分别为
5.10/5.11 与 3.57/3.57GB（同进程连测会读高：释放模型并不会把页还给 OS，
第二条路径从被抬高的工作集起算）。改默认 dtype 是进程级操作，但它只发生在
`_WHISPER_MODEL_LOAD_LOCK` 内、且仅 CUDA 路径启用，而 CUDA 下 GPU stage gate
已保证 separator 模型族不与 WT 同时驻留。非官方模型名（本地 `.pt`、HF 标识符）
仍回落 whisper-timestamped 自己的解析与原加载路径。

`WtModelPool.warm()` 一次性读入 checkpoint 并**构建全部实例**，构建完立即丢弃
checkpoint（因此它计入预热期的峰值，而非常驻内存）。池的大小来自 shard 计划，
所有实例本来就都会被用到，惰性加载只是把其中一次构建挪到了第二个 shard 的关键
路径上——`wt-parallelism.md`「损失分解」把这项「模型加载错峰」计为实测损失。Whisper 的内部上下文满窗为 30 秒；并发 sweep 给每个实例输入
60 秒真实人声音频，使每个实例连续处理两个满窗，避免短任务启动噪声左右结论。

| 实例数 | 总 wall time | 相对单实例吞吐 | 合计峰值 reserved |
| ---: | ---: | ---: | ---: |

### 分块：等长、且块数是 worker 数的整数倍（2026-07-30）

原先固定 600 秒 core，块数 = `ceil(时长/600)`，于是每个 worker 分到的块数不等、
末块还特别短。现在改为：先定 worker 数，再取**最小的整数轮数**使每块 core ≤ 600 秒，
块数 = `轮数 × worker 数`，各块等长。44.5 分钟素材 2 worker 时由 5 块（4×600s + 269s）
变为 **6 块 × 444.8s**——每个 worker 恰好 3 块，且单块缓冲小了约 26%。

- **worker 数由时长阶梯决定**（`separator_worker_limit`，每 300 秒音频多一个 worker）。
  分离跑在 VAD 之前，拿不到有效语音，所以只能看**墙钟时长**——这与 WT 那条按**有效语音**
  的阶梯口径不同，两个 300 不是同一个东西。
- 这条阶梯是**必需项**：块数变成 worker 数的整数倍之后，原来「短文件只有一块 → 自然只有
  一个 worker」的隐式门槛就消失了。
- **不需要另设 core 最小值**：一轮时 core = 时长/worker 数，阶梯把它下界在
  `300k/(k+1)`，k=1 时最小，即 **150 秒**；对 10 秒 pad 而言最坏是 13% 的冗余计算。
- 待拼接结果上限由 `2 × instances` 降为 **`instances + 1`**：等长块消除了那个
  2 倍前瞻本来要掩盖的落后块，同时少驻留几块已解码音频。

**产物影响**：块边界移动，分离结果因此**与 worker 数相关**，且与旧版本不同。

但**既有 `-vocal.ogg` 可以放心复用**——它就是一段有效的人声音轨，下游 VAD/ASR 不关心它
当初是怎么分块的，块边界移动带来的接缝差异与换个 profile 重跑属于同一量级。2026-08-18 起
新产物是 16 kHz 单声道（见 README_DEV「交付两模式」），旧的 44.1 kHz 立体声产物同样照读
不误，只是更大、且带内更脏——复用与否只影响质量，不影响正确性。这正是
「按存在性跳过、不校验内容」的既有 resume 设计，**不要因为改了分块就强制要求重跑，也不要
求 resume 时 GPU profile 一致**。

只有一种情况需要先删除重跑：**你要的是可复现的对照**（A/B 实验、prompt 迭代测试床、
分割金标准标定等需要冻结上游的场景）。日常生产跑不在此列。

## RAM 口径：`peak_mem` 是**按 stage 采样**的

`peak_gmem` 可以用 `torch.cuda.reset_peak_memory_stats` 每个 stage 归零，但
Windows 的 `PeakWorkingSetSize`（以及 POSIX 的 `ru_maxrss`）是**进程生命周期峰值，
没有任何 API 能重置**。同进程跑 sep→WT 时，WT 报的数必然 ≥ 分离阶段的峰值；
batch 模式下第一个任务冲高后，后面每个任务都继承那个数，于是预算告警变成永久噪声、
真正的回归反而看不见。

因此 `StageMemorySampler`（`speech/runtime/resource_usage.py`）用一个 0.25s 间隔的
采样线程记录**当前**工作集，给每个 stage 独立的峰值，**预算判定用的就是这个 stage 值**。
两个代价必须记住：

- 采样会**漏掉短于采样间隔的尖峰**，所以它是下界。模型加载那种数秒级瞬时占用能稳定抓到。
- 进程生命周期峰值并未丢弃：当它高于 stage 值时，额外打印一行 `peak_mem_process`，
  这样既不会把 stage 数误读成整轮，也能看出前面的 stage 冲得更高。

单进程 CLI（`vad_asr` / `energy` 的 `main()`）不传 sampler，退化为原来的进程峰值——
那里一个进程只有一个 stage，进程峰值本来就是对的。

## 一致性与边界

- FP16 主体 / FP32 LayerNorm 的 185 秒真实音频对照输出与旧 FP32 staging
  路径逐字节一致，并把单实例峰值从 5.28GiB 降至 2.17GiB。
- FP16 直建（2026-07-30）与旧 `load_model(...).half()` 路径构建出的模型，
  **589 个 parameter/buffer 全部逐比特相同，dtype 亦相同**——权重相同则输出
  不可能不同，故未另跑对齐比对。验证脚本 `out/mt8g-stress/verify_fp16_build.py`
  （本地产物，不随仓库发布）：`--mode compare` 比权重，`--mode stock|new`
  各自独占一个进程测峰值。
- 并发 sweep 覆盖正常 efficient 路径；beam rescue / naive fallback 不会增加
  模型权重份数，但极端输入的临时 activation 仍由 `heavy_resource` 守卫测试持续观察。
- GPU model-family gate 允许多个 separator 或多个 WT 同类任务并行，但不允许
  两个模型族跨任务同时驻留；切换前由最后一个活跃任务释放上一模型族。
- 数值是这套硬件与依赖版本上的实测标定，不应外推为所有 GPU 的同等吞吐比例。
