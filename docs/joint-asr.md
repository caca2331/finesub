# 一体转写：各家的行为、设计取舍与理由

`--asr mai2|gemini-35t|moss-pro|moss-local`（`speech/joint/`）的开发者文档。一体转写是一个模型交回整份带时间与说话人的转写，
替掉本地的人声分离、VAD、Whisper 与声学说话人分离那一串；后端是云端三家与本机 GPU 上的开源 MOSS（[本地 MOSS](#本地-moss)）。
这里写各家模型实际怎么表现、生产为它们补了什么、为什么这样接。改 `speech/joint/`、一体转写任务在 `stages.py` 里的分支或重叠规则之前先读；用户向的行为在
[`manual/joint-asr.md`](manual/joint-asr.md)，模块地图在 [`architecture.md`](architecture.md) 的 `speech/joint/` 一行，
重叠的行在 LLM 层的规则与理由在 [`llm_design_notes.md`](llm_design_notes.md)「`同时` / `换回` 的决策记录」。

## 为什么接、接成什么样

2026-10 的一轮实验在纠错前的 `-raw.srt` 上让读者模型逐窗盲判云端结果与生产（每窗 5 分钟、A/B 随机，附人工字幕作参照，
只比文字与分句、关掉说话人；偏好率 = 云端赢的窗 /（两边赢的窗之和），区间按素材重抽）：

- **MAI2**（不跑任何本地模型，词进生产的分句 DP）：18 份、两个读者都同意才算赢，90.6% [80.0, 97.8]；中文、日语几乎全胜，
  英文多数赢。坍缩行（≥5 加权字、快于 25 字 / 秒）每小时 8.2 → 0.4，音频裁判确认的幻觉 11 → 2。
- **MOSS Pro**：7 份、一个读者，段直接当行 71%，段内按 Silero 定时之后对段直接当行 92.6%。说话人在五人以内的整集上是各路线里最好的
  （[`diarization-findings.md`](diarization-findings.md)「换成一体的转写 + 分人模型」）。
- **Gemini 3.5 Transcribe（35t）**：12 份、一个读者，35%（输在专名听错与抢话处的碎行，免费层）；加本地分句模型对不加 83%。

owner 2026-10-29：云端不必全面打赢生产，持平或可接受的退化也行，换来的是不用本地算力。所以接成**方向一**：一个任务可以不跑人声分离、
Whisper 与第二模型，由云端转写原始混音，本地只做轻量的事（解码、Silero、分句 DP、时间轴整理），重的本地计算做成可选项
（这一期只有 `--asr-aligner`）。三家默认都关。**方向二**（本地链路与云端深度融合）没做，想法在 [`speech-followups.md`](speech-followups.md)。
之后接的本地 MOSS 走同一条路，只是解码在本机 GPU 上，见[本地 MOSS](#本地-moss)。

## 各家的已知行为

改适配器之前要知道的，都是实测出来的：

- **35t**：
  - 时间在 100 ms 网格上，相邻词首尾相接；生产 DP 把停顿 0 当连读，所以进 DP 前相接处的前一个词收 10 ms。
  - 按说话人成段输出：B 的附和排在 A 那句之后、时间更早。往回跳的时间几乎全在换人处，是对的，**不能按时间排序**（话轮靠输出顺序）。
  - 真坏的时间少而有形：end < start、单词时长 > 3 s、同一个人往回跳；常像数字错了一位（3.5 → 353.6），会带着后面一串词一起偏。
  - 会提前收尾、偶尔复读退化（一个词连写上百次，响应 `status` 不是 `completed`）；输出上限 32 768 token，按 540 s 切窗（600 s 就退化）。
  - 偶尔整窗（约 9 分钟）的回答不带说话人。混音只会让它漏、不会多写（BGM 下的英语句会整句丢）。
  - 免费 key 每天每把 24 次可用（第 25 次被拒），额度日从太平洋时间零点起。
- **MOSS Pro**：
  - 只有段级时间、没有词（`verbose_json` 被拒，`diarized_json` 也只有段）；段是话轮，不同说话人的段会互相重叠、各带各的字。
  - 输出上限约 16 384 token，撞上限时**静默截断**：状态照样 `SUCCESS`，最后一段坏掉（end 为 0）。会静默漏段。
  - 会把英文素材整份转成日语译文（`SUCCESS`、一整段）；API 没有语种、prompt 或翻译参数，只能事后检测。
  - 常把一个人拆成几个标签（一集 12 个标签对 4 个人）；续调、补调各是独立调用，标签重新编号。
  - 每把 key 每天约 1.25 音频小时免费，之后扣账户余额（预付费；生产只让池里最后一把走到这一步，见「设计取舍」）；控制台计的比文件时长多 5–6%；额度日从北京时间零点起，要登录一次控制台才刷新。
- **MAI2**：
  - 词级时间与说话人；中日文每个字恒 79 ms、词间隙偏大。原始的行首晚、行尾早：对人工逐词时间，行首晚约 0.06 s（生产早约 0.06 s），行尾早约 0.13 s（生产早约 0.06 s），最早的一成早 0.3 s 以上（生产 0.11 s）；英文的行首对 Whisper 也晚约 0.09 s。词在时间上不重叠（不标同时说话）。
  - 两条路：OpenRouter（`microsoft/mai-transcribe-2`，转到 Azure，JSON + base64）与 Azure fast transcription（multipart、自己的资源）；两边回答的形状不同（`words` 对 `phrases`）。
  - 一行可能含两个人的词（25 份 12 745 行里 91 行）。
- **Silero 会漏听**：分离后偏安静的真语音、BGM 下的旁白（一处 64 s 空档生产 VAD 有 14 s 语音、Silero 0 s），所以凡是拿 Silero 定时或当闸门的地方都要限住它出错的后果。

## 设计取舍

| 决策 | 理由 |
| --- | --- |
| 云端后端不接 `asr_backend` 契约（[`asr-backends.md`](asr-backends.md)），直接把词或段送进分句 DP | 那个契约是对齐循环里逐窗解码的面；云端整份转写、自带时间与说话人，硬套要伪造 refine 信号 |
| 云端任务跳过人声分离、Whisper、第二模型、语言重解与 stabilize；stable 原样拷贝 aligned（profile -1），坍缩修复、补空档也不跑 | 这些规则是为 Whisper 的失败写的：缺能量与 confidence 时噪声那几条不触发，剩下的套话清理在没有第二模型证据时会删掉云端真听到的致谢 |
| 「是不是云端任务」看产物 metadata 记的后端（先 stable、再 aligned），不看这次的 `--asr` | [resume 延续任务自己的产物与当时的选择](../README_DEV.md#复用的依据是任务身份不是质量判断)；否则云端产物换成 `--asr local` 续跑时，quality 档的声学说话人分离去读不存在的人声轨，整个任务崩掉 |
| 每次调用的原始回答缓存在任务旁的 `<stem>-cloud/`，归进「保留」；源音频的指纹（`identity.json` 的 `audio`）对不上时，那个缓存目录的回答整个作废、删掉重问，打 `Warning:`；后端、模型、切窗参数、语种对不上只告警（`cache.py`） | 删产物重跑不再花额度；同一段音频再问一次回答会不同，删了就回不去。音频是 [compatibility key](../README_DEV.md#复用的依据是任务身份不是质量判断)：调用按窗口起止命名，换了录音还复用，旧回答就按时间贴到新音频上，这是错的结果，不是旧参数。旧回答删掉而不是按音频分子目录留着：一个任务目录只对一个源，留着的只会越积越多，不会再被读到；离线重放不删，只是一份都不用 |
| 35t、MOSS Pro 每个话轮单独跑一次分句 DP，各话轮的行按起点合并；不在全局 DP 上加强制切点 | 话轮交错时全局 DP 的词序本身没有定义，全局 DP 的接缝只是打折、一个 piece 可以吞掉它（MOSS Pro 在全局 DP 下有 19 个 piece 把两个人并进一行）；强制切点要改 DP 与它的剪枝证明，效果与「话轮边界必切」相同 |
| MAI2 不切话轮，走一次全局 DP；不按词上的说话人拆行（owner 2026-10-30） | 它的词在时间上不重叠，全局 DP 就是验收过的那一臂；按说话人拆开多出 103 行，几乎都是 1 秒以下、一两个字的碎行 |
| MAI2 的行分句之后行首提前、行尾推后各 0.1 s，只占和相邻行之间的空隙（行尾先占），不越过音频末尾（`lines.widened`，owner 2026-11-03）；首字的开始、末字的结束跟着挪，metadata 记 `edge_pad` | owner 对听觉得 MAI2 比生产紧。离线比了三种扩法：这个常数在人工逐词时间上行首、行尾与生产对齐（交付层行首 −0.044 对 −0.055，行尾 +0.241 对 +0.237），Silero 两个方向的标记（语音露在行外、行伸进静音）在 13 份上都不比生产多；按中、英、日分开看，只有日语的「行尾后露出语音」仍比生产多（2.5% 对 1.6%）。代价是行尾偏差的 p90 从 0.31 到 0.41 s（生产 0.48）。生产的尾词能量延长跑在混音上，有空间的行里约四分之一（24%）延满 1 s 上限，行尾拖 > 1 s 的行从 0.9% 到 12.7%（多半是背景音、笑声让能量下不去，没逐条核实）；按 Silero 的语音延行尾，行尾又比生产晚约 0.15 s；都没用。两行同一时刻开始、按说话人排在后面的那行只有一个 10 ms 的词时，放宽会让两条 cue 多叠约 0.1 s，与下一行零长词那条同类，13 份里没出现，不改 |
| 跨两个人的行，`line_speaker` 取词时长占多数的那个人；缺说话人的段共用 `unknown` 一个键 | `unknown` 是云端说的「某个人」，所以它的两段互相重叠时照样截断；与「没有键的行自成一个键」（模型补写、裁判补出，没人说过是谁）的区别是有意的 |
| 本地分句模型只给 35t 开、默认开（owner 2026-10-30） | 加了对不加 83%；35t 的词首尾相接、DP 在没有空隙处切代价高，会留下 40 多字一行。常驻 1.1 GB（峰值 1.9 GB）、30 分钟素材跑 4 s，算轻量 |
| MOSS Pro 段内的字时间默认由 Silero 定（S5b），超长段可选强制对齐（`--asr-aligner`，S6b），对齐失败的段退回 S5b（owner 2026-10-30） | owner：「首先是不能丢字」——Silero 只决定时间，字全部来自 MOSS；Silero 在一段里听到的语音不到三成就整段按字数插值。Silero 定时对段直接当行 92.6%；对齐器把段内切点误差 > 0.5 s 的比例从 11% 降到 6%，读者看不出差别，CPU 上 30 分钟 25–85 s、约 2.4 GB，所以只做可选项 |
| S5b 的段首最多修 0.1 s、段尾最多修 1.0 s，最后一次停顿之后不足 0.1 s 的一小段不算语音（`moss_timing.py`） | MOSS 的段首本来就准（中位误差 0.055 s），修多了的全是 Silero 漏了轻起音；段尾的修剪多半是对的，错的约 4% 用 Silero 的任何特征都分不出，上限只限最坏情况（两边都卡 0.5 s 时英文行尾 > 0.5 s 的比例 21% → 31%，否了）；末尾的咔哒声、呼吸会让最后的字挤在一起 |
| MOSS Pro 撞输出上限就从最后一个好段续调；≥30 s 的空档要 Silero 听到 ≥3 s 人声才补调一次（owner 2026-10-30：「要确认一下是真的缺失还是假的，要做一个 balance」） | 截断是静默的，不续就丢尾巴；补调什么也没补回的 16 个空档 Silero 都只听到 0–0.3 s（片头、PV、休息段）。Silero 漏听时少补一次，按闸门不补 |
| 续调、补调回来的说话人用声纹（WeSpeaker + PLDA，与默认说话人分离同一个模型）一对一配回主调用的标签，相似度 < 0.8 的当新人（owner 2026-10-30） | 原样混用时续调里约八成的标签配错人；在多人素材的合成续调上按精修字幕的真人计，声纹重连续调对 95.3%、错并 0.8%，补调对 78.9%、错并 0.2%（错拆多是说得少的标签）。声纹模型拿不到时退回只加前缀 |
| 只在给了 `--language` 时做语种检查：对不上就整份重转一次，仍不对报错停下，不悄悄退回本地 | MOSS Pro 的译文是 `SUCCESS`；悄悄退回本地会让用户以为用的是云端结果 |
| MOSS Pro 本地记账：选 key 时先预留这次调用（按控制台的计法乘 1.06，每把 1.2 h 停），只有服务端肯定没收下（上传被拒、根本没连上）才退回，退在预留的那一天的账上（已过北京零点就不退，也不把新的一天记成用完）；轮询失败、5xx、丢了回答都照记 | 服务端可能已经计费：多记只会早一步换 key，少记会扣账户余额（owner：不超时的主要意义是余额为 0 时不截断输出）。两个任务并行时不会挤进同一把 key 剩下的额度 |
| `[asr] moss_pro_paid`（默认开）：池里最后一把 key 不设每天的 1.2 h 停，一次调用放不进前面几把剩下的额度时轮到它，超出免费额度的部分扣它的余额；它回 402 是余额用完或当天还没刷新，任务停下、不把它记成当天用完（登录控制台或充值后当天就能重跑；代价是批处理里之后每一项都先上传一次才被拒），前面的 key 回 402 照旧记成当天用完；不另打告警（owner 2026-11-09） | owner：用户放进 key 就预期可能付费，和 MAI2 一样；MOSS Pro 是预付费，扣到余额为零为止，支出不会失控。「最后一把」按解析后的池（点名的顺序，或 `.env` 前 3 把），不另设标记，免得多一个要配的东西 |
| MAI2 与 35t 对没收到回答（连接重置、代理断开、超时）与临时的状态码（408、409、425、429、5xx）在同一把 key 上就地退避重试，判定与 LLM 层共用 `api_http.is_retryable_http_error`：MAI2 按 `RETRY_WAITS`（30 / 60 / 120 s，`Retry-After` 优先），35t 一次请求（与它的上传）最多 4 次、每次等 60 s，2xx 的正文不是 JSON 对象也算临时；MAI2 的窗口从不拆半，504 照 5xx 重试，413 直接报错（owner 2026-11-07） | 一个长源切成好几窗，一次连接重置或一次 502 曾让整个云端阶段失败（已缓存的窗不重花额度，但要人工重跑）。不拆半：Azure fast transcription 写明单个文件 120 分钟、300 MB 以内，一窗 100 分钟的上传 MP3（16 kHz 单声道 64 kbps）约 48 MB；以前把 504 当「窗太大」缓存下来、从此拆半，可 504 是网关忙，缓存之后这个任务的窗口形状就永久变了 |
| 35t 只用免费 key 池，不自动转付费池（owner 2026-10-30）；三家都一把 key 用到撞日额度才换 | 不让用户在不知情时花钱；交替用会让失败没法归到哪把 key |
| MAI2 的 OpenRouter 与 Azure 两条路都接，端点可配（owner 2026-10-30）；回答按自己的形状解析，不按这次的路线 | owner：以后多半也是这两种格式之一，只是端点换；按形状解析让 30 分钟以内的源换了路线照样读回缓存（窗名两边相同） |
| 云端任务的说话人只来自它自己的识别结果，不跑声学说话人分离；不管 `--diarize` 是哪档都从 `line_speaker` 写 `-diar-rows.json`，不读不写 `-diar.json`（owner 2026-10-30） | 三窗上 MOSS Pro 加 Sol 裁判比它自己的标签每分钟编辑代价 2.6 → 2.0，再加声学置信标 2.0 → 2.0：逐行改成声学的备选只有 6 行变好、40 行变坏。`-diar.json` 是声学分离对这段音频的产物，任务回到本地识别时照用 |
| 批处理里云端任务走 asr bin 的网络道，默认两个 worker（owner 2026-10-30） | 它等的是网络不是 GPU，排在本地 ASR 后面就白等；共享状态见 [`batch-scheduler.md`](batch-scheduler.md)「asr bin 的两条道」 |
| 云端请求与 LLM 层走同一条代理设置（`[api] proxy`，`api_http.py`；owner 2026-10-30） | 一个用户只有一套网络环境；两把 MOSS key 的端点都在国内，不加国际端点的选项 |
| 重叠规则只管有分组键的行，本地链路不填 `line_speaker`（owner 2026-10-30）；本地只有坍缩行挪过去、下一行整段落在它里面（或切开会让一行又挤成一闪而过）的那一段另走叠拉道（`overlap_lane`，[`asr-stabilize.md`](asr-stabilize.md)「坍缩行」） | 本地的重叠多是 Whisper 的缺陷（幻觉长段裹住真台词），按说话人放开就会照原样叠着显示，是质量上的改动，要单独验；叠拉的那一段是修复确知「与下一行同时、不知道是谁」的，所以不填说话人，只给一个键 |
| 不同说话人的重叠行交付成各自的 cue，**绝不**并成一条两行的 cue（owner 2026-10-30：「这绝对是不符合设计理念的」）；不在交付前把重叠排成先后 | 排成先后就要截短或推后后一条：截短让 MOSS Pro 对齐那一臂的坍缩行每小时 6 → 78 行，这正是重叠处的主要损失 |
| MAI2 换人处一个长度为 0 的词正好落在下一个人的开始点上时，两条 cue 同时显示约 0.31 s，接受、不改（owner 2026-10-31） | 时间轴修复把零长词撑长 10 ms，延长再加 0.3 s；13 份真实素材里没出现 |

## 退化的修补

`--asr-repair`（`repair.py` 放共用的探测，各家的补法在各自适配器的 `transcribe()` 里，35t Live 的客户端是 `live.py`）。
用户向的行为在 [`manual/joint-asr.md`](manual/joint-asr.md)「补漏转与复读」。

**找什么**（离线调查的读数，25 份、各前 30 分钟，拿同一时间的其余几路转写当尺子）：

- 漏转：这一家 ≥2 s 的空档（词各向外放 0.3 s）里 Silero 听到 ≥1.5 s 语音。35t 每小时 12 处真漏转、MAI2 1.4 处、MOSS Pro 3 处；
  这个闸的精度 / 召回在 35t 上 54% / 74%、MAI2 16% / 75%（多出来的是笑声、音乐与没人写的附和，重问回来几乎都是空的）。

## 本地 MOSS

`--asr moss-local`（`speech/joint/moss_local/`）：开源 MOSS-Transcribe-Diarize（0.9B，Apache-2.0）在本机 GPU 上由进程内的快速解码器解码，
加运行时救援，交回与 MOSS Pro 同形的段（段级时间、话轮、不同人的段可以重叠），之后的建行与 MOSS Pro 那一支相同（S5b / S6b、按话轮分句）。

**为什么接**（owner 2026-11-02 起）：MOSS Pro 是另一个更强的模型（上游 README 的说法；官方基准 AliMeeting CER 24.86 → 18.22），
不是同一份权重加服务端救援。开源版的失败（复读、整秒时间戳、中场后时间跳走、提前收尾、整份换语种）是一处处的，救援补得上；逐词听写的差距补不上。
到纠错之前与 Pro、本地 Whisper 比（2026-11-05；开发 11 份剪段，留出 4 份没有哪条规则在上面调过）：

- CER（`-raw.srt` 对人工字幕）：开发 11 份本地 0.109、Pro 0.108、本地 Whisper 0.133；留出 4 份 0.108 / 0.108 / 0.126。中文差得最多（0.151 / 0.158 / 0.221）。
- 读者盲判（DeepSeek 一个读者、附人工字幕，比的是还没做第三阶段工程项的版本）：本地对 Pro 偏好率 31.5% [15.4, 47.4]，「内容」一项 9 : 34，差在听错与漏话。
- 时间坍缩的行只出在本地 Whisper（11 份 40 行）；对 Pro 整段错开 > 3 s 的行 4 行。
- 每份耗时中位：本地 121 s、本地 Whisper 146 s、Pro 216 s（顺带测时；本地不含约 20 s 的模型加载，Pro 不含上传与排队）。
- 说话人（同一档节目有真值的 5 份）：B³ Pro 0.940、本地 0.917、本地 Whisper 加声学分离 0.897；非这档节目的素材上本地比 Pro 多出不少标签，没有真值读不出对错。
- 行时间：与 Pro 的差在 0.1 s 以内；中文行首比 Pro 晚约 0.08 s（中位，4 份中文里 3 份），不改，记在 [`speech-followups.md`](speech-followups.md)。

### 开源 MOSS 的已知行为

- 上游给中文默认 prompt 与一份英文配方，模型没有语种参数；中文 prompt 下一份英文演讲前十分钟整份转成了德语（另五份英文没翻），用英文 prompt 就正常。
  翻了就从第一段起一直翻下去。8 位 K/V（int8）也把它翻成西班牙语、把一份中文转成繁体。
- 复读：一段里同一串 token 绕圈，或连写几百个「...」、同一句「おはようございます」。
- 整秒时间戳：一整份的时间戳都是 `.00`，说话人跟着合并（旧的 transformers 解码上见过，新解码器没复现）。
- 中场长休息之后时间整体后跳 180 s、写到音频结尾之外；也见过从 900 s 跳回 307 s 把一段重写一遍（加了热词时）。
- 提前收尾：还有几分钟话就结束了；token 用完也是静默的。
- 跳过片头（冠名口播、PV）从第一句正片起头。
- 偶尔写出一段离谱的长段尾（`Mum.` 21.5–222.1 s），后面接着正常；真话的段最长 23 s。
- 输出 `[音楽]` 这类声学事件段（标签不是 `S01` 的形式）。
- 一个人常被拆成两个标签，比 Pro 多。
- 段尾会拉过掌声与停顿（`Thank you, Brett.` 拉了 14 s）。

### 接法与取舍

| 决策 | 理由 |
| --- | --- |
| 只支持 CUDA 的 NVIDIA 卡、计算能力 8.0 以上（owner 2026-11-03 / 11-05），档位的空闲显存不低于 `standard` 的 6.5 GiB；没有可用的 CUDA、AMD 卡、8.0 以下、`entry` 档、`--gpu-tier cpu`、`--device cpu` 都报错停下，提示改用 `--asr local` 或云端，不悄悄退回（`device.moss_local_unusable_reason`） | 8.0 以下 bf16 没有张量核，prefill 的 bf16 SDPA 退到 math 后端、分数矩阵装不下；ROCm 下 `torch.cuda` 也可用，但能力号与 fp8 格式不是一回事。`entry` 档（3 GiB）扣掉权重、prefill 峰值与余量放不下一分钟的音频，不拦就要等下载、加载之后才失败。不退回的理由与云端的语种检查相同：用户以为用的是 MOSS |
| 这个检查在建任务时做（单任务进任务前、批处理读完清单后、追加的行加入时），只查这次真要解码的任务：到 `aligned` 阶段、`-aligned.json` 还不在；URL 在下载前不知道产物，没给输出路径就按这次的 `--asr` 算（这样的 URL 任务只续跑 LLM 阶段时，给 `--output` 或不写 `--asr`） | 不等下载 1.7 GB、不等排进 asr bin 才报；续跑已有产物的 LLM 阶段不挡 |
| 显存按本次运行的 `--gpu-tier` 与设备算：档位的空闲显存数扣 `CONTEXT_GIB`（0.3 GiB，分配器之外的 CUDA 上下文、cuBLAS、Triton，本机解码后实测 0.27–0.29），其余给 PyTorch 的分配器，并用 `set_per_process_memory_fraction` 卡在这里 | 档位的数是整个进程能用的；Windows 上超出不报错、静默溢到共享内存，只能事前卡住 |

| 批处理走 asr bin 的 GPU 道；解码期间持有 `joint.GPU_LOCK`，网络道上云端任务的强制对齐等它（owner 2026-11-05）。⚠ 锁的顺序先 `GPU_LOCK` 再 Silero 的锁（`silero_exclusive`） | GPU 道一次一个任务，网络道上的强制对齐是唯一会同时占卡的；显存上限管的是整个进程，锁挡的是同时计算。对齐模型加载后常驻，它的权重由本地 MOSS 按 `memory_allocated()` 算预算时扣掉，只让每趟变短。本地 MOSS 拿着 `GPU_LOCK` 跑 Silero，反过来拿就死锁 |
| 音频是原始混音，ffmpeg 解成 16 kHz float32 喂模型；S5b 另解一份 int16（与 MOSS Pro 那一支共用），音频解两次 | 模型的读数都是在 float32 上量的，经 int16 再转输入就不同；S5b 的 Silero 时间在 int16 上量过。解码一次几秒，不值得为它改 S5b 的接口 |
| 不缓存解码结果：`-aligned.json` 就是结果，删了重跑重新解码（owner 2026-11-05） | 云端缓存是因为同一段音频再问回答会不同、还花额度；本地重解只花时间（30 分钟约 2–4 分钟 GPU），不值得多一套身份与清理规则 |

### 本地 MOSS 的救援

`rescue.py` 编排、`rules.py` 放纯判断。模型整份的上下文一直在：救援把解码退回到某个 token 边界再接着解（`Decoder` 的 K/V 已经在缓冲里，退回只是挪位置），说话人编号还是这一趟的。
阈值都是在出过事的素材上定的（样本内），各条在开发 11 份上多半只出场一两次；留出 4 份上没有退步。按作用的地方：

- **在一趟里**：
  - 复读（`loop`）：一段尾部 48 个 token 以周期 ≤12 重复，或一段超过 400 token（Pro 与开源所有运行里最长的段约 230 token），退回段首，先对段内已写的 token 加重复惩罚（1.3）重解，再采样（温度 0.7）重解，还不行就放弃这一块：下一段强制从 10 s 之后 Silero 的下一处说话开始，留下的空档交补转。
    连续 5 段都没有字母或数字、或同一个标签连续 5 段文字相同，也放弃（几个人连喊同一句是真话，所以要同一个标签）。
  - 整秒时间戳：连续两个 `.00` 之后，下一个时间戳的第二位小数不许是 0。
  - 跳段：新段起点在已转到的地方之后留下 ≥30 s 空档、空档里 Silero 有 ≥3 s 说话，退回去把起点强制写成成片说话开始处（起点后 30 s 内 ≥9 s 说话；只有零星人声的片头 PV 不算：强制到那里，模型把 307 s 的台词写到了 46 s）。同一处最多两次。
    还没出第一段时不强制：第一个时间戳没有前文可漂，晚起是模型略过了片头，略过的那段交补转单独解（强制的话，一份的冠名口播整段晚了约 10 s、持续几分钟）。
  - 时间回跳：新段起点比已转到的地方早 30 s 以上，退回去强制从那之后的下一处说话开始，同一处最多两次；30 s 以内可能是有人插话。「已转到的地方」不算长过 30 s 的段（离谱的段尾会把它盖住的几分钟真话跳掉）。
  - 提前收尾：结束时离音频末尾还有 ≥30 s、其中 Silero 有 ≥3 s 说话，把结束换成新段，强制从成片说话处开始，最多两次。
  - 语种（给了 `--language` 时）：每攒够一段文字（英文 30 词、其他 40 个字，一个拉丁词算一个字）测一次：英文看常用虚词占比（< 0.15 算错）、日语看假名占比（< 0.2）、中文看假名与拉丁字母、其余照 MOSS Pro 只分字母体系。
    错了就把这批文字的第一段退回重解，先禁它写的第一个词，再禁它写的全部字母；还错就放回原文、这一趟不再测（源里可能真有大段别的语言）。
    两次人为翻转（中文 prompt、int8）都在第一段触发、禁第一个词就转回英文；在全部本地产物上按代码的窗重算，正常输出英文最低 0.19、日语最低 0.42，英文这侧余量小，误报的代价是一段重解。繁简不算语种错。
  - token 预算：每秒音频 12 个 token 加 512；撞上就停，剩下的是空档。
- **一趟之后**：剩下 ≥3 s、Silero 听到 ≥3 s 说话的空档单独开窗解（≥30 s 的前后各带 1 s，3–30 s 的各带 10 s 上下文、只留中点落在空档里的段），窗里不做跳段与提前收尾。
  窗口的时钟要核：窗里的段与窗内已有的、文字相似（≥0.7）的段配成锚点，时差的下中位数超过 1 s 就整窗不收；收下的去掉时差 ≤1 s 的锚点段（同一句又转了一遍），更远的是另一句同样的话、留下。
  说话人按声纹配回这一趟的（生产给 MOSS Pro 补调的 `relink`）。补转窗撞了 token 预算，从它最后一段的结尾接着解（不带前导），剩下 ≥1 s、这一窗推进了 5 s 以上就接着。
- **整份**：一趟装不下的源按显存切段（下一节），段间重叠 60 s，照 MOSS Pro 的分段拼接（`stitch`）。然后按声纹合并标签：每个标签的声纹质心（说话不到 3 s 的不比），余弦最高的一对 ≥0.8、互相重叠不到小的那个说话时长的 10% 就并进说话多的那个，反复到没有为止。
  最后收段尾：比段里 Silero 听到的最后一点说话晚 1 s 以上的收到那里，但不短于它的文字按这份素材中位语速的三分之一说完要的时间（Silero 会漏掉游戏配乐下的台词，那些段的长度对文字是正常的）。

救援事件逐条进 debug 日志，`-aligned.json` 的 `metadata.joint_asr.events` 记各种的次数，`kv` 记每段主趟的 K/V 格式与位置数。

### 显存与速度

- **解码器**（`decoder.py`）：transformers 只做 prefill（音频编码器每次 16 个 30 秒块，再整段提示一次前向），每层的 K/V 直接写进解码缓冲、不留 transformers 自己的缓存；之后每步是手写的 Qwen3 前向、按 2048 位置一档捕获的 CUDA graph 重放。
  `model.generate` 在 1.6–3 万 token 的提示上每步 51–63 ms、GPU 占用 9%（Python 下 28 层小算子的启动开销）；这里约 10 ms，与 `generate` 前几百个 token 逐个相同、之后只在时间戳的百分位上分叉（执行形态）。
- **融合 kernel**（`kernels.py`，Triton）：flash-decoding 式注意力（沿 K/V 切块并行、在线 softmax、不展开 GQA，切块数按 SM 数推），残差 + RMSNorm、q/k 的 RMSNorm + RoPE + 写 K/V 各融成一个，按 transformers 的位置舍入到 bf16。
  一步的 kernel 约 1 800 → 400 个，24 k 位置上 11.9 → 6.1 ms，11 份解码墙钟 −41%。块大小 64 放得进计算能力 8.0 以上各卡的共享内存。没装 Triton 或编译失败时回到同一前向的纯 PyTorch 写法（stderr `Warning:`，约慢一倍）。
- **K/V 格式**：bf16 装得下就 bf16，装不下才 fp8（e4m3，每位置每头一个缩放，位置数约翻倍、解码再快约 25%）。fp8 配一次过的 prefill 在 11 份上没有翻语种的；prefill 切块（后面的块读量化过的前文）时 fp8 也翻过，所以 prefill 一次过。
  Triton 转不了 fp8 的卡留 bf16（stderr `Warning:`）。
- **一趟多长**：按预算现算能放多少位置（提示每秒音频 13.9 token、输出每秒 12 token，prefill 峰值按每提示 token 24 KB 加 0.35 GiB、再留 0.5 GiB 余量），在能用的最省格式里装得下的整分钟数，最长 90 分钟（上游的上限）。
  `standard` 档（8 GB 卡、6.5 GiB）一趟 33 分钟，`high` 档（10 GiB）68 分钟；一小时的源在 6.5 GiB 上切两段、fp8，进程约 5.9 GiB，墙钟约 4 分钟（顺带测时）。

### 开发开关与验证

- `MOSS_FAST_KV=bf16|fp8` 强制 K/V 格式，`MOSS_FAST_KERNELS=0` 强制走纯 PyTorch 的解码步：回退路径要能在这张卡上测。只给开发用，不进 manual。
- 实验版（各条规则的开关、热词、int8 K/V、prefill 切块、对照臂与读数脚本）在维护者的归档里，`dev` 上不留第二份；复现第一到三阶段的读数在那里跑。
- 验收的尺子是等价重放：生产 `--asr moss-local --stage raw-srt` 在同一张卡、同一份音频上与实验那一臂逐行比；动 `moss_local/` 的解码或救援之后要重跑。逐 token 的分叉（换卡、换 kernel、换 K/V 格式）是执行形态，只刻画。

## ⚠ 改的时候容易踩的

- **产品层的行序不等于时间序**：说话人裁判拆出的后一半（`<id>b`）紧跟在原行后面，开始可能晚于后面别人的行。凡是按时间判「同时」「切在哪」的地方
  都要按时间扫（`subtitles/line_groups.py` 的 `covered`、`parted`，`llm/chunking.turn_seams` 的 `换回`），不能拿列表邻居当时间邻居。
- **35t 的词保持输出顺序**：坏时间修复后、跨窗拼接时都不做全局排序（按词中点归交接点的一侧，再按输出顺序接上）；排序会把附和插进别人的句子。
- **MOSS Pro 的缓存名就是调用的身份**：`s-<起>-<止>`，语种重试加 `-retry`；同一次转写里空档补问一个已经问过的区间时加 `-again`，否则读回同一份无效回答。
  续调没有进展（新段的结束不晚于续调的起点）就停，不然会一直原地续。
- **验收的尺子是等价重放**：实验缓存的原始回答离线喂进生产，`-raw.srt` 与实验各臂逐行相同；之后有意改过的两处除外：MOSS Pro 续调、补调回来的说话人（声纹重连），
  中文里夹的拉丁词与数字不再拆成单个字母（2026-11-03 重跑：MAI2、35t 的 `-raw.srt` 全同，MOSS Pro 只差这些行的空格），MAI2 的行两头各扩 0.1 s（之后 MAI2 的行时间与实验不同，字不变）。动 `lines.py`、`moss_timing.py` 的常量或拼接要重跑它。
- **修补不碰原来的调用**：Live 宽窗、Live 只听这一段、MAI2 重问、35t 重问的回答各在自己的缓存目录（`gemini-35t-live-ctx/`、`gemini-35t-live/`、
  `mai2-repair/`、`gemini-35t-repair/`），名字是 `ctx-`（送去的音频起止：同样的音频就是同一次调用）/ `gap-` / `run-` / `r-` 加起止，不碰原来的 `identity.json` 与窗名；`--asr-repair off` 的 `-aligned.json` 与没有这个选项时逐字节相同（metadata 只在
  不是 `off` 时记 `repair`）。Live 插入的字接在空档前最后结束的那个词之后（声纹配到同一个人时并进它的话轮），35t 的词照旧不做全局排序；MAI2 插入后按开始时间排。Live 整个进程同时不超过 5 条会话，key 只在请求头里。
- **35t 的句末模型按固定步长分块**：修补补进来的字会推移后面的块边界，几百秒外的同一句可能换个切点。逐行比 `--asr-repair on` 与 `off` 的产物时，别把这些算成修补的改动。
- **本地 MOSS 的救援只有一部分在 GPU 上跑过**：等价重放与验收覆盖了补转、短漏段、撞预算、提前收尾、收段尾、合并与语种的两个杠杆；复读之后的放弃（`loop-skip`、`empty-run`）、时间回跳、补转窗撞预算后的续接、重解后立即结束这几条只靠与实验逐行对照。改这几条之前，先用假 tokenizer 与假 `Decoder` 按脚本出 token 驱动 `rescue.Pass`，把现有行为钉住。
- **本地 MOSS 拿着 `GPU_LOCK` 跑 Silero**：任何新的 GPU 用户先拿 `GPU_LOCK` 再拿 Silero 的锁，反过来会死锁；新的进程级设置（显存上限、库的全局开关）都要在 `moss_local.transcribe` 的 `finally` 里复原。
- 改云端任务在 stable 之前的任何一步，记着本地任务必须逐字节不变：本地的段没有 `line_speaker`，没有键的段在所有按键分组的地方都是一组（只有坍缩行的叠拉道各成一组，[`asr-stabilize.md`](asr-stabilize.md)「坍缩行」）；
  `test/test_overlap_local_golden.py` 钉着一个带缺陷重叠的本地样例。
