# 一体转写：各家的行为、设计取舍与理由

`--asr mai2|scribe|gemini-35t|moss-pro|moss-local|moss-diarization-aligner`（`speech/joint/`）的开发者文档。一体转写是一个模型交回整份带时间与说话人的转写，
替掉本地的人声分离、VAD、Whisper 与声学说话人分离那一串；后端是云端四家与本机 GPU 上的开源 MOSS（[本地 MOSS](#本地-moss)），以及别家的行配本地 MOSS 的说话人（[给别家的行配说话人](#给别家的行配说话人--asr-moss-diarization-aligner)）。
这里写各家模型实际怎么表现、生产为它们补了什么、为什么这样接。改 `speech/joint/`、一体转写任务在 `stages.py` 里的分支或重叠规则之前先读；用户向的行为在
[`manual/asr-backend-choice.md`](manual/asr-backend-choice.md)，模块地图在 [`architecture.md`](architecture.md) 的 `speech/joint/` 一行，
重叠的行在 LLM 层的规则与理由在 [`llm_design_notes.md`](llm_design_notes.md)「`同时` / `换回` 的决策记录」。

## 为什么接、接成什么样

2026-10 的一轮实验在纠错前的 `-raw.srt` 上让读者模型逐窗盲判云端结果与生产（每窗 5 分钟、A/B 随机，附人工字幕作参照，
只比文字与分句、关掉说话人；偏好率 = 云端赢的窗 /（两边赢的窗之和），区间按素材重抽）：

- **MAI2**（不跑任何本地模型，词进生产的分句 DP）：18 份、两个读者都同意才算赢，90.6% [80.0, 97.8]；中文、日语几乎全胜，
  英文多数赢。坍缩行（≥5 加权字、快于 25 字 / 秒）每小时 8.2 → 0.4，音频裁判确认的幻觉 11 → 2。
- **MOSS Pro**：7 份、一个读者，段直接当行 71%，段内按 Silero 定时之后对段直接当行 92.6%。说话人在五人以内的整集上是各路线里最好的
  （[`diarization-findings.md`](diarization-findings.md)「换成一体的转写 + 分人模型」）。
- **Gemini 3.5 Transcribe（35t）**：12 份、一个读者，35%（输在专名听错与抢话处的碎行，免费层）；加本地分句模型对不加 83%。
- **ElevenLabs Scribe v3**（2026-11 另一轮，一个读者，词进分句 DP、加本地分句模型）：日语对 MAI2 35.7% [15.0, 53.8]（节目上分不出，输在电话录音上的听错），对生产与本地 MOSS 都 > 95%；中文 CER 各家最好。说话人在多人节目的整集上与本地 MOSS 同档（B³ 0.952 对 MAI2 0.854），专名漏写率 13.7%（MAI2 24.2%）。读数在维护者的本地报告里。

owner 2026-10-29：云端不必全面打赢生产，持平或可接受的退化也行，换来的是不用本地算力。所以接成**方向一**：一个任务可以不跑人声分离、
Whisper 与第二模型，由云端转写原始混音，本地只做轻量的事（解码、Silero、分句 DP、时间轴整理），重的本地计算做成可选项
（这一期只有 `--asr-aligner`；本地分句模型算轻量、固定开）。MOSS 两家的长段与 35t 的修补默认开对齐（有 CUDA 显卡时在卡上，否则在 CPU 上）；在卡上时 MOSS 两家再由 Whisper 重定对齐器没把握的切点（英语除外）。**方向二**（本地链路与云端深度融合）没做，想法在 [`speech-followups.md`「搁置的小项」](speech-followups.md#搁置的小项)。
之后接的本地 MOSS 走同一条路，只是解码在本机 GPU 上，见[本地 MOSS](#本地-moss)。

## 各家的已知行为

改适配器之前要知道的，都是实测出来的：

- **35t**：
  - 时间在 100 ms 网格上，相邻词首尾相接；生产 DP 把停顿 0 当连读，所以进 DP 前相接处的前一个词收 10 ms。
  - 按说话人成段输出：B 的附和排在 A 那句之后、时间更早。往回跳的时间几乎全在换人处，是对的，**不能按时间排序**（话轮靠输出顺序）。
  - 真坏的时间少而有形：end < start、单词时长 > 3 s、同一个人往回跳；常像数字错了一位（3.5 → 353.6），会带着后面一串词一起偏。
  - 会提前收尾、偶尔复读退化（一个词连写上百次，响应 `status` 不是 `completed`）；输出上限 32 768 token，按 540 s 切窗（600 s 就退化）。
  - 偶尔整窗（约 9 分钟）的回答不带说话人。混音只会让它漏、不会多写（BGM 下的英语句会整句丢）。
  - 免费 key 每天每把 25 次，额度日从太平洋时间零点起。服务端出错的请求（包括高峰期的过载）多半也计数：2026-11 两把 key 撞上限时本地账上只有 20 / 18 次（owner 2026-11-09），
    所以用户向的额度估算按两成请求白费算（[`manual/asr-backend-choice.md`](manual/asr-backend-choice.md)「额度与费用」）。
- **MOSS Pro**：
  - 只有段级时间、没有词（`verbose_json` 被拒，`diarized_json` 也只有段）；段是话轮，不同说话人的段会互相重叠、各带各的字。
  - 输出上限约 16 384 token，撞上限时**静默截断**：状态照样 `SUCCESS`，最后一段坏掉（end 为 0）。会静默漏段。
  - 会把英文素材整份转成日语译文（`SUCCESS`、一整段）；API 没有语种、prompt 或翻译参数，只能事后检测。
  - 常把一个人拆成几个标签（一集 12 个标签对 4 个人）；续调、补调各是独立调用，标签重新编号。
  - 每把 key 每天约 1.25 音频小时免费，之后扣账户余额（预付费；生产只让池里最后一把走到这一步，见「设计取舍」）；控制台计的与文件时长基本一致；额度日从北京时间零点起，当天的免费额度自动到账，不用登录控制台（2026-11-14 到 11-24 每天定时转写、三把 key 每天都用到约 1 h，没有一次 402）。
- **MAI2**：
  - 词级时间与说话人；中日文每个字恒 79 ms、词间隙偏大。原始的行首晚、行尾早：对人工逐词时间，行首晚约 0.06 s（生产早约 0.06 s），行尾早约 0.13 s（生产早约 0.06 s），最早的一成早 0.3 s 以上（生产 0.11 s）；英文的行首对 Whisper 也晚约 0.09 s。词在时间上不重叠（不标同时说话）。
  - 三条路：Vercel AI Gateway（`/v4/ai/transcription-model`，转到 Azure，JSON + base64，Azure 的选项放 `providerOptions.azure`）、OpenRouter（`microsoft/mai-transcribe-2`，转到 Azure，JSON + base64）与 Azure fast transcription（multipart、自己的资源）。OpenRouter 的回答是 `words`，另两条是 `phrases`：Vercel 的回答里只取、只缓存 `providerMetadata.azure` 那一块，它就是 Azure 的形状。
  - Vercel 的 `locales` 与 Azure 一样只是提示：冒烟时英语音频在 `["ja"]` 下照样出英语。一窗 30 分钟的请求体约 19 MB，11 秒回答；Vercel 没写请求大小的上限。生产一窗 119 分钟（见「设计取舍」窗长那一行），经 Vercel、OpenRouter 的请求体约 76 MB：Vercel 2026-11-20 跑通（198 分钟的源切成两窗，整个转写阶段约 3 分钟），OpenRouter 还没跑过。
  - 一行可能含两个人的词（25 份 12 745 行里 91 行）。
- **Scribe**：
  - 一次调用转整份：单个文件最长 15 h、小于 5 GB（ElevenLabs 文档，2026-11-21；15 h 的 16 kHz 单声道 FLAC 约 1 GB）；服务端把超过 8 分钟的文件切成最多 4 段并行转写，接缝的位置不在回答里。
  - 逐字（中日文每个字）时间与说话人，标签全份通用；词在时间上不重叠（37 份回答、16 万对相邻词里没有一对跨人重叠）。
  - 标点字自带时间，有时打在停顿的另一头：「What？」的「？」晚 11 s，「。26」的「。」在停顿之前，整个词就被拉过停顿。
  - 听不清处逐字写成「（聞き取り不能）」这样的括号占位，类型是普通的 word（37 份里 7 处）。
  - 偶有时间戳坍缩：一串字的时间全是零长、撒在几十秒里，原处留下一段空档（10.6 h 里一次：hina-73 约 12 s 的台词被挪晚约 42 s）。只重转那一段就回来了。
  - 偶把一大段话粘成一个词：一个 `type: "word"` 的 token 装下 983 s、4263 字（11.8 h 里一次，73 分钟的直播；从一个不配对的「[聞き取り不能）」起、到下一个声音事件「[笑い]」的「]」止，像是它的分词把方括号里的当成一个整体）。token 里的逐字时间照常（起点单调、零长的比例与普通的词相当），说话人只有一个标签。
  - 行首比生产晚约 0.17 s（人工逐词时间，中位），行尾不晚。
  - 电话录音（CALLHOME 日语）明显不如 MAI2：去掉 ≤5 字的短行再判仍是 3 胜 20 负，输在听错，不是少写附和。默认就是逐字转写（`no_verbatim` 关），没有「多写附和」的开关。
  - 声音相近的两人会并成一个标签（hina-70 四人给三个）；CALLHOME 有两通只给一个标签。
  - 额度是账户的积分：`GET /v1/user/subscription`（key 要有 `user_read`）给档位 `tier`、已用 `character_count`、上限 `character_limit` 与刷新时间
    `next_character_count_reset_unix`；每音频小时扣多少积分随档位变（`starter` 实测 1000，免费档按 1 万积分约 4.5 h 推算约 2222）。
    免费档的 key 也给刷新时间（按月，2026-11-11 实测），`can_extend_character_limit` 为假：不能超额，额度不够就只能被拒。
    转写接口在额度用完时怎么回没有文档（可能与 key 无效一样是 401）。
  - 只有转写权限的 key 查不了余额与模型表。
- **Silero 会漏听**：分离后偏安静的真语音、BGM 下的旁白（一处 64 s 空档生产 VAD 有 14 s 语音、Silero 0 s），所以凡是拿 Silero 定时或当闸门的地方都要限住它出错的后果。

## 设计取舍

| 决策 | 理由 |
| --- | --- |
| 云端后端不接 `asr_backend` 契约（[`asr-backends.md`](asr-backends.md)），直接把词或段送进分句 DP | 那个契约是对齐循环里逐窗解码的面；云端整份转写、自带时间与说话人，硬套要伪造 refine 信号 |
| 云端任务跳过人声分离、Whisper、第二模型、语言重解与 stabilize；stable 原样拷贝 aligned（profile -1），坍缩修复、补空档也不跑 | 这些规则是为 Whisper 的失败写的：缺能量与 confidence 时噪声那几条不触发，剩下的套话清理在没有第二模型证据时会删掉云端真听到的致谢 |
| 「是不是云端任务」看产物 metadata 记的后端（先 stable、再 aligned），不看这次的 `--asr` | [resume 延续任务自己的产物与当时的选择](../README_DEV.md#复用的依据是任务身份不是质量判断)；否则云端产物换成 `--asr local` 续跑时，quality 档的声学说话人分离去读不存在的人声轨，整个任务崩掉 |
| 每次调用的原始回答缓存在任务旁的 `<stem>-cloud/`，归进「保留」；源音频的指纹（`identity.json` 的 `audio`）对不上时，那个缓存目录的回答整个作废、删掉重问，打 `Warning:`；后端、模型、切窗参数、语种对不上只告警（`cache.py`） | 删产物重跑不再花额度；同一段音频再问一次回答会不同，删了就回不去。音频是 [compatibility key](../README_DEV.md#复用的依据是任务身份不是质量判断)：调用按窗口起止命名，换了录音还复用，旧回答就按时间贴到新音频上，这是错的结果，不是旧参数。旧回答删掉而不是按音频分子目录留着：一个任务目录只对一个源，留着的只会越积越多，不会再被读到；离线重放不删，只是一份都不用 |
| 35t、MOSS Pro 每个话轮单独跑一次分句 DP，各话轮的行按起点合并；不在全局 DP 上加强制切点 | 话轮交错时全局 DP 的词序本身没有定义，全局 DP 的接缝只是打折、一个 piece 可以吞掉它（MOSS Pro 在全局 DP 下有 19 个 piece 把两个人并进一行）；强制切点要改 DP 与它的剪枝证明，效果与「话轮边界必切」相同 |
| MAI2 不切话轮，走一次全局 DP；不按词上的说话人拆行（owner 2026-10-30） | 它的词在时间上不重叠，全局 DP 就是验收过的那一臂；按说话人拆开多出 103 行，几乎都是 1 秒以下、一两个字的碎行 |
| MAI2 的行分句之后行首提前、行尾推后各 0.1 s，只占和相邻行之间的空隙（行尾先占），不越过音频末尾（`lines.widened`，owner 2026-11-03）；首字的开始、末字的结束跟着挪，metadata 记 `edge_pad` | owner 对听觉得 MAI2 比生产紧。离线比了三种扩法：这个常数在人工逐词时间上行首、行尾与生产对齐（交付层行首 −0.044 对 −0.055，行尾 +0.241 对 +0.237），Silero 两个方向的标记（语音露在行外、行伸进静音）在 13 份上都不比生产多；按中、英、日分开看，只有日语的「行尾后露出语音」仍比生产多（2.5% 对 1.6%）。代价是行尾偏差的 p90 从 0.31 到 0.41 s（生产 0.48）。生产的尾词能量延长跑在混音上，有空间的行里约四分之一（24%）延满 1 s 上限，行尾拖 > 1 s 的行从 0.9% 到 12.7%（多半是背景音、笑声让能量下不去，没逐条核实）；按 Silero 的语音延行尾，行尾又比生产晚约 0.15 s；都没用。两行同一时刻开始、按说话人排在后面的那行只有一个 10 ms 的词时，放宽会让两条 cue 多叠约 0.1 s，与下一行零长词那条同类，13 份里没出现，不改 |
| 跨两个人的行，`line_speaker` 取词时长占多数的那个人；缺说话人的段共用 `unknown` 一个键 | `unknown` 是云端说的「某个人」，所以它的两段互相重叠时照样截断；与「没有键的行自成一个键」（模型补写、裁判补出，没人说过是谁）的区别是有意的 |
| 本地分句模型给五家一体转写后端（MAI2、35t、Scribe、MOSS 两家）的所有语言固定开，没有用户开关（owner 2026-10-30、2026-11-11、2026-11-19 日语、2026-11-20「没有理由和别的 ASR 后端不一样」）；加载或下载失败时告警一次，这个进程里的行不带它，metadata 的 `sentence_boundary_model` 记有没有用上；`FINESUB_SBD=off` 只给开发对照 | 35t 加了对不加 83%；35t 的词首尾相接、DP 在没有空隙处切代价高，会留下 40 多字一行。Scribe 加了对不加 81%，MAI2 68%（日语，区间 [49, 89]，按门槛算持平）。MOSS 按断法不同的处盲判：日语 140 胜 103 负（p 0.021），中文 54 胜 23 负（p < 0.001），英文 163 胜 149 负（持平）；代价是多切的句末一刀有时落在段内字时间放偏的停顿上，那是字时间的问题。常驻 1.1 GB（峰值 1.9 GB）、30 分钟素材跑 4 s，算轻量，所以不设开关（owner：开关已经够多）。失败不让整次运行停下：分句模型只是证据，不带它的行就是改动之前的行 |

## 本地 MOSS

`--asr moss-local`（`speech/joint/moss_local/`）：开源 MOSS-Transcribe-Diarize（0.9B，Apache-2.0）在本机 GPU 上由进程内的快速解码器解码，
加运行时救援，交回与 MOSS Pro 同形的段（段级时间、话轮、不同人的段可以重叠），之后的建行与 MOSS Pro 那一支相同（S5b / S6b、按话轮分句）。

**为什么接**（owner 2026-11-02 起）：MOSS Pro 是另一个更强的模型（上游 README 的说法；官方基准 AliMeeting CER 24.86 → 18.22），
不是同一份权重加服务端救援。开源版的失败（复读、整秒时间戳、中场后时间跳走、提前收尾、整份换语种）是一处处的，救援补得上；逐词听写的差距补不上。
到纠错之前与 Pro、本地 Whisper 比（2026-11-05；开发 11 份剪段，留出 4 份没有哪条规则在上面调过）：

- CER（`-raw.srt` 对人工字幕）：开发 11 份本地 0.109、Pro 0.108、本地 Whisper 0.133；留出 4 份 0.108 / 0.108 / 0.126。中文差得最多（0.151 / 0.158 / 0.221）。
- 读者盲判（DeepSeek 一个读者、附人工字幕，比的是还没做第三阶段工程项的版本）：本地对 Pro 偏好率 31.5% [15.4, 47.4]，「内容」一项 9 : 34，差在听错与漏话。
- 时间坍缩的行只出在本地 Whisper（11 份 40 行）；对 Pro 整段错开 > 3 s 的行 4 行。
- 每份耗时中位：本地 121 s、本地 Whisper 146 s、Pro 216 s（顺带测时；本地不含约 20 s 的模型加载，Pro 不含上传与排队）。
- 说话人（同一档节目有真值的 5 份）：B³ Pro 0.940、本地 0.917、本地 Whisper 加声学分离 0.897；非这档节目的素材上本地比 Pro 多出不少标签，没有真值读不出对错。
- 行时间：与 Pro 的差在 0.1 s 以内；中文行首比 Pro 晚约 0.08 s（拿 Whisper 的词作伪真值，中位，4 份中文里 3 份，留出的一份晚 0.07 s）。这是唯一成系统的时间偏差，量级与 MAI2 放宽前的中文相当，但没有中文的人工逐词尺子、Pro 自己也偏一点，所以不改（owner 2026-11-05）；要改先在中文上要一把人工尺子，再试 MAI2 那样的放宽。

### 开源 MOSS 的已知行为

- 上游给中文默认 prompt 与一份英文配方，模型没有语种参数；中文 prompt 下一份英文演讲前十分钟整份转成了德语（另五份英文没翻），用英文 prompt 就正常。
  翻了就从第一段起一直翻下去。8 位 K/V（int8）也把它翻成西班牙语、把一份中文转成繁体。
- 复读：一段里同一串 token 绕圈，或连写几百个「...」、同一句「おはようございます」。
- 整秒时间戳：一整份的时间戳都是 `.00`，说话人跟着合并（旧的 transformers 解码上见过，新解码器没复现）。
- 中场长休息之后时间整体后跳 180 s、写到音频结尾之外；也见过从 900 s 跳回 307 s 把一段重写一遍（加了热词时）。
- 提前收尾：还有几分钟话就结束了；token 用完也是静默的。
- 跳过片头（冠名口播、PV）从第一句正片起头。
- 偶尔写出一段离谱的长段尾（`Mum.` 21.5–222.1 s），后面接着正常；真话的段最长 23 s。
- 输出 `[音楽]` 这类声学事件段（标签不是 `S01` 的形式）。
- 结构偶尔写错：整趟把段间的 `][` 写成 `] [`；一段写到一半就出 EOS；补转窗没写满就自己停；段外只写一串时间戳（`[1374.68][1374.70]…`）。
  按格式严格读时这些都不报错，后面的话整段丢掉：13 集 hina 人声轨按 10 分钟、30 分钟切段与整趟重解，丢了三处，最长一处 28 分钟（2026-11-21）。
- 一个人常被拆成两个标签，比 Pro 多。
- 段尾会拉过掌声与停顿（`Thank you, Brett.` 拉了 14 s）。

### 接法与取舍

| 决策 | 理由 |
| --- | --- |
| 只支持 CUDA 的 NVIDIA 卡、计算能力 8.0 以上（owner 2026-11-03 / 11-05），档位的空闲显存不低于 `standard` 的 6.5 GiB；没有可用的 CUDA、AMD 卡、8.0 以下、`entry` 档、`--gpu-tier cpu`、`--device cpu` 都报错停下，提示改用 `--asr local` 或云端，不悄悄退回（`device.moss_local_unusable_reason`） | 8.0 以下 bf16 没有张量核，prefill 的 bf16 SDPA 退到 math 后端、分数矩阵装不下；ROCm 下 `torch.cuda` 也可用，但能力号与 fp8 格式不是一回事。`entry` 档（3 GiB）扣掉权重、prefill 峰值与余量放不下一分钟的音频，不拦就要等下载、加载之后才失败。不退回的理由与云端的语种检查相同：用户以为用的是 MOSS |
| 这个检查在建任务时做（单任务进任务前、批处理读完清单后、追加的行加入时），只查这次真要解码的任务：到 `aligned` 阶段、`-aligned.json` 还不在；URL 在下载前不知道产物，没给输出路径就按这次的 `--asr` 算（这样的 URL 任务只续跑 LLM 阶段时，给 `--output` 或不写 `--asr`） | 不等下载 1.7 GB、不等排进 asr bin 才报；续跑已有产物的 LLM 阶段不挡 |
| 显存按本次运行的 `--gpu-tier` 与设备算：档位的空闲显存数扣 `CONTEXT_GIB`（0.3 GiB，分配器之外的 CUDA 上下文、cuBLAS、Triton，本机解码后实测 0.27–0.29），其余给 PyTorch 的分配器，并用 `set_per_process_memory_fraction` 卡在这里 | 档位的数是整个进程能用的；Windows 上超出不报错、静默溢到共享内存，只能事前卡住 |
| 进程级的副作用都在这一步里收回：显存上限解码前设、结束复原到 1.0；`use_gqa_in_sdpa` 只在 prefill 期间换掉；`TRITON_CACHE_DIR` 只在这一步里指向它的缓存；模型每个任务加载、这一步结束卸载（owner 2026-11-05：与 Whisper 的模型池相同）；都在 `finally` 里，失败时先清掉异常栈帧对模型与 K/V 缓冲的引用再卸载 | 生产一个进程跑完整批，批处理隔离了失败接着跑下一个；带着上限往下走，后面的人声分离、Qwen 裁判、强制对齐都会被卡住 |

### 本地 MOSS 的救援

`rescue.py` 编排、`rules.py` 放纯判断。一段之内模型的上下文一直在：救援把解码退回到某个 token 边界再接着解（`Decoder` 的 K/V 已经在缓冲里，退回只是挪位置），说话人编号还是这一趟的。
只有本地 MOSS 要读 token 流：35t、MOSS Pro、MAI2 与 Scribe 回来的都是服务端解析好的结构，没有格式可读错（35t 的 178 份缓存回答里正文每个字都落在词注释里，MOSS Pro 的 31 份里 `text` 就是各段拼起来的）。以后再接一个本地逐 token 输出的模型（LLM 改成 ASR 的那一类），读法照这里的顺序：边解边按格式读、换了写法但意思没错的照读，不合格式的 EOS 屏蔽，强制补结构时照模型自己的写法，读不了的地方退回重解、同一处再失败就放弃那一块、再不行就收住这一趟交补转；代码要按它的格式另写一份，`rescue.py` 的读法是按 MOSS 的格式写的。

阈值都是在出过事的素材上定的（样本内），各条在开发 11 份上多半只出场一两次；留出 4 份上没有退步。按作用的地方：

- **在一趟里**：
  - 读 token 流：一段是 `[起点][标签]正文[终点]`，终点后的 `]`（或接着开下一段的 `][`）收段；开段的 `[` 与标签的 `[` 之前可以有上一段的 `]` 与空白，标签不能是时间戳。
    宽松只在这些空白上：格式正确的流读出的段与原来按 `][` 严格读的逐段相同。读不了的地方重解：
    - 段头读不出（`unparsed`）：上一段收段之后 24 个 token 还没有 `[起点][标签]`（一个段头 9–13 个），或标签处写的是时间戳。退回上一段的收段 token，强制从 Silero 在那之后的下一处说话开始；同一处再读不出，像复读一样放弃这一块（`unparsed-skip`）；放弃之后一段都没读出来又放弃，这一趟就在上一个完整的段结束（`unparsed-end`），剩下的交补转。后面没有说话也在上一段结束。
    - 不该结束的地方出 EOS（`eos-mid`）：只有什么都没写、或一段收段的 `]`（后面只跟空白）之后能结束；段里、段头里、开了下一段的 `][` 之后出的 EOS 被屏蔽，取次优的 token 接着写。同一段最多屏蔽 3 次，再出就在上一个完整的段结束（`eos-mid-end`），剩下的交补转。
    - 下面各条强制写起点时，退回到上一段的收段 token 之后，照模型自己开段的写法补：收段的是 `][` 就只补时间；是 `]`，就留下模型在那里写的开段符（` [`），没写就用它这一趟上一次在 `]` 之后写的那个。
      在 `] [` 写法的一趟里补一个它不这么写的 `[`，模型每次都在标签处写时间戳：hina-03 那一趟跳段之后连着读不出 101 次（2026-11-21 真机重跑）。
  - 复读（`loop`）：一段尾部 48 个 token 以周期 ≤12 重复，或一段超过 400 token（Pro 与开源所有运行里最长的段约 230 token），退回段首，先对段内已写的 token 加重复惩罚（1.3）重解，再采样（温度 0.7）重解，还不行就放弃这一块：下一段强制从 10 s 之后 Silero 的下一处说话开始，留下的空档交补转。
    连续 5 段都没有字母或数字、或同一个标签连续 5 段文字相同，也放弃（几个人连喊同一句是真话，所以要同一个标签）。
  - 整秒时间戳：连续两个 `.00` 之后，下一个时间戳的第二位小数不许是 0。
  - 跳段：新段起点在已转到的地方之后留下 ≥30 s 空档、空档里 Silero 有 ≥3 s 说话，退回去把起点强制写成成片说话开始处（起点后 30 s 内 ≥9 s 说话；只有零星人声的片头 PV 不算：强制到那里，模型把 307 s 的台词写到了 46 s）。同一处最多两次。
    还没出第一段时不强制：第一个时间戳没有前文可漂，晚起是模型略过了片头，略过的那段交补转单独解（强制的话，一份的冠名口播整段晚了约 10 s、持续几分钟）。
  - 时间回跳：新段起点比已转到的地方早 30 s 以上，退回去强制从那之后的下一处说话开始，同一处最多两次；30 s 以内可能是有人插话。「已转到的地方」不算长过 30 s 的段（离谱的段尾会把它盖住的几分钟真话跳掉）。
  - 提前收尾：结束时离音频末尾还有 ≥30 s、其中 Silero 有 ≥3 s 说话，把结束换成新段，强制从成片说话处开始，最多两次。
  - 语种（给了 `--language` 时）：每攒够一段文字（英文 30 词、其他 40 个字，一个拉丁词算一个字）测一次：英文看常用虚词占比（< 0.15 算错）、日语看假名占比（< 0.2）、中文看假名与拉丁字母、其余照 MOSS Pro 只分字母体系。
    错了就把这批文字的第一段退回重解，先禁它写的第一个词，再禁它写的全部字母；还错就放回原文、这一趟不再测（源里可能真有大段别的语言）。
    两次人为翻转（中文 prompt、int8）都在第一段触发、禁第一个词就转回英文；在全部本地产物上按代码的窗重算，正常输出英文最低 0.19、日语最低 0.42，英文这侧余量小，误报的代价是一段重解。繁简不算语种错。
  - token 预算：每秒音频 18 个 token 加 512；撞上就停，剩下的是空档。以前是 12 个：密的多人对喊每秒要写 14 个以上（10 分钟一段里最密的一段按交付的字算约 14.4 个，写了又丢掉的输出没算，是下限），87 段里 12 个截住 8 段，撞了就交补转窗从静音起解、标签靠声纹合并连回去；按 20 个重解这 8 段都没撞上（owner 2026-11-23 定 18）。
- **一趟之后**：剩下 ≥3 s、Silero 听到 ≥3 s 说话的空档单独开窗解（`rules.window`），窗里不做提前收尾，跳段只查一次（下面「跳段」）。
  - 上下文：窗口每一侧先带 10 s 已转出的话，再延到那一侧下一个段边界，不切在半句话上；横跨边界的段（有人插话）与首尾正好相接的段（同一段话被切开）也整段带上。素材头尾没有已转出的话的一侧到素材边上为止。
  - 窗口解出的全部收下，替换掉它又转了一遍的已有段（`rules.replace`，owner 2026-11-20）：至少一半时长在窗里、又碰到窗口实际解到的范围（第一段起点到最后一段终点，各放宽 0.5 s）的已有段删掉。窗口常把空档头尾几个字和旁边那句上下文写成一段：以前只留中点在空档里的段，这样的段要么整段扔掉（丢字），要么留下与原来那句重复。解码撞上 token 预算或提前收尾时，没解到的上下文留着；窗口在解到的范围里跳过的句子会随之丢掉，记下的窗里能判断的都不是跳过（见下面的读数）。窗口的右侧上下文可能盖住下一个空档：那一段先按这一窗收下，下一个空档的窗照样解，再替换它（与以前一样每个空档各解一次）。
  - 素材开头、前面没有已转出的话的窗，从 Silero 在空档里听到的第一句话前 0.5 s 起解：一份片头前 14.5 s 只有音乐，从 0 s 起解时整窗的时间早了 6–14 s（台词被挤到音乐里），从人声起解后都在 0.2 s 以内。
  - 跳段：≥30 s 的空档开的窗（撞了预算、接着解的续写窗也算，它的空档起点就是窗口起点），写进空档的第一句（起点不早于空档起点的第一句说话，声音事件段不算）比空档里第一处成片说话晚 ≥5 s（从窗已经写到的地方之后找：引子里的一句说进了空档，那一截已经写了）、其间到空档结尾为止 Silero 有 ≥3 s 说话，就退回去强制从那处说话写起（事件 `hole-skip`；一段复读已放弃的地方不回去），每窗一次（hina-73 片头的窗跳过了开场两句、只写了空档之后那句）。主解码要晚 30 s 才算跳段，是为了不把插话、短停顿当跳段；窗的音频本身就是空档，开头离说话该很近。短空档窗不查：它只在空档里有说话时才开，引子里都是主解码写过的话，这条在那里几乎必然触发，可能把引出那句提前几秒再写一遍。
  - 窗口的时钟默认不核（`rules.CLOCK_CHECK` 关，owner 2026-11-20、11-25）：以前按文字把窗里的段与已有段配成锚点，时差超过 1 s 就整窗不收。它拒掉的窗里，除了上面那次片头音乐都是误拒（同一句切法不同、起点差几秒），长窗一拒就丢几分钟的话。起点修好之后，量过的窗里没见过整窗时间错开的。检查写在代码里、关着，以后见到整窗错开再打开：窗内已有的每一段配窗里离它最近、文字相似（≥0.7）的一段，不限距离，比起点差与结尾差里小的那个（窗口把一句切得不同时总有一头对得上，时钟偏了两头都偏），下中位数超过 1 s 就整窗不收；关着时这个时差也记在每个窗的事件里（`anchor_off`）。离线比过三种查法（本分支记下的 173 个窗与 `dev` 定规则时的 5 个窗，没重解）：只比起点（起点在窗外的比结尾）在本分支的窗上误拒 4 个（2.3%），按次序认上下文误拒 `dev` 的 hina-44 那个写对的窗，比差得少的那头两批都不误拒、两处真漂移（8FI8、hina-72 的片头）都拦下，整体平移 1.5 / 3 / 6 / 30 / 213 s 拦下 92 / 95 / 97 / 98 / 98%。打开它的代价：误拒时整个空档没有字、不重试，不打开的代价是漏拦时整窗时间错开，整段替换还会把两边对的上下文换成错开的。
  - 读数（15 份素材的模拟空档，主趟当尺子，每 100 字的编辑数）：30–90 s 的中间空档 5.98 → 3.24，150–200 s 的 11.45 → 4.76；片头片尾单边的窗与 3–30 s 的窗打平（以前 ≥30 s 的窗前后只带 1 s、留下凡与空档重叠的段，3–30 s 的带 10 s 不延到段边界）。代价：≥30 s 的窗解码多花 10–28% 的时间。
  - 整段替换的读数（171 个记下的窗，精修字幕当尺子，每 100 字的编辑数）：只留中点的规则在 35 个窗上丢字或重复（都在模拟空档上：重扫 173 个窗事件，空档内有 ≥1 s 人声却被扔掉的段 16 个，与已有段重叠超过 0.3 s 的留段 24 个），替换后 33 窗变好、2 窗差 1–3 字，共少 591 字；其余 136 窗多 0.10（上下文换成窗口版本，字有好有坏），真实空档净打平；替换进来的上下文的时间与主趟版本持平。代价：每窗中位约 9 段、20 s 的上下文换成窗口版本，用窗口的说话人标签（下一条）。只删窗口解到的范围里的段，是看过读数后加的，在这批记录上与全删窗内已有段逐窗相同；只删被窗口的段盖住一半以上的已有段那种做法多留下 15 段，能判断的 13 段都是窗口已经转出的重复，另 2 段太短判不了，不用。
  - 说话人先改名分开（`c1:` 前缀），留给整份的声纹合并。一个窗口标签的声音（它在整份里所有的行，上下文也算）不到 5 s 时记成 `unknown`，但其中重说了被替换的某一段的行改用那一段的标签（`rules.twin`，owner 2026-11-20）：这一行的时间至少 80% 落在那段里、字（只算字母与数字）至少 80% 按顺序出现在那段的文字里，并且只对得上一种标签；时间不要求两头对齐，因为窗口常把一段拆成两行。被替换的那段若是前一个补转窗写的、它自己又重说了更早的一段，就取更早那段的标签（相互重叠的补转窗里会这样）。读数（开发 11 份的生产重放里有补转窗的 7 份）：整段替换之后没有说话人的行 143 行 / 164 s，加这一步之后 51 行 / 60 s，只留中点时是 25 行 / 28 s；离线量时接回的 99 行逐行看过都是同一句话。生产比离线多记了 7 行未知：它们重说的是前一个补转窗的一行，那一行没对上更早的段、前一窗的标签又被整个替换掉了，认不出是谁。剩下的是空档里的行（没有已有段可比，只留中点时一样）与窗口写法差得多、主趟里没有、或一边中文一边英文的上下文行。字的线取 90% 时少接回 8 行，那 8 行是同一句的小听写差别（「我粘脸呢」对「我粘脸吗」）；时间的线取 50% 时与 80% 接回的相同。
  - 补转窗推进了 5 s 以上却没写到空档结尾时接着补：撞了 token 预算的，从它最后一段的结尾接着解（起点不带上下文，末端照样带），剩下 ≥1 s 就接着；没撞预算、自己停下的，剩下的 ≥3 s 当一个新空档，照上面开窗。
- **丢了读点的日语段**（补转之后，`punctuate`）：段里一串字中间没有任何标点、加权字数超过一行能放的上限（36），就把这一段前后各带至少 10 s（往外放到停顿）单独开窗、用带日语示例的后段 prompt 重解（第一段也是：同样 308 次重解，收到读点的段 97 → 128，示例一次也没写进结果），窗里中点落在这一段里的文字只借读点（子句标点，一律写成「、」：中文默认 prompt 下窗偶尔写「，」；数字与英文中间的「,」不借），按字对齐加回原文；字一个不换，时间、说话人不动，新旧文字（去掉标点）相似度 < 0.9 的不收。
  开源 MOSS 一趟越往后写的读点越少（5 份 30 分钟日语剪段每 100 字，开头 5 分钟 2.9，之后 1.8–2.1；MOSS Pro 3.0–3.7、不掉；句末标点两家一样多），短窗回到正常习惯。没有读点，分行 DP 就少了最主要的分句证据，只能按行长在文节组之间切。
  在 24 份日语材料上触发 130 段、62 段收到读点，每段约 1 s；读数在[设计取舍](#设计取舍)里「丢了读点的日语段」那一行。只借读点：窗自己的句末可能落在原文的句子中间（「まあそれか。アルレッキーノ…」）。只做日语：本地 MOSS 的中文段本来一句一段、不带标点，英文没量过。
- **整份**：长过 10 分钟（或一趟装不下，下一节）的源切段，切在 Silero 的停顿上、段间重叠 60–90 s（「[设计取舍](#设计取舍)」切在停顿上那一行），照 MOSS Pro 的分段拼接（`stitch`）。然后整份按声纹合并标签，与 MOSS Pro 同一步（[设计取舍](#设计取舍)里声纹合并那一行）。
  最后收段尾：比段里 Silero 听到的最后一点说话晚 1 s 以上的收到那里，但不短于它的文字按这份素材中位语速的三分之一说完要的时间（Silero 会漏掉游戏配乐下的台词，那些段的长度对文字是正常的）。

救援事件逐条进 debug 日志，`-aligned.json` 的 `metadata.joint_asr.events` 记各种的次数，`kv` 记每段主趟的 K/V 格式与位置数。

⚠ **耳语上靠 Silero 的救援都不触发**：跳段、提前收尾、一趟之后的补转（以及 MOSS Pro 的空档补调）都要 Silero 在那一段听到 ≥3 s 说话，而 Silero 听不见耳语——两份能转出八九百词的耳语片段上它整份听到 0 s。
所以模型在耳语里提前收尾时没有救援接住：一份「故意听不清」的 inaudible ASMR（10 分钟）上，本地 MOSS 与 MOSS Pro 都在 2:20–2:30 停下，后面 7 分多钟为空，35t 与 MAI2 在同一段都转出了词。
能听清的耳语上两家都没停、与 Qwen 尺子重合 91–93%，所以这是已知行为、不修（owner 2026-11-10）；读数在 [`bench-baselines.md`](bench-baselines.md)「17.19 耳语重测：一体转写不丢，Whisper 链路改成提示」。
要修得给这些闸门换一个听得见耳语的证据（能量，或裁判在尾部听词）；能听清的耳语上也出现提前收尾时再看。

### 显存与速度

- **解码器**（`decoder.py`）：transformers 只做 prefill（音频编码器每次 16 个 30 秒块，再整段提示一次前向），每层的 K/V 直接写进解码缓冲、不留 transformers 自己的缓存；之后每步是手写的 Qwen3 前向、按 2048 位置一档捕获的 CUDA graph 重放。
  `model.generate` 在 1.6–3 万 token 的提示上每步 51–63 ms、GPU 占用 9%（Python 下 28 层小算子的启动开销）；这里约 10 ms，与 `generate` 前几百个 token 逐个相同、之后只在时间戳的百分位上分叉（执行形态）。
- **融合 kernel**（`kernels.py`，Triton）：flash-decoding 式注意力（沿 K/V 切块并行、在线 softmax、不展开 GQA，切块数按 SM 数推），残差 + RMSNorm、q/k 的 RMSNorm + RoPE + 写 K/V 各融成一个，按 transformers 的位置舍入到 bf16。
  一步的 kernel 约 1 800 → 400 个，24 k 位置上 11.9 → 6.1 ms，11 份解码墙钟 −41%。块大小 64 放得进计算能力 8.0 以上各卡的共享内存。没装 Triton 或编译失败时回到同一前向的纯 PyTorch 写法（stderr `Warning:`，约慢一倍）。
- **K/V 格式**：bf16 装得下就 bf16，装不下才 fp8（e4m3，每位置每头一个缩放，位置数约翻倍、解码再快约 25%）。fp8 配一次过的 prefill 在 11 份上没有翻语种的；prefill 切块（后面的块读量化过的前文）时 fp8 也翻过，所以 prefill 一次过。
  Triton 转不了 fp8 的卡留 bf16（stderr `Warning:`）。
- **一段多长**：至多 10 分钟（`PART_SECONDS`，理由在[设计取舍](#设计取舍)「本地 MOSS 一段至多 10 分钟」那一行）；卡放不下 10 分钟时，按预算现算能放多少位置（提示每秒音频 13.9 token、输出每秒 18 token 加 512，prefill 峰值按每提示 token 24 KB 加 0.35 GiB、再留 0.5 GiB 余量），取能用的最省格式里装得下的整分钟数。
  `standard` 档（8 GB 卡、6.5 GiB）放得下 bf16 15 分钟、fp8 28 分钟，`standard_large_vram` 与 `high` 档（10 GiB）31 / 57 分钟，所以这几档都是 10 分钟一段、bf16 装得下；10 分钟一段的 K/V 是 20 480 个位置、2.19 GiB；4 集 hina（45–63 分钟）在 `standard` 档的预算下 PyTorch 峰值保留 4.6–4.9 GiB，加上进程外约 0.3 GiB，进程约 4.9–5.2 GiB。用时每 60 分钟音频 2.2–5.1 分钟（多人抢话的密集素材取上限），同集整趟一趟解的 0.47–0.57 倍（2026-11-23，不预热；第一集含内核编译，比整趟还慢 10%）。
- **Silero 与声纹**：Silero 对整段只打一次分（`SpeechSpans`，Whisper 管线的 `SileroProbStream`，CPU 上 30 分钟约 1 s），救援的语音区间（上游 `get_speech_timestamps` 的规则跑在算好的概率上）与段内定时共用；
  声纹用同一模型的 CUDA 版（`relink.VOICEPRINTS_CUDA`），只在全部解码结束之后、整份合并标签时算一次，拿着 GPU 锁、卡本来闲着；每个补转窗口解码之前、每段与任务结束时卸载（常驻会让下一趟按 `memory_allocated()` 算出的长度随之前跑过什么而变），GPU 版用不了时打警告改用 CPU 版；云端后端的声纹仍在 CPU 上（它们与别的 GPU 工作并行）。
  以前两样都在 CPU 上逐个算、Silero 整段逐帧过两遍，占解码与救援墙钟的 27–41%；改了之后 joint 阶段墙钟少 30–45%，5 份素材的产物逐行相同（2026-11-10，正式测时）。
- **墙钟花在哪**（2026-11-10 改动之后）：joint 阶段 30 分钟剪段 79–179 s、整小时 147 s，大头是解码本身，加载约 5 s，声纹 2–11 s。
  同一份代码在 WSL2 上慢 2–6%，不为 WSL 或 Linux 专属的库优化（[`decisions.md`「本地 MOSS 不为 WSL2 与 Linux 专属的库做优化」](decisions.md#本地-moss-不为-wsl2-与-linux-专属的库做优化2026-11-10)）。

### 开发开关与验证

- `MOSS_FAST_KV=bf16|fp8` 强制 K/V 格式，`MOSS_FAST_KERNELS=0` 强制走纯 PyTorch 的解码步：回退路径要能在这张卡上测。只给开发用，不进 manual。
- 实验版（各条规则的开关、热词、int8 K/V、prefill 切块、对照臂与读数脚本）在维护者的归档里，`dev` 上不留第二份；复现第一到三阶段的读数在那里跑。
- 验收的尺子是等价重放：生产 `--asr moss-local --stage raw-srt` 在同一张卡、同一份音频上与实验那一臂逐行比；动 `moss_local/` 的解码或救援之后要重跑。逐 token 的分叉（换卡、换 kernel、换 K/V 格式）是执行形态，只刻画。

### 给别家的行配说话人（`--asr moss-diarization-aligner`）

`--asr moss-diarization-aligner --asr-rows mai2|scribe|gemini-35t`：文字、行与行时间来自 `--asr-rows` 那一家（走它自己的转写与分句；修补照那家的做法，读转写文件时不补），
说话人由本地 MOSS 强制解码给出（`moss_local/forced.py`）。它是本地 MOSS 解码的一个变体，像给字配时间的对齐器那样：输入音频与带时间的行，输出每行的说话人。

**为什么接**（owner 2026-11-24；读数在维护者的本地报告里）：MAI2 的文字各家最好，自带的说话人却差；本地 MOSS 的说话人好，文字差。
把 MAI2 的行按 MOSS 自己的格式喂进去、只让它在每行开头选标签：

- 11 个日语窗（综艺、游戏实况、视觉小说）上说话人裁判式的编辑代价（每分钟要改几处标签），MAI2 自带 11.52、把 MOSS 自由解码的标签按时间映射过来 4.50、强制解码 3.24，窗窗不比两者差。
- 没看过的 14 集（日语电话 12 通、游戏 2 集，预先登记）上，B³（每条参考行与哪些行同标签、与哪些行同一个人，取精度召回的调和平均）对映射 +0.070 [+0.028, +0.137]、14 胜 0 负；对 MAI2 自带（再加 2 集只有 MAI2 可比的游戏，共 16 集）+0.036 [+0.009, +0.067]，两人电话上持平，多人节目上 +0.11 到 +0.17。
- 强制解码赢在召回（同一个人的行归进同一个标签），离不开之后按声纹合并标签：不合并时与映射持平。
- 换成 Scribe、35t 的行（日语电话 12 通）：对 Scribe 自带持平，对 35t 自带好（+0.023），两家上都好过映射。
- 带 BGM 的游戏过场 4 份上，它对现在 10 分钟切段的自由解码没有占优（两胜两负）；前面这些读数里的自由解码都是长切段；生产的 10 分钟切段上没有再比，owner 定不重比（W11）。

## ⚠ 改的时候容易踩的

- **产品层的行序不等于时间序**：说话人裁判拆出的后一半（`<id>b`）紧跟在原行后面，开始可能晚于后面别人的行。凡是按时间判「同时」「切在哪」的地方
  都要按时间扫（`subtitles/line_groups.py` 的 `covered`、`parted`，`llm/chunking.turn_seams` 的 `换回`），不能拿列表邻居当时间邻居。
- **35t 的词保持输出顺序**：坏时间修复后、跨窗拼接时都不做全局排序（按词中点归交接点的一侧，再按输出顺序接上）；排序会把附和插进别人的句子。
- **MOSS Pro 的缓存名就是调用的身份**：`s-<起>-<止>`，语种重试加 `-retry`；同一次转写里空档补问一个已经问过的区间时加 `-again`，否则读回同一份无效回答。
  续调没有进展（新段的结束不晚于续调的起点）就停，不然会一直原地续。
- **验收的尺子是等价重放**：实验缓存的原始回答离线喂进生产，`-raw.srt` 与实验各臂逐行相同；之后有意改过的两处除外：MOSS Pro 续调、补调回来的说话人（先是声纹一对一配回，2026-11-09 起改成整份声纹合并），
  中文里夹的拉丁词与数字不再拆成单个字母（2026-11-03 重跑：MAI2、35t 的 `-raw.srt` 全同，MOSS Pro 只差这些行的空格），MAI2 的行两头各扩 0.1 s（之后 MAI2 的行时间与实验不同，字不变），中文的子句证据（2026-11-11 起中文的 MAI2、35t 行改变）。Scribe 的尺子是 2026-11 那轮的 E1st 臂加三处适配器修补。动 `lines.py`、`moss_timing.py` 的常量或拼接要重跑它。
- **挨着词的那一头读缓存时用原来的边界本身**（`cuts.widened`：35t Live 宽窗、MOSS Pro 空档补调）：调用名只到 0.1 s，回答里的时间从送出的那一刻算起；用名字里取整的时刻还原，补回的段会早几十毫秒、与前一段重叠而整段被滤掉。所以挪动不改 0.1 s 名的就不挪，同一个名字永远是从原边界问的；补调的缓存只在这一截 `[起点, 结尾]` 里找，名字差 0.1 s 以内的下一截主调用不能当补调读。
- **修补不碰原来的调用**：Live 宽窗、Live 只听这一段、MAI2 重问、35t 重问的回答各在自己的缓存目录（`gemini-35t-live-ctx/`、`gemini-35t-live/`、
  `mai2-repair/`、`gemini-35t-repair/`、`scribe-repair/`），名字是 `ctx-`（送去的音频起止：同样的音频就是同一次调用）/ `gap-` / `run-` / `r-` 加起止，不碰原来的 `identity.json` 与窗名；`--asr-repair off` 的 `-aligned.json` 与没有这个选项时逐字节相同（metadata 只在
  不是 `off` 时记 `repair`）。Live 插入的字接在空档前最后结束的那个词之后（声纹配到同一个人时并进它的话轮），35t 的词照旧不做全局排序；MAI2 插入后按开始时间排。Live 整个进程同时不超过 5 条会话，key 只在请求头里。
- **35t 的句末模型按固定步长分块**：修补补进来的字会推移后面的块边界，几百秒外的同一句可能换个切点。逐行比 `--asr-repair on` 与 `off` 的产物时，别把这些算成修补的改动。
- **本地 MOSS 的救援只有一部分在 GPU 上跑过**：等价重放与验收覆盖了补转、短漏段、撞预算、提前收尾、收段尾、合并与语种的两个杠杆；复读之后的放弃（`loop-skip`、`empty-run`）、时间回跳、补转窗撞预算后的续接、重解后立即结束这几条只靠与实验逐行对照。
  `test_speech_joint_moss_local.py` 用假 tokenizer 与假 `Decoder` 按脚本出 token 驱动 `rescue.Pass`，钉着 token 流的读法、跳段与提前收尾的强制起点、段中的 EOS、读不了的段头与补转窗没写满；改别的几条之前，照它把现有行为钉住。
- **本地 MOSS 拿着 `GPU_LOCK` 跑 Silero**：任何新的 GPU 用户先拿 `GPU_LOCK` 再拿 Silero 的锁，反过来会死锁；新的进程级设置（显存上限、库的全局开关）都要在 `moss_local._run`（或它调的 `_with_model`）里复原：`transcribe` 与 `label_rows` 都经它加载模型。
- **强制解码的块前向是 `Decoder` 一步的加宽版**（`moss_local/blocks.py`，共用 `_rms` 与 `_rot`）：改解码器的前向、kernel 或升级 transformers 时两份都要改；重资源测试（`--run-heavy-resource`）比两者的 logits，改了一份另一份会红。
- **`moss-diarization-aligner` 的第一步不拿 `GPU_LOCK`**：35t 修补里的对齐器自己会拿，这把锁不可重入，第一步拿了就自锁。
- 改云端任务在 stable 之前的任何一步，记着本地任务必须逐字节不变：本地的段没有 `line_speaker`，没有键的段在所有按键分组的地方都是一组（只有坍缩行的叠拉道各成一组，[`asr-stabilize.md`](asr-stabilize.md)「坍缩行」）；
  `test/test_overlap_local_golden.py` 钉着一个带缺陷重叠的本地样例。
