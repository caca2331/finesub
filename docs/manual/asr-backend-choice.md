# 转写后端（`--asr`）：本机 Whisper、本地 MOSS 与云端四家

`--asr` 选由谁来转写：默认是本机的 Whisper 那一串，也可以把转写交给一个「一体」的模型：它直接转写原始混音，一次交回带时间与说话人的整份转写，不跑人声分离、Whisper 转写、第二模型校验与声学说话人分离（MOSS 两家在有 GPU 时借 Whisper 重对一遍长段里没把握的切点，见[重的本地计算](#重的本地计算--asr-aligner)）。
这样的模型有云端四家，也有一个在本机显卡上跑的开源模型（[本地 MOSS](#本地-moss--asr-moss-local)）。云端几家时本机只做轻量的事：解码音频、
Silero 语音检测、在模型给的词或段上按本机 Whisper 路线的规则分句（35t 与 MOSS Pro 按[话轮](#两个人同时说话)各分各的；五家都另用一个约 1.1 GB 的分句模型在 CPU 上帮着判断句子在哪结束，第一次用时下载）、时间轴整理。出的还是 `-aligned.json` / `-stable.json` / `-raw.srt`，之后的
说话人、LLM 纠错与导出照常。
`--stage vocal` 是明确要人声轨，一体转写的任务上也照样在本机跑人声分离，只停在这一步。

```powershell
finesub input.mp4 --asr moss-local --language ja   # 本机显卡上的开源 MOSS，免费、不上传
finesub input.mp4 --asr moss-pro --language ja     # 云端 MOSS Pro（短名 moss）：超出免费额度默认扣账户余额，见「额度与费用」
```

⚠ **云端几家的音频会离开本机**：第一次上传之前打一行 `Warning:`，说明发给了哪家。本地 MOSS 不上传。

## 怎么选、怎么接

`--asr` 有六个选择：默认的本机 Whisper、本机显卡上的开源 MOSS，以及云端四家；另有一个组合，文字用云端一家、说话人由本机的开源 MOSS 定（[`moss-diarization-aligner`](#别家的文字本地-moss-的说话人--asr-moss-diarization-aligner)）。

| | `local`（默认） | `moss-local` | `moss-pro`（`moss`） | `mai2` | `scribe` | `gemini-35t`（`gemini`） |
| --- | --- | --- | --- | --- | --- | --- |
| 是什么 | 本机 Whisper 那一串 | MOSS Pro 的开源本地版 | MOSI 的 MOSS Pro，云端 | Microsoft MAI-Transcribe-2，云端 | ElevenLabs Scribe v3，云端 | Gemini 3.5 Transcribe（下称 35t），云端 |
| 字准 | 中等 | 好，略逊 MOSS Pro | 好 | 最好 | 很好，电话录音明显不如 MAI2 | 好 |
| 词级时间戳 | 有 | 无 | 无 | 有 | 有 | 有 |
| 段级时间戳 | 有 | 有 | 有 | 有 | 有 | 有 |
| 时间准确度 | 很好，偶有退化 | 不错（长段里的切点靠强制对齐，默认开） | 不错；长段里的切点默认用强制对齐（有 GPU 时更快、再加 Whisper 修一遍，更准；关掉时由 Silero 分配） | 很好 | 很好 | 不错 |

| 参考耗时（60 分钟音频） | 约 3–5 分钟 | 约 2–5 分钟（多人抢话的密集素材取上限） | 约 5–10 分钟 | 约 1 分钟 | 约 1.5–3 分钟 | 约 10–25 分钟 |
| 需要 | GPU，4 GB 显存以上（没有时退回 CPU，很慢） | RTX 30 系列或更新，8 GB 显存以上；第一次用时下载约 1.7 GB 的 MOSS 模型、约 1.8 GB 的对齐模型、约 1.1 GB 的分句模型与约 1.6 GB 的 Whisper（本机转写用的同一个，用过就不再下） | MOSS key；第一次用下载约 1.8 GB 的对齐模型与约 1.1 GB 的分句模型，有 GPU 时另下约 1.6 GB 的 Whisper | Vercel AI Gateway key、OpenRouter key 或自己的 Azure Speech 资源；第一次用时下载约 1.1 GB 的分句模型 | ElevenLabs key；第一次用时下载约 1.1 GB 的分句模型 | Gemini 免费 key；第一次用时下载约 1.1 GB 的分句模型 |

- `local` 是唯一提供逐行说话人置信标、行内换人拆行与坍缩行（一闪而过的行，见上表）修复的路线。
- `moss-local` 的性质与 MOSS Pro 相同，模型更小，听错、漏话比 MOSS Pro 多，见[本地 MOSS](#本地-moss--asr-moss-local)。
- **耳语、ASMR 这类轻声素材用 `moss-local`**（没有跑得动它的卡时用 `gemini-35t` 或 `moss-pro`）：人声分离会把耳语当噪声去掉，`local` 常常只转出一半甚至几乎什么都没有；三家直接读原始混音，能听清的耳语上不丢；「故意听不清」的那类 ASMR 上两家 MOSS 可能中途停下、后面全空（35t 不会）。
  `local` 发现分离器去掉了大段轻声人声时会打一行 `Note:` 提示换后端；只是提示，那一份字幕照常产出。同一个任务目录换 `--asr` 续跑会沿用已有的识别结果，所以重跑前删掉任务目录，或另开一个任务：源码运行与批量换一个 `--name`，安装版跑单个输入时换 `--name` 不另开任务，加 `-o <新目录>`（见[运行产物「重跑某一阶段」](outputs.md#重跑某一阶段需删除的产物)）。
- `scribe` 的说话人在多人节目上比 MAI2、35t 分得好（整集上与本地 MOSS 同档，不如 MOSS Pro），专名漏写也最少；电话这类音质差的录音明显不如 MAI2，主要是听错。
- 中文素材给了 `--language zh` 时，`mai2`、`scribe`、`gemini-35t` 在逗号、句号这些标点处更容易断行，`mai2`、`scribe` 的行长接近人工字幕，`gemini-35t` 逗号写得少、仍偏长一些；不给时不这样做，长行会长到人工字幕的两倍左右。`moss-pro`、`moss-local` 也在这些标点处更容易断行（它们的段本来多在句末收尾，加了之后的行长没单独量过）。
- 35t 不用额外配置：一把 Gemini 免费 key 就能跑完整条管线，只受每天的额度限制。它的字准按 Google 官方公布的字错率与另几家对比定，本项目没量过它的字错率。
- MOSS Pro 的价格以 MOSI 的[价目页](https://platform.moss.cn/app/pricing)为准（2026-11，按它的积分账扣）；超出免费额度的部分由池里最后一把 key 付费，见[额度与费用](#额度与费用)。
  Scribe 的价格以 ElevenLabs 的[价目页](https://elevenlabs.io/pricing/api)为准。
  MAI2 的优惠价到 2026-12-31，以 [OpenRouter 的模型页](https://openrouter.ai/microsoft/mai-transcribe-2)与微软的[价目页](https://azure.microsoft.com/pricing/details/cognitive-services/speech-services/)为准。
- 表里的评价都是本项目工程处理之后、LLM 之前的读数：不是模型或 API 直出的结果，也不是 LLM 说话人裁判与纠错之后的结果。
  工程处理指云端几家由本机在模型给的词或段上重新分句、MAI2 给的时间偏紧而本机把每一行两头各放宽 0.1 秒、Scribe 的行首偏晚而本机把它提前 0.17 秒、本地 MOSS 出错时自动重解、[补漏转与复读](#补漏转与复读--asr-repair)这些。
  评价的做法是拿纠错之前的字幕和人工字幕对照，再让另一个大模型在不知道哪份出自哪家的情况下比较好坏，只能当方向看。
- 字准量的是纠错之前的字幕。跑到 LLM 纠错阶段（`--stage` 到 `translated-srt` 或 `final-srt`）时，听错的字（专名、同音词之类）还会再修一遍，所以表里字准的差别不等于成品字幕的差别。
- 参考耗时是在 RTX 5070 Ti 上跑到 `-raw.srt`（不含 LLM）的实际耗时，按 60 分钟音频折算，不是正式测时：本机 Whisper 含人声分离
  （开 `--diarize` 再加约半分钟），本地 MOSS 不含首次下载与编译；MAI2 的约 1 分钟是经 Azure 的几百次调用的中位，慢的时候到 4–5 分钟；云端几家随服务端的负载变。
- 短名 `gemini`、`moss` 跟着提供方的当前模型走，产物里记的是全名。

### 拿到 key

key 写在 `.env`（在哪、怎么新建、怎么确认配上，见[环境变量与 API Key](env.md)）。各家去这里申请，申请到之后照下面那一行写进 `.env`：

- **MOSS Pro**：MOSI 开放平台的控制台 [platform.moss.cn](https://platform.moss.cn)，在它的「[API Keys](https://platform.moss.cn/app/api-keys)」页建 key（API 在 `api.mosi.cn` 上）。
  ⚠ **账户里有余额时，免费额度用完会默认扣费**（2.00 元人民币 / 小时），只配一把 key 时扣的就是这一把；扣哪把 key、怎么关掉见下面的[额度与费用](#额度与费用)。

  ```text
  MOSS_PRO={"main":"sk-..."}
  ```

- **35t**：在 [Google AI Studio](https://aistudio.google.com/apikey) 建的 Gemini key，与 LLM 层用同一组 key（已经配了就不用再写）、次数各算各的，见[环境变量与 API Key](env.md)「[Gemini(Google AI Studio)](env.md#geminigoogle-ai-studio)」。
  35t 也可以经 OpenRouter 接、在那边付费（对中国大陆用户付款可能更方便），本项目不接这条路：免费额度用完不如改用另两家。

  ```text
  GEMINI_FREE={"main":"AIza..."}
  ```

- **MAI2 经 Vercel AI Gateway**：每月有 5 美元免费额度，注册、绑付款方式、建 key 的步骤与两条注意事项见下面的[用 Vercel 的每月免费额度转 MAI2](#用-vercel-的每月免费额度转-mai2)。
  价格见 [MAI2 在 Vercel 的模型页](https://vercel.com/ai-gateway/models/microsoft/mai-transcribe-2)（2026-11 与另两条路同价）。

  ```text
  FINESUB_KEY_VERCEL_STT=vck_...
  ```

- **MAI2 经 OpenRouter**：在 [openrouter.ai/keys](https://openrouter.ai/keys) 建 key；当前价格在它的[模型页](https://openrouter.ai/microsoft/mai-transcribe-2)。

  ```text
  FINESUB_KEY_OPENROUTER_STT=sk-or-...
  ```

- **MAI2 经 Azure**：在 [Azure 门户](https://portal.azure.com) 建一个 Speech 资源，区域选快速转写（fast transcription）可用的（[区域表](https://learn.microsoft.com/azure/ai-services/speech-service/regions?tabs=stt)）；
  地址与 key 在资源的「Keys and Endpoint」页。微软的[价目页](https://azure.microsoft.com/pricing/details/cognitive-services/speech-services/)注明 MAI-Transcribe-2 的价格是到 2026-12-31 的限时优惠。

  ```text
  FINESUB_AZURE_SPEECH_ENDPOINT=https://<名字>.cognitiveservices.azure.com
  FINESUB_KEY_AZURE_SPEECH=...
  ```

- **Scribe**：在 ElevenLabs 的 [API Keys 页](https://elevenlabs.io/app/settings/api-keys)建 key，权限只开两项：**Speech to Text**（转写）与
  **User: Read**（本机在每次上传前查这把 key 还剩多少额度；不开也能用，只是查不了，额度用完时会被拒一次再换下一把），其余都不用开。
  免费档每月 10,000 积分，按价目表推算约够 Scribe v3 转 4.5 音频小时；超出的部分建议在账户里开按量付费（API 价目页上约 0.20 美元 / 音频小时），
  不推荐订阅套餐：各档的积分换算不同，按月付、用不完不退。

  ```text
  ELEVENLABS=sk_...
  ```

  配几把时写成 `ELEVENLABS={"main":"sk_...","paid":"sk_..."}`，最多用 3 把，按顺序用，付费的那把放最后（见[额度与费用](#额度与费用)）。

几把 key 组成池、两条 MAI2 路都配了时走哪条，见[环境变量与 API Key「云端转写」](env.md#云端转写--asr)。

### 用 Vercel 的每月免费额度转 MAI2

Vercel AI Gateway 是先充值后用的：账户里的钱叫 AI Gateway Credits，不买就不会从卡上扣，额度不够时请求直接被拒。
没买过 Credits 的账户在免费档，从第一次请求起每 30 天送 5 美元额度（2026-11 实测 MAI2 能用这笔额度）。
按 2026 年的优惠价（0.10 美元 / 音频小时，见 [MAI2 在 Vercel 的模型页](https://vercel.com/ai-gateway/models/microsoft/mai-transcribe-2)）约够转 50 音频小时；优惠结束后同样 5 美元能转的小时数会少很多。
⚠ 两件事决定你拿不拿得到它：

- **要绑付款方式**：不绑就用不了免费额度，请求被拒（HTTP 403 `customer_verification_required`）。
- **绝不要充值**：买过一次 Credits，账户就转成付费档，之后不再送免费额度（Vercel 的文档没说能转回来）。
  也别打开 **Auto-reload**：它默认关着，打开后余额一低就自动从卡上买 Credits，那一次就算充值。

另外，Vercel 的套餐（免费的 Hobby、付费的 Pro）与这里的免费档、付费档是两回事：不用订阅 Pro。

步骤：

1. 在 [vercel.com](https://vercel.com/signup) 注册账户，用免费的 Hobby 套餐就行。Vercel 的付款方式、额度与 key 都属于一个团队（team），下面几步都在注册时建好的那个团队里做。
2. 按 Vercel 的[入门说明](https://vercel.com/docs/ai-gateway/getting-started)给这个团队添加一种付款方式（信用卡等）。只添加付款方式；看到 **Buy Credits**、**Continue to Payment**、**Confirm and Pay** 这类购买按钮不要点。
3. 在控制台左栏的 **AI Gateway** 里打开 **API Keys** 页，点 **Create key**，起个名字建好（[说明](https://vercel.com/docs/ai-gateway/authentication-and-byok/api-keys)）。
   key 只在建好时显示一次，马上复制，另存一份。
4. 写进 `.env`（在哪、怎么新建见[环境变量与 API Key](env.md)）：

   ```text
   FINESUB_KEY_VERCEL_STT=vck_...
   ```

5. 转写：

   ```powershell
   finesub input.mp4 --asr mai2 --language ja
   ```

   同时配了 OpenRouter 或 Azure 时也先走 Vercel（顺序见[额度与费用](#额度与费用)的 MAI2 一条）。开工前那行 `Warning:` 按整份音频估费用（已缓存的部分其实不花）；在免费档花的是免费额度，不从卡上扣。

- 免费档的请求按模型限速，比付费档低。撞上时（HTTP 429）本机自动重试，最多三次：Vercel 给了等待秒数就照它等，没给就依次等 30、60、120 秒；它要求等超过 5 分钟时不再重试。重试都失败时和下面额度用完一样：转写本身的请求让任务停下（过一会儿重跑），补漏转的重问只打 `Warning:`、空档留着。
- 额度用完时（HTTP 402）：
  - 转写本身的请求被拒，任务报错停下。已经转好的部分存在缓存里，重跑不再花额度。
  - 转写都做完、只是后面[补漏转](#补漏转与复读--asr-repair)的重问被拒时，任务**不停**：只打一行 `Warning:`，那几处空档照原样留着，字幕照常产出。额度恢复后要补上，删掉 `-aligned.json` 及其下游再跑。
  - 可以等下一个 30 天的额度再重跑；也可以在 `.env` 里这把 key 的行首加 `#` 注释掉（下回还能放开），改走 OpenRouter 或 Azure（要另付费），已转好的部分照样读回、不重新计费。

### 设成默认、走代理

可以在 `config.toml` 里把一家设成默认：

```toml
[asr]
backend = "moss-pro"
```

请求走 `[api] proxy` 设的代理（见[模型路由配置](model-routing.md)「走代理：`[api] proxy`」）。

## 额度与费用

- **35t 的 key 用到当天额度用完才换下一把**，不轮流用：出了问题能知道是哪把 key。MOSS Pro 每次调用各自挑 key（见下面），用的是哪把记在转写的日志里。池里所有 key 当天都用完时任务报错停下，等第二天的额度再跑。
- **可以多把免费 key 组成一个免费池，但不建议超过两三把**：越多，被服务方风控的风险越高。在同一台设备上先后用两把免费 key（一把用完换下一把）没出过问题，更多把没试过。
  `GEMINI_FREE` 建议最多 2 把、`MOSS_PRO` 最多 3 把：`config.toml` 的 `[pools]` 没点名时只用 `.env` 里排在前面的这几把，点名的超过建议数时照用、打一行 `Warning:`
  （`[pools]` 的写法见[环境变量与 API Key](env.md#关掉某家服务挑用哪几把-keyproviders-与-pools)）。
- **MOSS Pro 先用免费额度、尽量不切**：本地记着每把 key 当天用了多少音频。一段音频放得进某把 key 当天剩下的免费额度时，整段放进剩得最少的那把；
  哪把都放不进时，切成几截分别放进几把 key，切得越少越好，切口尽量落在 Silero 听到的停顿上（一截与下一截重叠 60–90 秒，一截最长 1 小时）。
  剩不到 10 分钟的 key 只接整段放得下的小调用（补问）。回答撞了输出上限要续问时，剩下的部分就是下一截，同样按这些规则放 key。重跑时沿用第一次的切法，缓存里的每截照用，不按当时的余量重切。
  **池里最后一把 key 例外**：它的免费额度和别的 key 一样先装；所有免费额度合起来装不下的部分也放进它，超出它免费额度的部分从它的账户余额扣（MOSS Pro 是预付费，扣到余额为零为止）。
  不想付费就在 `config.toml` 写 `[asr] moss_pro_paid = false`，这时免费额度装满能装的部分、报额度用完停下，第二天重跑从缓存接着转。「最后一把」是实际用到的那几把里的最后一把：
  **只配了一把时就是它**，账户里有余额就会扣；`[pools] moss_pro` 点名时按点名的顺序；没点名时只用 `.env` 里的前 3 把，第 4 把起不用，最后一把是第 3 把。
  服务端拒绝（HTTP 402）时：
  - 付费的那把：余额用完了。这次转写不再用它，改用别的 key 的免费额度接着装，装不下才停下；它不记成当天用完。在 MOSI 控制台充值后重跑，当天就能接着用。
  - 前面的 key：服务端认为它当天的免费额度已经用完，多半是这把 key 在别处（别的设备、别的程序）也用过、本机没记到。本机把它记成当天用完、换下一把，到北京时间零点为止不再用它；等第二天再跑即可。
  每天的免费额度在北京时间零点自动到账，不用登录控制台领取。
- **35t**：每把免费 key 每天 25 次请求（额度按 Google Cloud 项目算，同一项目里建的几把 key 共用这 25 次，所以池里的 key 要来自不同项目），撞上某把 key 的日上限就换下一把，每天的额度从太平洋时间零点起算（北京时间夏令时 15:00、冬令时 16:00）。
  服务端出错的请求（包括高峰期的过载）多半也算进当天的次数，所以估能转多少时给每把 key 留两成余量：一把 key 一天约 20 次有效请求，
  每次约 8 分钟新音频，约 2.7 音频小时；续问、补问另占次数。
- **MAI2**：回答都已缓存时（例如删了 `-aligned.json` 重新分句）不要 key，也不打费用估计；key 与估计到第一次真要发请求时才读、才打。配了几条路时按 Vercel、OpenRouter、Azure 的顺序用第一条配好的。三条路都按 119 分钟一窗切，换路线照样读回缓存、不重新计费。
- **Scribe**：`ELEVENLABS` 的几把 key 从前往后用，一份音频整份交给一把 key，不切。开了 User: Read 的 key 每次上传前查余额，按每小时耗多少积分估还能转多久
  （免费档先按约 2222 积分 / 小时、别的档先按 1100 估，之后按实际扣的积分修正）：剩的不够这一份就换下一把；剩不到 5 分钟就记成用完，
  到它的额度刷新时间之前不再查、不再用（可以[提前放回](env.md#额度与解冻)）。**最后一把当作付费的那把**：不看余额，免费档剩得不够也照样上传
  （开了按量付费就由它付超出的部分；免费档的账户不能超额，多半被拒）。没开 User: Read 的 key 用到被拒为止。任何一把 key 被拒后这次运行都不再用它（不记成用完，下次运行照常再试），
  并打一行 `Warning:`，说是哪把、为什么（没开 User: Read 时提示去开；余额够却被拒时提示查 Speech to Text 权限）。
  每份音频上传前在 stderr 打一行：用的是哪把 key，免费档说还剩约多少小时，付费档说大约扣多少积分，查不到余额时按 0.20 美元 / 小时估费用。
  最后一把也被拒时任务报错停下，说明是哪几把、为什么没用上、最后一把何时刷新。
- 每次调用的原始回答存在任务目录旁的 `<名字>-cloud/` 里：**重跑不再上传、不再花额度**。这个目录要留着（清理中间产物时也不删），
  删了就只能再花一次额度重转，而且同一段音频再问一次会得到不同的回答。源文件换成了另一段录音（同名任务目录）时，旧回答对不上这段音频，
  会被删掉、重新请求并花额度，同时打一行 `Warning:`。

## 额度与解冻

额度用完的 key（ElevenLabs 冻结到刷新时间，35t、MOSS Pro 当天记成用完）本机先搁到一边；怎么查看、提前放回见[密钥：额度与解冻](env.md#额度与解冻)。

## 本地 MOSS（`--asr moss-local`）

开源的 MOSS-Transcribe-Diarize（MOSS Pro 的开源版，0.9B 参数，Apache-2.0 许可）在本机显卡上转写原始混音，本机另加了一套救援，补它已知的失败
（复读、时间跳走、提前收尾、整段换成别的语言、漏掉的片段）。说话人、两个人同时说的行都与 MOSS Pro 一样；长段默认用强制对齐对时间（`--asr-aligner auto`，见[重的本地计算](#重的本地计算--asr-aligner)）。

```powershell
finesub input.mp4 --asr moss-local --language ja
```

- **什么卡能用**：NVIDIA 显卡、计算能力 8.0 以上（RTX 30 系列及更新、A100 之类），8 GB 显存以上（`standard` 档）。别的卡（RTX 20 / GTX 16 系列、AMD、6 GB 及以下的卡）、没有显卡、`--gpu-tier entry` 或 `cpu`、`--device cpu` 时，开工前报错停下，
  请改用本机的 Whisper（`--asr local`）或云端；不会悄悄换成别的模型。只在 RTX 5070 Ti 上实测过。
- **要多少显存**：8 GB 显存就能跑，长过 10 分钟的源按 10 分钟左右一段转、切在说话的停顿上再拼回（能用它的档位都放得下 10 分钟一段）。要跑多久见上面对比表的「参考耗时」一行（RTX 5070 Ti）。
- **第一次用**：下载约 1.7 GB 的模型（只下一次，按所在地区走镜像或官方源，下完校验）；第一次解码还要编译几个 GPU 内核，多等一会儿，之后存在缓存里。
  批处理里下载发生在本机转写那条道上，排在后面的本机 Whisper 任务会一起等。
- **语言**：模型自己支持 50 多种语言，`--language` 什么都收。
  **请给 `--language`**：不给时打一行 `Warning:`，英文素材可能整份转成别的语言（见过一次转成德语）；给了之后转偏了会自动重解那一段、尽量拉回来，拉不回就照原样留下。只验过中文、英文、日语。
- **和 MOSS Pro 比**：在中英日剪段上，字错率与 MOSS Pro 打平、好于本机 Whisper；但让大模型不看出处比较两份字幕时，MOSS Pro 更常被选中，差在听错与漏话（MOSS Pro 是一个更强的模型）。
  说话人与 MOSS Pro 相近，在人多、不是同一档节目的素材上标签更碎（一个人拆成几个标签）。
- **不缓存**：删了 `-aligned.json` 重跑就重新解码（只花时间）；`--asr-repair` 对它不起作用。
- 安装版不用另装；源码运行要 `[asr]` 依赖（transformers、Windows 上的 Triton）。

## 别家的文字、本地 MOSS 的说话人（`--asr moss-diarization-aligner`）

文字、分行与每行的时间用一家云端（`--asr-rows`：`mai2`、`scribe` 或 `gemini-35t`；`moss-pro` 不行，它的段本来就带 MOSS 的说话人），说话人由本机显卡上的开源 MOSS 来定：
把那家的每一行按 MOSS 自己的格式交给它，只让它判断每一行是谁说的。MAI2 的字最准、说话人却较差，这样两头都取好的那一边。

```powershell
finesub input.mp4 --asr moss-diarization-aligner --asr-rows mai2 --language ja
```

- **效果**：在日语素材上，MAI2 的行配上它定的说话人，比 MAI2 自己的说话人好，多人节目上好得多，两人电话上差不多。比本地 MOSS 自己转写时的说话人好，是对以前一趟转很长的 `moss-local` 量的；对现在 10 分钟一段的 `moss-local` 没有再比，几份带背景音乐的游戏素材上它没有占优。
  Scribe 的行配上它，与 Scribe 自己的说话人差不多；35t 的行配上它，比 35t 自己的好。只在日语上量过。
- **要什么**：与 `moss-local` 一样的显卡（见[本地 MOSS](#本地-moss--asr-moss-local)），开工前就检查，不合格的话不会先调云端再报错；外加 `--asr-rows` 那一家要的 key 与费用（见上面的对比表）。行读转写文件，或缓存里已有全部回答（含修补）时，这一步不调用、不要 key（`--diarize judge-text` / `judge-audio` 的 LLM 裁判照常要它自己的 key）。
  `--asr-rows` 也可以写进 `config.toml` 的 `[asr] rows`。
- **行从哪来**，按顺序：`--asr-transcript` 给的转写文件；这个任务目录里已有的那家回答（之前用 `--asr <那家>` 或这个后端转过）；都没有才调那家的 API，照 `--asr <那家>` 计费、打估价。任务目录里已有 `--asr <那家>` 的结果时，先删掉它的 `-aligned.json`、`-stable.json` 及之后的产物才换得过来（[一个任务记着自己用的是谁](#一个任务记着自己用的是谁)），`<名字>-cloud/` 里的回答照读。调来的回答照样缓存在 `<名字>-cloud/`，之后换成 `--asr <那家>` 也读得回来。
- **重叠的字幕**：MAI2 常在别人插话的地方把一个人的一句话切成几行。`--asr-overlap-cue`（默认开）把这样被插话隔开的同一个人的几行合成一条字幕，插话单独一条、与它同时显示（[两个人同时说话](#两个人同时说话)）；前一行已经以句号、问号、感叹号收尾的不合。`--no-asr-overlap-cue` 关掉，或写 `[asr] overlap_cue = false`。
- **说话人**：哪一档 `--diarize` 都给说话人，明确写了 `--diarize off` 时打一行 `Warning:` 说明这一点；`judge-text` / `judge-audio` 照常再加 LLM 说话人裁判。
- **很少的情况**：比 10 分钟分段之间的重叠（60–90 秒）还长的一行（一般是一两分钟不停顿的独白）没法判断，说话人记作未知，stderr 打一行提示有几行。
- `--asr-repair` 照 `--asr-rows` 那家的做法补；读转写文件时不新补（补就要调 API），目录里已有的修补照读。
- 任务目录里多一份 `<名字>-moss-diar.json`：这一步的记录（交给它判说话人的原行、每段怎么选的标签、合成一条的插话），只给人看，可以删（[运行产物](outputs.md#一次运行留下什么)）。

### 自己转好的文字怎么接进来

`--asr-transcript <路径>` 收两种（批处理里每个源一份，写在 manifest 那一行的 `asr_transcript` 里）：

- **之前一个任务的 `<名字>-cloud/` 目录**：同一个源用 `--asr <那家>`（或这个后端）转过的任务目录里那个文件夹。原地只读，不复制、不改；源音频对不上、或缺了一段的回答，报错停下，不调 API。
- **一份 JSON 文件**：`--asr-rows` 那家 API 原样的回答，盖住整段音频、时间从 0 秒起。MAI2 与 35t 转长音频时本来就分成几份回答（MAI2 每份至多约 2 小时、35t 每份 9 分钟），这样的几份用上面的目录，不要拼成一份文件。
  用别家 ASR 或自己的工具转写的，按 Scribe 的形状写、配 `--asr-rows scribe` 最省事：每个词一条，起止时间（秒）与文字，说话人可以不给：

  ```json
  {"words": [
    {"text": "こんにちは", "start": 0.52, "end": 1.10, "speaker_id": "a"},
    {"text": "。", "start": 1.10, "end": 1.10},
    {"text": "はい", "start": 1.40, "end": 1.62}
  ]}
  ```

  `speaker_id` 只会留作参考（产物里的 `asr_speaker`），说话人仍由本地 MOSS 定。只有一段段的时间、没有词级时间的转写（比如 SRT）接不进来：分行要按词来切。读不出词时报错（多半是文件的格式与 `--asr-rows` 那一家对不上）；有不少词落在音频结尾之后时打一行 `Warning:`，多半是文件与音频对不上。

## 一个任务记着自己用的是谁

任务的产物（`-aligned.json`、`-stable.json` 的 metadata）记着是哪家转写的，**续跑时照产物走，不看这次的 `--asr`**：
云端转写过的任务换成 `--asr local` 续跑，照样用原来的云端结果；本机转写过的任务加上 `--asr moss` 续跑，也照样用本机的结果。两种情况都只多一行提示。
要换一家（或换成本机 / 云端），删掉 `-aligned.json` 与 `-stable.json` 以及它们下游的产物再跑（要删哪些文件见[运行产物「重跑某一阶段」](outputs.md#重跑某一阶段需删除的产物)的「语音检测 / 识别 / 分句」一行）。本地 MOSS 也一样。

## 说话人

一体转写任务的说话人标签**来自转写模型自己的识别结果**，不跑本机的声学说话人分离：

- 不管 `--diarize` 是哪一档，每行都标上转写模型给的说话人（写进 `-diar-rows.json`，不花额度、不跑本机的说话人模型；唯一的例外是下面合并 MOSS 说话人标签时用的约 26 MB 声纹模型），所以 `off` 与 `acoustics` 在一体转写任务上是一样的；
  `judge-text` / `judge-audio` 再加 LLM 说话人裁判，裁判听的是原始混音。详见[说话人分离](diarization.md)。
- 没有逐行置信标，也不做行内换人拆行；`--diarize-backend` 不起作用，写了只打一行说明。
- Scribe 一次转完整份，说话人编号全份通用，本机不再合并；它偶尔把声音相近的两个人并成一个标签，电话录音上有时整通只给一个人。
- 35t 偶尔有一整个窗（约 9 分钟）的回答不带说话人：这一段的行都算同一个说话人，彼此不同时显示（按[同一个人](#两个人同时说话)的规则截短），两个人的字也可能进同一行。
- MOSS 每次调用各自给说话人编号，一次调用里也常把一个人拆成几个标签。MOSS Pro 与本地 MOSS 转完之后，本机用声纹把整份里声音很像的标签合并（只并很像的，像得没那么确定的留给说话人裁判）：补问回来的人、长素材分段（含续问接上的那一截）之间的人、一次调用里被拆开的人都算。第一次用时下载一个约 26 MB 的声纹模型；拿不到时打一行 `Warning:`，不合并。并不上的按下面处理：
  - 补问回来的标签说话不到约 5 s：声纹认不准，不并也不当新人，记成 `unknown`（开了[说话人裁判](diarization.md)时由裁判把认得出的行挪给对的人）。
  - 本地 MOSS 补转时连同空档两边一起重转的那些话：说得少、声纹认不准的，只要还是原来那句话，就保留原来的说话人；说得多的照旧按声纹合并。
  - 说得多、但声音不像任何已有的人：保留成一个新的人，补问回来的标签带 `c1:` 这样的前缀，分段里的带 `w1:` 这样的前缀。
- 长素材分段转写时（35t 约每 9 分钟一段，MAI2 每 119 分钟一窗，本地 MOSS 与 `moss-diarization-aligner` 每 10 分钟一段，MOSS Pro 与 Scribe 在素材长过一次调用时），每一段的说话人各自编号，段与段之间不对上：同一个人在接缝之后换一条轨（标签带 `w1:` 这样的前缀）。以前按接缝重叠里一起说话的时长把两边的人对上，量过之后对错的多、省下的少，改成交给[说话人裁判](diarization.md#一体转写的任务)：裁判看得到哪些轨声音相近，认定是同一个人就整份并成一条。MOSS 两家声音很像的标签照旧先在本机并掉；MAI2、35t 与 Scribe 本机不按声纹合并（MAI2 的标签常混着几个人，并错的太多）。**只出 `raw-srt`、不开裁判的任务，长素材上同一个人会拆在几条轨上。**

## 两个人同时说话

一体转写给出的几个说话人同时说话时（MOSS Pro、本地 MOSS 与 35t 常见，例如一个人说着长句、另一个人插一句附和），各自的行**在时间上重叠**，交付时也保留：

- **分句**：35t、MOSS Pro 与本地 MOSS 按话轮分句（一个人连着说的一段），两个人的字不会进同一行；行按开始时间排。MAI2 与 Scribe 不标同时说话（字在时间上一个接一个），按时间一次分句，换人处照样断行，所以它们的行不重叠。
- **SRT**：两个人的行写成各自的一条字幕，播放器同时显示（VLC、mpv 等基于 libass 的播放器把后开始的叠在上面）；**同一个人**的行之间照旧不重叠，重叠时截短较早的那条。字幕后处理的延长也不会让一条字幕盖到它原本不重叠的别人的行上。
- **分轨导出**（`--speaker-tracks ass`）：每个说话人一个样式，同时说的两句是两条同时的事件。
- **LLM 纠错**：两个人同时说的行不并成一条字幕；被插话隔开的同一个人的两行也不并（`moss-diarization-aligner` 在转写这一步就把这样的几行合成一条，见它那一节）。

本机转写的任务不受影响：行照旧按「不重叠」交付。

## 补漏转与复读：`--asr-repair`

云端转写偶尔会漏掉一段话、把一个词连写几十次，Scribe 偶尔把一段话的时间挤坏、或把一大段话粘成一个词。默认（`on`）本机找出这几样并补上：

- **漏转**：`mai2` 把漏掉的那一段再交给 MAI2 转一次（按音频计费，约多 6%，开工前那行费用估计里写着）；35t 交给 Gemini Live 重听，不占每天的请求数。
  补的字来自另一个模型（35t 的情形），有时只补回一部分，补回的一句也会摊在整个空档上。补回的话按声纹配说话人，配不上、或补回的那个人说话不到约 5 s（声纹认不准）的记作 `unknown`，开了说话人裁判时由裁判挪给对的人；35t 补回的多半是几秒的一小段，所以基本都是 `unknown`。
- **复读**（35t）：同一个词或短语连写十次以上。快得不像人说的直接裁短；正常语速的交给 Live 再听一遍，Live 也连写了一半以上次数的就留着，所以真的口令不会被裁掉。

- **时间戳坍缩**（`scribe`）：十几秒台词的时间全被挤成零、撒到后面几十秒里，字幕上那段话出现在错的地方、原处一片空白。本机认出这种情形，把那一段（前后各多 10 秒）再交给 Scribe 转一次，换掉挤坏的字（按音频计费，一处约 1–2 分钟音频）；重转失败时那段话照原样留在错的位置，并打一条告警。很少见：试过的 10 小时里一次。
- **一段话粘成一个词**（`scribe`）：Scribe 把一大段话（见过的一次是 16 分钟）当成一个词交回来，字幕上就是一整段一行。本机认出这种情形，先按它自带的逐字时间拆开（字与时间都是对的），再把那一段（前后各多 10 秒）交给 Scribe 重转一次，好拿回那一段里谁在说话（按音频计费，粘住多长就多转多长）；重转回来的人对到整份已有的人上，对不上的当新的人。`off`、重转失败或额度不够时只用本地拆开的：分行正常，但那一段的说话人全是同一个人，不可信，打一条告警。很少见：试过的 12 小时里一次。

35t 偶尔整个窗（约 9 分钟）不给说话人：`on` 不补，这一窗的话说话人是 `unknown`。

`quota` 在这之上让 35t 花每天的请求数，把漏转、复读的那一段与不带说话人的窗再问它自己一次（每个源最多 4 次请求；一把 key 一天 25 次），
问不了的照 `on` 走（`scribe` 上 `quota` 与 `on` 相同）。`off` 什么都不补。`moss-pro` 不看这个选项：它自己的续问与补问照旧。也可以写进 `config.toml` 的 `[asr] repair`。

- 补问的回答也缓存在 `<名字>-cloud/` 里，重跑不再花。
- 补了什么记在 `-aligned.json` 的 `metadata.joint_asr` 里：`repair` 是这次的取值（`off` 时不记），`log` 逐处记着补了什么、走的哪条路。校对补回的字时按它区分哪些是原转写、哪些是补的。
- 补问失败（连不上、服务端拒绝、额度用完）只放弃那一处，打一行 `Warning:`，任务照常完成；续跑也不再补，要补就删掉 `-aligned.json` 与它下游的产物再跑。

## 重的本地计算：`--asr-aligner`

MOSS Pro 与本地 MOSS 只给到段（一段常是一个人的一整段话），段内每个字的时间由本机的 Silero 语音检测分配。超出字幕长度上限的长段
要在段内切行，切点的时间改用本机的强制对齐模型（Qwen3-ForcedAligner）对更准：段内的词边界落在 100 ms 以内的，英语朗读约从五成半到九成，
日语约从四成到八成（日语量的是在 Whisper 结果上人工修订的时间）；中文没有量过。

- `auto`（默认）：`moss-pro`、`moss-local` 的长段与 `gemini-35t` 修补时 Live 补回的文字都对，要装了 `[asr]` 依赖里的 transformers（只装 `[cloud]` 时不对、也不提示）。
  - 这次运行能用 CUDA 显卡（NVIDIA，或 ROCm 版 torch 下的 AMD）时在卡上对，每音频小时多约 20–30 秒；之后 MOSS 两家再由 Whisper 重新对一遍对齐模型没把握的切点，估计每音频小时再多约 1 分钟；在三集日语素材上（以 MAI2 的词时间为尺），误差超过半秒的切点少九成以上。英语不做这一步：对齐模型在英语上本来就更准（没给 `--language` 时由 Whisper 逐段认语言，所以英语素材也会载一次 Whisper、第一次也下载它；给 `--language en` 就不载）。
  - 没有能用的卡、只有 Intel 卡、`--device cpu` 或 `--gpu-tier cpu` 时在 CPU 上对（用四分之三的 CPU 线程，每音频小时多约 3 分钟；不是你自己选的 CPU 时打一条 `Warning:`），不做 Whisper 那一步。
  - `--language` 是对齐模型不认的语言时都不对（它认中、粤、英、日、韩、法、德、意、葡、俄、西 11 种，本地 MOSS 认 50 多种）。
- `on`：同 `auto`，另外不看语言都对，英语也做 Whisper 那一步。
- `off`：都用 Silero。
- 也可写进 `config.toml` 的 `[asr] aligner`；命令行上对别的后端写 `on` 只打一行说明，`config.toml` 里的设置在别的后端上不提示。
- 第一次用时下载约 1.8 GB 的对齐模型，Whisper 那一步另下约 1.6 GB（本机转写用的同一个 Whisper，用过就不再下；都只下一次，按所在地区走镜像或官方源，下完校验）。对齐模型下不了或加载失败时打 `Warning:`，这一份退回 Silero 定时；Whisper 那一步失败时打 `Warning:`，保留对齐模型的时间；任务都照常完成；
  要重新对齐就删掉 `-aligned.json` 与它下游的产物再跑（本地 MOSS 会重新解码）。

## 安装

Windows 上用 `uv tool install finesub` 装的安装版不用另装：它首次运行时建的运行环境已经带着云端转写要的依赖。Linux / macOS 走[仓库安装](repo-install.md)，按下面的源码安装加上 `[cloud]`。

源码安装：只用云端转写时 `pip install -e ".[cloud]"`（不含本机转写那一套，torch 只在 CPU 上跑 Silero）；已经装了 `[asr]` 的，
再加上它：`pip install -e ".[asr,cloud]"`（分句模型要的 onnx、sentencepiece 在 `[asr]` 与 `[cloud]` 里都有；模型下载失败时打一条 `Warning:`，行照出、只是不带它，句中切开的会多一些）。
⚠ Windows 上从 PyPI 装到的 torch 就是 CPU 版；Linux 上要 CPU 版，先从 `https://download.pytorch.org/whl/cpu` 装 torch 与 torchaudio，否则会拉下 CUDA 版。
MAI2、35t、Scribe 与 MOSS 两家第一次用时下载一个约 1.1 GB 的分句模型（只下一次，各家共用，走与其他模型相同的下载路线与镜像）。

## 现在的限制

- MOSS Pro 偶尔会把英文素材转成日语译文：本机检查到文字不是素材语言的文字时重转一次，仍不对就报错停下。这项检查要知道素材的语言（`--language`）。
- Scribe 把超过 8 分钟的文件在服务端切成几段同时转写，接缝处可能出错，本机定不出接缝在哪。认坍缩的门槛只在一处实例上定过。
- 一批任务里，云端任务不排在本机转写后面：它们另走一条可以同时跑两个的道（见[一次跑多个输入](batch.md)）。本地 MOSS 排在本机转写那条道上。
- [补漏转与复读](#补漏转与复读--asr-repair)的补法只让大模型拿补出来的文字和人工字幕对照评过，没人听音频核对；Live 补的字偶尔不对或只补回一部分，背景里另一个人同时说的话它多半也听不出。
  `quota` 让 35t 自己重问的效果还没评过。
