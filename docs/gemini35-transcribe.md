# Gemini 3.5 Transcribe：调用规则

`gemini-3.5-transcribe`（`3.5-transcribe-08-2026`）是一个**专用转录模型**，接口与本仓库其余
Gemini 用法都不一样，也不在 `llm/routing` 的目录里。本文只记**怎么调、代价是多少、哪些是硬墙**
——它是拿来做一次性调查与离线仲裁的工具，不是生产管线的一部分。

**完整实测报告不在主仓**：证据、四臂对照、逐项数字在分支 `explore/speaker-clustering` 的
`docs/gemini35_transcribe_findings.md`（worktree `../asr-playground-speaker-clustering`），
脚本与产物在那边的 `tmp/gemini35/`。下面每条结论都来自它，2026-08-31/09-02 实测。

## 1. 两条通道，选哪条由配额决定

| | `/v1beta/interactions` | Live API（WebSocket） |
| --- | --- | --- |
| 形态 | unary，或加 `"stream": true` 走 SSE | 真流式 |
| **配额** | **Free key RPD 25 / RPM 3**（SSE 与 unary **共用同一份**） | **不计入那个额度**（一次调查约 500 个 session 零拒绝） |
| **墙在哪** | 每天 25 次 —— 逐段裁判类用法直接出局 | **同时在线 5 条会话**；第 6 条建连即失败 |
| 时间戳 / 说话人 | 有（词级 `word_info`，`speaker` 形如 `spk:0`） | **都没有**，只有 `text` |
| 确定性 | 同音频跨运行、跨 key **逐字节相同** | **不确定**：同设置三轮，62 段里判定一致 55 |
| 每段耗时 | — | 命中 1.17 s；**空结果 ~2.9 s**（没有终止信号，要等满 grace） |

**选择规则**：要时间戳或说话人 → `interactions`，但先算够不够 25 次；要逐段跑几十上百次 →
Live，接受它没有语种字段、且结果不可复现。

⚠ **两种撞限都不是 HTTP 429**：
- SSE 撞限是 **HTTP 200 + 流内一条 `event: error`** —— 只看状态码会把配额耗尽当成空结果；
- Live 撞并发是 **WebSocket close code 1011**，reason 写的是
  `You exceeded your current quota...`（**文案是 quota，触发条件是并发**；close 帧载荷上限
  125 字节，metric 名被协议截断）。失败**全部发生在建连**，会话一旦建起来结果与串行完全一致，
  所以并发失败不污染数据，重试即可。

TPM 20k **不是**绑定约束：N=4 并发实测才 ~5 600 tokens/分钟。音频计费 **25 tokens/秒**。

**RPD 25/key 是真的、而且当天不回补**（2026-09-03 复核）：两把 free key 连着跑到第 48 次
左右撞顶，形态与上面写的一致——HTTP 200 + 流内 `event: error`，正文
`You exceeded your current quota...`。所以要跑几十次的调查**得先按 25×key 数排预算**，
并把「撞顶之后怎么办」提前想好（当天不会恢复）。

## 2. `interactions` 的请求形状

```
POST https://generativelanguage.googleapis.com/v1beta/interactions
{
  "model": "gemini-3.5-transcribe",
  "input": [{"type": "audio", "uri": "<Files API uri>", "mime_type": "audio/wav"}],
  "generation_config": {"transcription_config": {
     "language_codes": ["ja-JP"],
     "mode": {"type": "verbatim", "diarization_mode": "speaker",
              "timestamp_granularities": ["word"]}
  }}
}
```

- 模型的 `supportedGenerationMethods` 写的是 `generateContent`，**那条路不通**，实际入口是
  `/v1beta/interactions`。`inputTokenLimit` 98304、`outputTokenLimit` 32768。
- 音频**只能走 Files API**（resumable upload），没有 inline base64 的路。
- 输出是 `steps[].content[].annotations[]`，逐**词**一条，要自己按说话人 + 间隔合并成段。
- ⚠ **SSE 的词不在那里**：加了 `"stream": true` 之后，词级标注一条条来自
  `event: step.delta` 的 `delta.annotations`，正文来自 `delta.text`，而
  `interaction.completed` 事件里**没有** `steps`。拿 unary 的形状去解析流式响应会得到
  **零个词**——而「零个词」看起来恰好就是「模型什么都没听到」，也就是很多实验想要的那个结论。
  2026-09-03 就这样假阴了一整轮 10 个片段。**空结果必须先证明解析对，再当成观测。**
- **三组开关互斥，别浪费时间试**：`mode: "smart"` 与 `timestamp_granularities` /
  `diarization_mode` 互斥（smart 只回正文）；`custom_vocabulary` 与时间戳、与 diarization
  各自 400，且在 smart 下被**静默忽略**（输出逐字节相同）——只有「verbatim + 无时间戳 +
  无 diarization」那一档真正生效，而那一档做不了字幕。

### 切窗按词数，不按分钟

瓶颈在**输出侧的 32768**，不是输入也不是 TPM：verbatim + 词级时间戳是每个词一条 JSON 标注。
密集对话（约 3.2 词/秒）实测安全边界 **540 s / 1 731 词**；**600 s 失败**，且失败形态是
**退化成无限复读**而不是干净截断（换 key 重跑一模一样，确定性失败）。同一个 600 s 文件换
`smart` 档就跑得完——**能吃多长取决于语音密度**。留在 ~1 700 词以内。

## 3. Live 的三条必须

1. **必须关服务端 VAD**：`realtimeInputConfig.automaticActivityDetection.disabled=true`
   加手动 `activityStart`/`activityEnd`。不关的话 20 s 素材一条消息都不回。
2. **必须喂人声轨**（分离器输出），不是原始混音：同 62 个片段，混音出字 19、人声轨 37，
   **18 个由空变有、0 个反向**。拿混音测会得出完全相反的结论。
3. **没有 `language` 字段**，只能从返回文本的字符集反推——而字符集分不出中文与纯汉字日文。

Live 的 setup 会校验未知枚举与字段（直接关连接），**唯一的例外**是
`inputAudioTranscription.diarization: true`：**接受但不生效**，不要据此以为 Live 有说话人。

## 4. 它擅长什么、不擅长什么

**能用**：转录文本本身（`smart` 档质量高于本项目现有 whisper 链路，专名与重叠语音尤其明显）；
≤3 人的「主播 vs 其他」二分（96.4%，同素材 pyannote 3.1 是 92.9%）。

**不如现有链路，别拿去换管线**：时间戳（100 ms 网格，对金标准必切位每个分位都不如生产）；
分句（**它不输出字幕行，也没有任何旋钮能让它输出**——无原生句级粒度、配置面无分句字段、
Live 提示词通道是死的、`interactions` 的 text part 计费但不进模型）；4 人真实联动
（40.0%，Sortformer v2.1 同判据 70.0%）。

**已知的既定行为**：笑声、叹息、相槌这类**非词汇发声不转**，孤立送进去也不转 —— 那不是漏听。

## 5. 用它做仲裁时的纪律

它是**第三个模型**，不是耳朵，也不是金标。拿它去判另一个模型的输出时：

- **先划分它的强弱区**再看结论。逐段仲裁的实测分歧**全在低能量端**：>−28 dB 的段它和
  Qwen 基本一致（29 段 25 vs 28），< −45 dB 时只出 1/8 而 Qwen 出 5/8。**落在它的弱区的样本
  不能算它赢，也不能算它输——只能算无结论。**
- **它自己有噪声地板**：同设置三轮之间就有 1–3 段判定不同。任何「它和 X 差了 n 段」的结论，
  n 必须显著大于这个地板才算信号。
- **两类它明确会漏**：英文演唱整句、中等能量相槌（`ん` `はい` 这类，即非词汇发声）。
- 语种上它与 Qwen **按内容类型分裂**、方向相反：日语相槌它给假名（对，whisper 站它 6/6），
  英文演唱它幻觉成片假名（错，whisper 站 Qwen 3/3）。

### 一个好用的形状：上下文窗 + 词级时间戳

要问「**这一小段音频里到底有没有语音**」时，**不要把那一小段单独送进去**。它不转非词汇
发声，所以 0.2 s 片段返回空是零信息——分不出「没有声音」和「有声音但它不写」。

改送 **±6 s 的上下文窗**，开 verbatim + 词级时间戳，然后看它**有没有在目标时间位置上放词**。
这样一次调用回答三件事：目标位置有没有词、周围说的是什么、以及**目标位置正负若干秒内**
有没有词——最后一条是判断「证据是不是来自邻居」的唯一确定式手法，2026-09-03 就是用它
反证掉了第二模型否决的 pad 泄漏假说（`docs/plans/crispasr-followups.md`）。

⚠ 这个形状**必须走 `/interactions`**：Live 没有时间戳，问不出「在哪个位置」。所以「Live
不限额度」不能替代它——额度便宜的那条通道答不了这一问。

### ❌ 别把多个窗拼成一条调用（2026-09-03 实测否决）

省调用次数的自然想法：把 N 个窗拼成一条音频、中间用「0.5 s 静音 + 1 s beep + 0.5 s 静音」
分隔，一次调用拿回全部。**实测不能用**：

| | 逐窗各调一次 | 拼接成一条 |
| --- | ---: | ---: |
| 10 个窗里段内检出 | **5** | **0** |
| 其中整窗 0 词 | 0 | 3（逐窗时分别有 5 / 42 / 2 词） |

**不是长度也不是位置**：只拿那 5 个有内容的窗拼成 76 s 再跑，同样 5/5 全丢、同样那 3 个窗
0 词。**是拼接本身。** 丢失的方式很典型——某个窗逐窗给
`…これ思いつけるの。と`（11 词），拼接给 `…これ思い付くの。`（10 词），**恰好少了目标那个
尾字**：拼接后它倾向于交一份更“干净”的转写，把边缘的碎片抹掉，而碎片正是要问的东西。

⚠ **危险的地方在方向**：错误**全部是假阴**（0 个假阳）。而假阴看起来就是「这里没有语音」
——通常正是实验想要的那个结论。省下来的调用次数远不值这个风险。时间轴映射本身是对的
（beep 只用来隔断上下文，偏移由构造和 `ffprobe` 得到），所以别以为改改对齐就能救。

### 人声轨 vs 原始混音：失效是单向的

分支上那份 findings 的 Live 结论（必须喂人声轨）在 `/interactions` 上同样成立，但可以更精确地用：
2026-09-03 拿三段已在人声轨上确证的窗改喂混音，**2/3 复现、1/3 完全丢失**——丢的那条正是
BGM 下的英语句（人声轨上 42 词逐词准确，混音上段附近一个词都没有）。

⇒ **混音只会漏，不会把日语音频变出英文词**。所以混音上的**正例仍然可信，负例不可信**。
没有人声轨又不想重跑分离器时，可以照这个非对称性用：把「检出」当证据，把「没检出」记成
**无结论**，不要记成「这里没有语音」。

## 6. 用了它就要记的两笔

调查性用法容易在结论里留下无法回溯的数字，所以每次用它至少记下：**哪条通道、哪一档
`mode`、送进去的是人声轨还是混音、以及跑了几轮**。前两个决定输出里有没有时间戳/说话人，
第三个在 Live 上直接决定出字率，第四个决定这个数字能不能拿来和别的数字比。
