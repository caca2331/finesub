## 1. 为什么动它

三个已核实的事实，合起来说明现状不是"还没调好"，是"没在跑"：

1. **两个库今天对生产零影响。** `## 精选` 是空的（人工维护，从没填过），
   `select_good_examples` 按设计返回 `[]`。所以 `render_featured_mistakes_block`
   注入的是空串，范例库只收集不消费。
2. **存量与现行收录口径矛盾。** 27 条 M 几乎全是专有名词误听个例，而
   `knowledge_update_refined_v1.md` 现在明写这类**不收**（该进词条）。任何"把精选填上"的
   动作都会把政策上不该注入的东西注入。
3. **它们是仅剩的两个没进 SQLite 的东西**（[`knowledge.md`](../knowledge.md) 自己写着）。
   于是版本行、CAS apply、prompt 投影、`rendered/` 回写、去重、共享协议、事件与证据——
   全都得为它们再造一份，或者干脆没有（今天是后者）。

折进知识库，上面第三条整条消失；前两条由本文的上限机制与迁移步骤处理。

### 一条不改结构就解决不了的观察

从精修对照里提炼出来的差异，大头既不是"错误"也不是"出彩范例"，而是**语域**——
机器译得不算错，但读着像机翻。现行判据把它们一律归到"精修有意译自由 → 不收"，
整类信息因此丢掉。`style` 条目正好装得下：一条约定 + 正例 + 反例是同一件事的三面，
不该是两个库。行文法 v3 的 `[标记] 行体` 本来就支持这个形状。

（差异分类的实测在本地精修对照组，见 `data/index.md`；判读纪律见
[`knowledge.md`](../knowledge.md)「精修字幕怎么读」——**精修不是金标，差异 ≠ 机器错了**，
这条对本方案的每一步都成立。）

## 2. 目标形态

### 2.1 身份：entry 自己，不再有「套」

一个 style = 一个 subject（category `style`）。它的**每条约定是一行**，行就是 node：自己的
版本行、自己的 evidence、自己的 `visibility`、自己的 sync 合并粒度。身份因此不需要发明——
本地是 `local_id`，共享侧是服务端签发的 `canonical_id`，和其余两类完全一样。

**为什么不是「一条约定一个 entry，若干 entry 组成一套」**（当日先这么写，随即改判；
owner 对两者无偏好，按数据模型代价定）：**套在模型里不存在**。subject 是顶层实体，
`membership` 只允许 subject → note/term 行，**行不能挂行**，所以「一组 entry」要么新增一层
实体、要么把套 id 抄进每个 entry 的 payload；两条路都要一路打通 apply / render / `rendered/`
回写 / exchange / sync。而套想要的四样东西——选取单位、上限单位、共享单位、身份——在
「一个 style 一个 entry」里全是现成的：选取就是点这个 entry 的名字，上限就是它「约定」节的
行数，共享单位本来就是整个 entry（§2.6），身份就是它自己。

**`style` 不进 `CATEGORIES` 的匹配面**（已实现）。软理由：专名条目是「从文本里按名字/别名
匹配到」，style 是「按 `--style` 显式点名」，进匹配面只会让它被文本误命中。硬理由：
`create_entry` 的查重是全局的（`ctx.repo.resolve(key)` 不带 category），进了匹配面，一条
**名字与某个专名条目相同的 style 会被直接拒绝创建**——而 style 通常就以它服务的字幕组或主播
命名，这个碰撞是常态不是角落；`subject_ref` 带 category 未命中时还会再全局 resolve 一次，
专名提案会顺手够到 style。代价是**名字唯一性没人替它管**（两条同名 style 仍然该撞、也确实
会撞，那是 style 自己命名空间内的事），所以有了 `repo.resolve_in(name, category)`：可匹配类别共用
一个命名空间（key 全局唯一，`append_lines` 的 category 回退依赖这一点），standalone 类别
各管各的。常量在 `node/model.py`：`MATCHABLE_CATEGORIES` / `STANDALONE_CATEGORIES` /
`CATEGORIES`，`base.KNOWLEDGE_CATEGORIES` 是前者的别名而不是第二份字面量。

### 2.2 preset 的五节，规则与例子按标记配对

| 节 | 装什么 |
| --- | --- |
| `档案` | `[本名]` 这套风格的名字（就是 `--style` 写的那个串）；`[作者]` 谁的口味，自由文本只给人看；`[适用范围]` 对谁成立。⚠ 静态选取下 `[适用范围]` **不参与任何判断**，别拿它做匹配 |
| `约定` | 一句祈使式的做法，一行一条，各带一个 `[标记]` 作短名。**唯一会被当作规则读的一节** |
| `正例` | `[标记] 原文 → 译文`，标记就是它演示的那条约定 |
| `反例` | 同上，违反约定的写法 |
| `待归类` | 暂存区 |

**一个 node 装不下结构**，所以规则和它的例子是三个节里的三行，靠**标记**配对。这不是新语法：
「同一节内标记唯一」是 apply 引擎已有的校验（`_check_label_uniqueness`），于是「一条约定至多
一个正例、至多一个反例」不用写代码就成立，孤例（标记在「约定」里找不到）也是可机器判定的。
（那条上限是本方案自己的取舍——注入面有界——不是标记机制强加的；想给一条约定多举几个例子，
出口是**不带标记的例子行**：合法、只是不参与配对。一个 node 至多一个标记，`split_label` 只吃
行首一个方括号。）

`share_inherit` 全节 `local`：风格是口味，默认不外发。`verify` 全节 `none`：style 没有外部
真相，一条约定的正确性不取决于任何可检索的事实。

⚠ **两条语法限制，例子的写法由它们定死**（2026-09-02 核实并改过一条）：

- **一行 = 一个 node**，没有续行、没有转义换行（写入按 `splitlines()` 切，投影一行一个 bullet）。
  例子天然单行——一条字幕就是一行；句内真有换行按素材原样写 `\N`。
- **只收 note 的节里，竖线只是字符**。原先「≥4 段竖线是术语行、恰三段是格式错误」是全局规则，
  会让带 ` | ` 的多人行例子**写不进去**；那两条是 term 诊断，只在允许术语行的节里生效
  （`classify_body`，同日改）。

### 2.3 两个上限，按 entry 计

约束落在**写入点**，不是读取点——排序只是把多余的藏起来，上限逼着做取舍。

- **条数上限 N**：一个 style 的「约定」节能有多少行。注入面是被选中的那一条 entry，两个
  style 之间不争名额，置换压力只在同一个 entry 内产生。今天的 `MAX_FEATURED_MISTAKES = 30`
  是"人工挑 30 条案例"的量，规则型条目该小得多。**现值 N = 20**（owner 2026-09-02 放宽），
  是拍的、不是标定的。
- **单条长度上限 L**：`约定` 行的字数上限；正例/反例各自的字数上限（现值 200 字，含标记）。
  防止行慢慢长成小作文（而且行写不下就该拆成两条，这正是"一行一个 node"想要的效果）。
- **整条的兜底：`max_entry_tokens`（style = 6000）**。前两个上限只管「一行多长、一节多少
  行」，三节都逼近上限时整条约 1 万 token——足以塞满一个窗口。⚠ 它**不是拒绝写入**：修复
  超大条目本身就是一次写入，一律拒绝会把条目锁死在最差状态。规则是**单调**的——超预算时只准
  改短或删行，不准新增、也不准把某行改长；同时条目在注入面顶部挂一行提示，让下一次更新或
  repair 先压缩（`node/apply.py` 的 `_check_entry_budget`、`entries.py` 挂的 marker）。

两个上限必须**同时**写进 prompt（让模型自己取舍）和 apply 层（模型不遵守就拒绝整批、
把错误回给它重试）。这是本仓库既有的模式：合并门槛就是 `fragment_merge_rules_*` 写规则、
validator 兜底，阈值只在 `prompt_constants.py` 写一次。

⚠ **这会推翻一条现有设计。** 今天知识更新 prompt 明写"本任务不注入已有台账作对照
（跨任务查重由独立维护模块处理）"，而那个独立维护模块从来没做。要删要融合，模型必须看得见
现有的那几条——**只注入本次 `--style` 选中的那一条 entry**，不是全库。有了条数上限，这份
注入的 token 就是有界的——这正是上限的第二个好处。

### 2.4 op：行级，不加新 op

模型面的 op 见 `node/proposals.py` 的 `MODEL_OPS`。约定是行，所以维护它们用的是**行级 op**：

- **加一条** = `append_lines`（带 `[标记]`）。
- **置换** = `update` 那一行（同一个 node 的新版本），或 `remove` + `append_lines`。
- **融合两条为一条** = `update` 留下的那条 + `remove` 另一条。
- **融合两条再加一条新的** = 上一条 + 一次 `append_lines`。

需要的不是新 op，而是**在 prompt 里明确告诉干活的 agent 可以这样组合**——否则它面对上限
只会做最笨的"删一条加一条"，不会想到把两条并成一条腾出位置。

⚠ **`retire_entry` 与 `merged_into` 在这里用不上**：那是 entry 级的退休与血缘（退掉的是整个
style），行级的历史本来就在版本行里，`knowledge revert` 能整体回退，共享侧也不会出现"旧两条
与新一条并存"——它们是同一个 entry 的行，sync 按 node 合并。

⚠ **退休权限定在本次注入过的那条 entry**（owner 2026-09-02）：更新任务只能改本次 `--style`
选中且实际进了 prompt 的那些行；没见过的 entry 与没注入的行它无权动。这是 §6 那条"删除权与
证据"的第一版答案——不等 evidence 机制，靠作用域。

⚠ **跨 entry 不融合。** style 没有真相，两家的同名约定并成一条就是抹掉差异，而且没有裁决者
（share 的 `verify="external"` 对 style 无效——它的正确性不依赖外部事实）。

### 2.5 选取：任务级静态，不做动态匹配

`--style <名字>[,...]`，未给则读 config，**再未给用 `default_style`**（库里有才算数；
owner 2026-09-02 把风格改成默认开、默认只读）；显式给空（`--style ""`）是「本次不用」的决定，
不回落默认。一个名字等于那条 entry 的整份注入投影。
与既有 `--extra-style`（这次临时加的一段自由文本）注入同一位置——[`knowledge.md`](../knowledge.md)
遗留项里那个「`--extra-style` 管理与范例库注入合并」由这个形状收口。

**为什么不是按内容动态匹配或让模型自己挑**（owner 2026-09-02）：

1. **没有可靠的匹配信号。** 词条靠名字/别名在文本里出现，style 没有表面形式可匹配。
2. **省掉一个真的坑。** `signals.py` 的 `landed` 判据是"canonical name 出现在 corrected
   text"——style 没有表面形式，这条信号对它不成立。自动排序要先解决它，静态选取直接绕开。
3. **符合实际。** 一家字幕组的风格就是固定那套，用户跑自己素材时知道要哪套，不需要模型猜。
4. **让共享变安全。** 拉别人的 style 进库**不会生效**，除非你把名字写进 `--style` 或 config。
   词条不是这样的（入库即可能被文本匹配到），style 是——它连匹配面都不在（§2.1）。

**`--style` 不进 resume 失效键**（owner 2026-09-02），与知识库词条正文同一档
（见 [`llm_harness_behavior.md`](../llm_harness_behavior.md)）。理由不是"它是库内容"，而是
**影响面**：style 条目有界、形状固定、只碰风格。

⚠ **`--extra-style` 一起移出**（owner 2026-09-02 定案）。它今天在 `WINDOW_INVALIDATION_INPUTS`
里，`commit.py` 写下的理由是"用户自己的指令：半新半旧是用户在字幕里看得见的差异"——中途改了
风格再 resume，前半段一个口吻后半段另一个。**owner 判定这个后果可以接受**，不值得为它作废
已经跑完的窗。这条要记下来，是因为它推翻的是注释里明写过的失败模式，不是一个无人认领的默认。
⚠ 改的时候删元组一行不够：`_task_fingerprint` 的 payload 要同时去掉 `extra_style`，否则
`unclassified` 断言直接炸；连带那条钉住元组内容的测试与 `llm_harness_behavior.md` 的失效键
一节。别把 `--extra-info` 混进来：那是注入 research 的背景信息，另一条路。

跨生产 run 的 A/B 靠实验时自己钉住。**replay 侧不靠自觉**：它必须进 fixture schema，规则已写在
[`session_replay.md`](../session_replay.md)「复用同一窗的」那一节——凡进 system prompt 又不来自
模板的输入都要进 fixture，漏了不报错、只会让 replay 悄悄漂移。

### 2.6 共享：零新增

**push 的单位已经是整个 entry**，这是现状不是待办：`share push <name>...` 把每个名字
resolve 成 subject_id 交给 `build_push_bundle(store, subject_ids)`；没有单条 push 的入口。
entry 内部逐节点按 `visibility` 过滤（`local` 的行留在本地），遍历 ancestry-closed
（挂在 local 父节点下的 shareable 行不会被推上去）。

一个 style 就是一个 entry，于是「一整套一起走」是免费的，而**逐行 `visibility`** 顺带给出
"这几条约定不外发"。接收方按 `canonical_id` 合并，与其余两类同一条路径；同名不同 id 的两个
style 并存（它们本来就是两家的口味）。⚠ 唯一要记的是 `share push` 按名字 resolve，
到那一步得让它认 standalone 类别——已经改成走 `resolve_qualified`（2026-09-02 复审），
所以 `share push style/某字幕组` 能指到，裸名字同名时会拒绝而不是推错条目。

## 4. 验收实验：**结案不做**（owner 2026-09-02）

原计划先跑一轮「只收集不注入」，用它定 N 与 L。**判定不值得单独跑**：

- 那一轮回答的是「一份素材自然产出多少条」，而 N 的量级由注入面的 token 预算定——两个量。
  预算侧的问题已经由 `max_entry_tokens` 这道兜底直接解决，不需要先知道漏斗压力。
- 上限本来就是**可改的粗值**：写在 preset 的三行里，改一次的成本远低于跑一轮实验。真觉得
  紧了就放宽，觉得松了就收紧。
- 已经有一个数据点：agy 预演在 65 条差异行上产出 4 条约定（临时库），迁移那次在 27 条范例上
  产出 5 条。两次都远低于 20，漏斗压力眼下不是问题。

⚠ 保留其中一条纪律：**真要接一个会改变译文的开关时，门槛仍须预先写死**，不能看完数字再判
（`README_DEV.md` → 开发原则）。这次没有跑实验，也就没有"看完数字再判"的机会——上限是拍的，
并且明说是拍的。
