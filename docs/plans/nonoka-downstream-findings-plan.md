## 二、P1｜已明确校验失败的权重仍会被标成可加载

### 背景

`dev` 上 `2b95ce64..f11455c7` 三个 commit 已经把 0004 的**第一半**修掉了：两个 loader 合到
`speech/runtime/hf_weights.py` 的 `prepare()`，返回 `HfLoad(revision, local_files_only)`，
`offline_first` 只对 `OSError` 做一次联网重试，`pinned_snapshot_loadable()` 在放行前按 manifest
逐个 `stat`。这解决了「权重齐了还去问网络、然后被 `ConnectTimeout` 打死」。

reviewer 在 `f11455c7` 上提出的是**另一个方向**的洞：不是该联网时没联网，而是**该拒绝时没拒绝**。

### 已复现

`pinned_snapshot_loadable()`（`finesub_bootstrap/model_ensure.py`）只问三件事：
`_hf_repo_complete` / `pinned_snapshot_present` / `files_present`。三者都不读 marker，
而 `files_present` → `file_present` 只比**大小**，不比摘要（它的 docstring 本来就写明
「It cannot answer 'is this the right file'」）。

于是构造：同尺寸、内容错误的 `model.safetensors`，`hf_verify._discard_failed()` 删除失败
（Windows 上文件被占用是常态，它本身就是 best-effort，docstring 明说删不掉时靠 failed marker 隔离），
marker 写下 `failed`。结果：

```text
marker  : failed
loadable: True
```

（复现脚本：伪造 hub 目录 + `hf_verify.write_marker(..., failed=...)` + monkeypatch
`_loader_hub_dir`，本轮已跑通。）

与此同时 `hf_weights.prepare()` 对 `ensure_hf_model` 是 `except Exception`——
`verify_downloaded()` 抛的 `VerificationMismatch` 被吞成一条 debug。两处合起来：
**官方源重试后仍校验失败的权重，会被当成「可离线加载」交给 loader。**

`_discard_failed` 的隔离承诺就是这样被新判据绕过的。

### 修法

三步，都在 `finesub_bootstrap` 与 `hf_weights` 两层，不碰 speech：

1. `pinned_snapshot_loadable()` 增读 marker：`marker_state(...) == "failed"` 直接返回 False。
   **只否决 `failed`**——现有 docstring 里「marker 说 stale 是重新 fetch 的理由，不是去网络问
   文件列表的理由」这句对 `stale`/`absent` 仍然成立，`failed` 不同，它是**损坏的正面证据**。
   把这条区别写进 docstring，否则下一个人会照原话把整段 marker 判定再删一次。
   ⚠ **必须读它自己 stat 的那个根**，即 `_loader_hub_dir()`，不是 `_hub_dir(models_root)`。
   marker 由 `verify_and_mark` 写在**下载根**，而本函数问的是**加载根**；managed 安装且环境里
   没有 `HF_*` 时两者不是一个目录，读错根等于没读。这不是笔误级的风险：两个函数名只差一个词，
   而读错的那一版**永远返回「没有 marker」，测试照样绿**。
   跨根那一半——坏权重落在下载根、加载根另有一份——由第 2 步的 `VerificationMismatch` 负责，
   不该由本函数去猜另一个根的状态：它回答的是「**这个**根能不能离线加载」。
2. `prepare()` 不再吞 `VerificationMismatch`：单独 `except VerificationMismatch: raise`，
   置于宽 `except Exception` 之前。理由是它与其余异常不同类——其余是「我们没能取到」，
   loader 接手后会给出更好的报错；这一条是「我们取到了并且判定它是错的」，loader 接手只会
   要么读出垃圾，要么抛 CT2 的裸 `RuntimeError`（与 CUDA 失败同类型，无法分辨）。
   ⚠ 只走**联网重试仍失败**这一路：`ensure_hf_model` 内部已经先镜像后官方源，抛到这里时
   两条路都试过了。
3. 契约测试：删除失败 + 坏文件同尺寸 + marker=failed ⇒ `pinned_snapshot_loadable` 为 False，
   且 `prepare()` 抛出而不是返回 `HfLoad(..., True)`。
   ⚠ **必须有一例让两个根不同**（monkeypatch `_hub_dir` 与 `_loader_hub_dir` 指向两个目录），
   否则读错根的实现也能全绿——这正是上面那条警告要防的。

### 与 §3 的耦合（重要）

第 2 步会让 referee 的权重校验失败**变成一个异常**。若 §3 不做，`--qwen-verify auto`
（默认值）下这会把整条 run 打死——正是 §3 要修的血溅面。两者的组合才是对的：
`prepare()` 抛 → `QwenReferee._load_model` 抛 → §3 的 containment 在 `auto` 下降级为
「少一层证据」，在 `on` 下照旧抛出。**建议同批实施，§3 先落。**

### owner 待决：manifest 是否登记小文件

reviewer 另提：把 pinned revision 的必需小文件（`config.json`、`preprocessor_config.json`
一类）的**名称与大小**一并写进 manifest，运行时仍只需 `stat`，不需要访问远端；这样
`_hf_repo_complete` 留下的那个窗口（两个文件之间被中断，无 `.incomplete` blob、revision 非空，
读起来像完成）也能关上。

判断：技术上成立，代价需要 owner 拍板——

- 与 manifest 现有约定相反。`model-manifest.json` 的 `_note` 明写「HF entries pin a revision
  rather than listing every file；per-file digests 记的是 LFS 对象，因为那是镜像可能替换的部分」。
  登记小文件是**换一条约定**，不是补一个条目。
- 每次 revision 变更都要重新抄一份文件清单（人工，易漏）。
- `entry_digest()` 会变 ⇒ 所有现存 marker 一次性变 `stale` ⇒ 每台机器多跑一次 1.6GB 摘要。

替代方案（更便宜、不改约定）：把这个窗口留给 `offline_first` 的 `OSError` 重试——它本来就是
为「缓存短了」设计的，缺配置文件时 transformers 抛的正是 `OSError`。**当前 dev 已经是这个形状**，
所以这一项更像是「要不要多一层保险」而非「有没有被覆盖」。

需要 owner 回答：接受现状（缺小文件时靠一次联网重试自愈，联不上则报错、用户删 snapshot 重跑），
还是换约定登记小文件。**在拍板之前，§2 的三步不依赖这个决定，可以先做。**

## 三、P1｜referee 的任何异常都会带走整条 run

### 背景

`--qwen-verify` 默认 `auto`。referee 的产物是**证据，从不是决策**（`qwen_referee` 自己的
措辞）——stabilize 消费它，没有它就是少一层交叉校验。但 `vad_asr_stage.run_vad_asr` 里
`qwen_referee.apply_verification(...)` 只包了 `finally: referee.close()`，**没有 except**。

后果：一台连不上 hub 的机器，在 ASR 对齐**已经跑完并付过账**之后，因为第二模型加载抛
`ConnectTimeout` 而丢掉整趟结果，traceback 里写的是 httpx。用户从未要求做验证（`auto` 是默认），
却为它付了全部代价。

下游把这条列为「两个独立故障、一个症状」的后一半。

### 修法

1. 在该调用点加 `except Exception`：`qwen_verify == "on"` 时原样 `raise`（调用方明确要这份证据，
   静默返回是错的答案），否则降级为一条 warning 事件并继续。
2. **不写 `align_meta["qwen_verify"]`**。这一点要照抄下游的理由：键缺失才是后续重跑愿意再试的
   条件；写一个「失败了」的记录反而会把一次瞬时网络故障固化成永久结论。
3. warning 走 `current_reporter().warning`，带 `impact="少一层校验证据"`，事件名
   `qwen-verify-failed`。**字段面不用重新设计**：同一段代码里「transformers 5.x 缺失」那支
   （`vad_asr_stage.py:1339-1350`）就是同一形状——`on` 抛、`auto` 发
   `qwen-verify-unavailable` warning 并跳过，impact 字面就是「少一层校验证据」。
   新的 except 与它并列，照抄那三个字段即可。

注意本仓库**没有** `finalize_qwen_verification`（那是下游 0001 加的，见本文「明确不做的六条」一节），所以只有一个
调用点要包，比下游的 patch 少一处。

### 验收

- 单测：让 `apply_verification` 抛异常，`auto` 下 `run_vad_asr` 正常返回且
  `align_meta` 里无 `qwen_verify` 键，`on` 下异常向外传播。
- 同步 `docs/vad-asr.md` 中 `--qwen-verify` 三档的行为描述。

## 四、P1｜共卡放置只看档位预算，不看卡上现在还剩多少

### 背景

`lang_redecode.referee_device()` 的第 4 问是「Room」：`spare = profile.usable_gpu_gb - resident`，
`spare >= QWEN_REFEREE_GIB` 就放到 CUDA。问题在 `usable_gpu_gb` 是**档位预算**（`standard` = 6.5 GiB），
不是**测量值**。CLAUDE.md 已经把这条写成戒律的另一半：档位要的是「空闲量」而非卡的容量，
「我的卡有 8GB 所以装得下」正是那条通向 OOM 的路——但代码目前只在**选档**时守住了这一点，
**放置**时又把预算当成了实测。

下游给的现场：`standard` 档上答「4.43 GiB spare」，而驱动此刻只剩 2.4 GiB（另开了游戏或别的模型）。
`vad_asr_stage.RefereeWarm` 随后在 CT2 解码的同时于辅助线程加载 referee，两者相撞——
encoder 慢到分钟级且无事件可看，或者 worker 直接吃访问违例（`0xC0000005`，在 8GB RTX 3070 上复现两次）
**没有 Python 异常**，桌面端/CLI 什么都报不出来。同任务同机对照：抑制并发 warm 后对齐 17.7s，
不抑制则进程在 60s 前消失。

这不是可以被 caught OOM 兜住的场景：CT2 那半是 abort，不抛异常。

### 修法

给 `referee_device()` 加第 5 问「Room, on the card」，用 `speech/runtime/device.free_vram_gib()`
（**已存在**，`device.py:343`）做一次**否决**：

- 只否决 **CPU/GPU 放置**，**绝不参与选档**。`free_vram_gib` 的 docstring 明写「Deliberately not
  used to pick a tier」，理由是实时值会让同一份素材在不同日子产生不同的 artifact 边界。放置不同——
  referee 只产证据，放哪只影响速度，不影响任何输出。**这条理由要写进 docstring**，否则它读起来
  像是在违反自己的注释。
- `free is None`（拿不到 CUDA 答案）时**保持档位的结论**，与本模块其余「未知」的方向一致。
- 需要一个 `pool_resident: bool` 参数区分两个调用点：`referee_warm_device()` 在
  `FwRefineModelPool.warm` **之后**问（池已计入实测空闲值，传 `True`），
  `run_vad_asr` 里语言重解那处在建池**之前**问（传 `False`，此时还要从实测值里买下 Whisper）。
  **搞错这个不是舍入误差——池是两者中更大的那个模型。** 顺序即前提，`referee_warm_device`
  的 docstring 要标注「必须在 warm 之后调用」。
- 否决时发 warning（`referee-on-cpu`），带 impact（复核明显变慢）与 action（关掉占显存的程序后重跑）。

⚠⚠ **上面这一段的最后两条在实施后被推翻了**（2026-09-04 复审，见下「验收」）：第 5 问**只留在
预热点**，语言重解那个调用点不问，因此 `pool_resident=False` 在生产里没有调用者，`referee-on-cpu`
这个 warning 码也不再存在（预热点只发 debug）。理由在「验收」那条更正里。

**第三个放置点：有意不覆盖。** `vad_asr_stage.py:1354-1367` 的尾部 referee 不经 `referee_device()`
（`verify_device` 直接由 `device` 派生），`vram_budget_gib` 拿的也是档位预算
（`resource_profile.usable_gpu_gb`）。它与上面两处**不是同一个风险**：那里 `model_pool.close()`
已经执行，Whisper 不在卡上，所以没有可撞的东西；剩下的只是**进程外**的显存压力。

不给它加实测否决，理由是代价不对称：这个预算的唯一作用是决定走不走
`qwen_decode.FixedShapeDecoder` 的定形编译解码步（要 Whisper 池之外 3.5 GiB），而**两条解码路
不是 bit-exact**（CLAUDE.md 与 `bench-baselines.md` 二十一）。用实测显存去拨它，等于让同一份
素材在不同日子走不同的解码路——正是 `free_vram_gib` 的 docstring 拒绝参与选档的同一类理由，
只不过这次动的不是 artifact 边界而是复核证据。而它失败的形态是 **torch 的 OOM 异常**
（不是 CT2 那种 abort），§3 落地后就被降级成「少一层证据」，代价有界。

⚠ 所以这是一条**写下来的决定**，不是遗漏：若将来有人报「尾部复核 OOM」，正确的第一步是确认
§3 已经把它兜住，而不是给这里补一个会改解码路的否决。

### 验收

- 单测：给定 profile 与 resident，`free_vram_gib` 打桩为足/不足/None 三态，断言放置结论与
  `pool_resident` 两值下的算式（`needed = QWEN_REFEREE_GIB + (0 if pool_resident else resident)`）。
- ~~非 bit-exact 问题不适用：这条只改**放置**，referee 在 CPU 与 GPU 上的输出按 `docs/asr-align.md`
  是逐字节相同的（CPU float32 只是慢 2.2–2.5×）。~~ ⚠ **这条作废，它是本计划最严重的一处错误**
  （2026-09-04 复审指出）。

  `asr-align.md` 那句「输出逐字相同」比的是 **CPU-float32 对 CPU-bf16/fp16**；而生产的 dtype 是
  **CUDA 上 `bfloat16`、CPU 上 `float32`**（`qwen_referee._load_model`）。**仓库里没有任何一处
  证明后一对相等**，我把前者当成了后者。于是「换设备只改速度不改输出」这个前提不成立——
  **换设备就是换数值路径**。

  代价具体在哪：语言重解的裁判输出直接喂 `maybe_redecode` 的采纳判据、决定**要不要替换字幕**，
  而 `--lang-redecode auto` 是默认路径。拿**实测显存**在那里选设备，等于让「机器上此刻还开着
  什么」改变最终字幕——同一台机器、两次运行结果不同。这正是 CLAUDE.md 那条「声称语义不变就要
  逐位相等」要挡的东西。

  **处置**：第 5 问从语言重解那个调用点**撤掉**，只留在预热点——那里被否决只是不预热，尾部裁判
  随后由 `tail_verify_device` 另行放置，**改不了任何产出输出的设备**。⚠ 这不是把问题绕开：
  档位本身早就在决定 CPU/GPU（`entry` 落 CPU、`standard` 起共驻），所以 CPU/GPU 若真有差异，
  **今天已经在机器之间造成差异**了。那是一个**既有的未决问题**，记在 `asr-align.md` 的「待标定」；
  第 5 问不能做的是在它之上再叠一层同机不可复现。
- **若将来要把第 5 问加回输出路径，先做这份对照**（预注册）：CPU-float32 与 GPU-bf16 两臂，
  同素材同触发，量 ① `adopt/reject` 一致率 ② 强制语言一致率 ③ 最终字幕差异。不能 100% 就写下
  替代指标与门槛，不得再声称「只影响速度」。

## 五、P2｜尾部复核是全流程最长的一段静默

### 背景

`QwenReferee.transcribe_batch()` 里没有任何进度上报（`qwen_referee.py` 中
`current_reporter()` 只出现在三处 warning）。下游测得：一个 197s 的阶段里有 168s 属于这一段，
期间**零事件**；日志停在 `group ASR (...)` 再不出声。在受限显卡上这可以是数分钟，
而这段静默与「进程挂了」在观感上完全一样——§4 那个 `0xC0000005` 就是从同一片静默里出来的。

### 修法

1. `transcribe_batch` 增加可选 `on_batch(done, total)` 回调。**批是最细的真实粒度**——
   一次 `generate` 从这里不可中断，逐 clip 计数会是假的。
2. `apply_verification` 传入一个进度上报器，并且**在加载之前就发 0/total**：先慢的是加载与第一次
   generate，观察者首先需要知道「在跑什么、有多少」，其次才是数字在动。
3. 上报**挂在 `aligned` 阶段名下**，不新起阶段名——它就是该阶段的尾巴，`aligned` 到 100% 之后
   冒出第二个阶段名会被读成新阶段开始。
   ⚠ 这一条要先对照 `docs/reporting.md`——**预先说明：那份文档里 grep 不到关于这件事的明文规则**，
   所以不要指望一句话定案，得通读它的事件语义再判断：`progress` 在同一阶段 100% 之后再回到 0/N 是否违反
   现有契约（八事件的语义、quiet/normal/verbose 三档的渲染）。若违反，改为在 `detail` 里标注
   「第二模型校验」并保持单调，或由 reporting owner 文档补一条例外——**不要静默地破契约**。
4. `usable` 为空时不发（`0/0` 会是唯一一条永远不动的进度线）。

### 验收

- 单测：假 referee + 假 reporter，断言事件序列以 `completed=0` 开头、按批递增、末尾等于 `total`。
- `docs/reporting.md` 同步（若走了第 3 条的例外路线，必须写进去）。

## 六、P2｜上传连接超时是「按地址」花的，45s 会变成 169s

### 背景

`llm/media_upload.py:279`：`GEMINI_UPLOAD_TIMEOUT = httpx.Timeout(connect=45.0, ...)`。
httpx 的 connect 预算是**按解析出的每个地址**花的，而 `generativelanguage.googleapis.com`
解析出多个地址。于是一台被**过滤**（而非拒绝）的机器会挨个地址各等 45s——下游实测在打出
第一行重试日志之前静默了 169 秒。这与挂死无法区分。

`--execute` 之外的默认 dry-run 不触发这条路径，所以影响面限于真正调用 Gemini 的运行；
但一旦触发，它就是纯粹的体验缺陷。

### 修法

`connect` 45.0 → 15.0，`read`/`write`/`pool` 不动。把「按地址计费」这个理由写进现有注释——
当前注释说「A proxy that is slow to accept may still need the connect value raised」，
读起来像是鼓励调大，正好是反方向。

判断：15s 仍能过一条正常链路；一条需要 >15s 才能 connect 的链路，不值得把整个 stage 挂在上面。
这是个常量取值，不需要实验预注册，但**要在 CHANGELOG 写一条**（用户可见的行为变化）。

## 七、P2｜agent 工具参数里的非 ASCII 被写成字面 `\uXXXX`

### 背景

这是 antigravity-cli（我们的 agy 后端）1.1.24 的缺陷：它把 `tools/call` 参数里的每个非 ASCII
码点写成 JSON 字符串**内部**的字面 `\uXXXX`，于是 `json.loads` 交回六个 ASCII 字符而不是那个字。
帧里其余部分未被转义（引号与反斜杠没有加倍，`<` 仍是正确序列化器写的 `<`），
所以这不是「JSON 被序列化了两次」，而是**只对非 ASCII 字符施加了一次变换**。

下游 2026-09-04 实测：一个纠错窗口提交了 5988 个字符、其中 815 个反斜杠后面全跟着 `u`；
validator 拿这段文本判 `char_count`（模型写了 16 个字，被判成 45 个加权字符）；
交付的 SRT 每一行都是 `伝える…`。**整个 stage 全程报告成功**。

### 实测（2026-09-04，下游提供的一份 `llm-artifacts`，本地复核过）

一次 `LOCAL_AGY` / `gemini-3.7-flash` 的纠错运行，task-report 全程 `completed`，
`Fallbacks And Warnings` 一栏写着「No fallback was recorded」：

| 事实 | 数字 |
| --- | --- |
| prompt 侧 | 有真正的中日文（非纯 ASCII） |
| 模型响应 | **纯 ASCII**，5991 字符 |
| 反斜杠 | 815 个，**每一个后面都跟着 `u`** |
| 解出非 ASCII 的转义 | 815 / 815 |
| **解出 ASCII 的转义** | **0** |
| 污染扩散 | `correction-windows.jsonl`（断点缓存）815 处；两条 task-artifacts payload 883 / 567 处 |

两条判断因此不再是推测：

1. **窄判据没有误判空间**（至少在这份素材上）：「纯 ASCII ∧ 含 `\uXXXX` ∧ 解出非 ASCII」
   在 815 个转义里零个落到「本来就想写这六个字符」那一侧。
2. **污染会进断点缓存**。所以一次坏运行不是只毁掉这一趟：`correction-windows.jsonl` 记的
   是已经转义的内容，resume 会照着它继续。

### ⚠ 信号早就有了，是我们把它扔掉的

同一份 exchange 的 Validation 段有 15 条同形告警：

```text
Row 2 char_count '16' does not match the computed value 45; normalized.
Row 23 char_count '10.5' does not match the computed value 33; normalized.
```

比值一律 ≈3×——正是「一个中日文字符变成 6 个 ASCII 字符、按 0.5 权重折算」的结果
（1.0 → 3.0）。也就是说**校验器看见了系统性异常，处置却是用被污染的计算值覆盖模型写的
诚实值（`normalized`）然后放行**。这把本节从「要不要新建一层校验」变成了「已有的那层为什么
在证据面前选择了沉默」，也让方案 B 的成本降到近乎为零：检测不需要新信号，现有的
`char_count` 偏差本身就是。

### 这为什么算我们的问题

CLI 的 bug 我们修不了，但「`submit` 之下没有任何东西能分辨转义文本与文本」是我们的契约缺口——
它把一个上游故障变成了**静默交付坏字幕**。这与 memory 里已知的
「agy 答案通道约 23% 畸形」是同一类：agy 这条通道需要出口校验。

### 修法（两选一，倾向 B）

- **A（下游做法）**：在 `agent_mcp_server` 的帧入口修复参数——纯 ASCII、含 `\uXXXX`、
  且解出非 ASCII 才动手；代理对处理；孤代理不动。narrow 且可逆。
  代价：我们替第三方 CLI 的 bug 长期背一段特判，且它一旦修好我们不会知道。
- **B（倾向）**：不改数据，**加出口校验**。在 `submit` 的 validator 上加一条：
  提交文本若为纯 ASCII 且含 `\uXXXX` 转义、且解出非 ASCII，则**判为无效并要求重提**，
  错误信息直说「你的工具参数被转义了」。这样故障在**发生的地方**被发现，
  不会静默进 SRT，也不需要我们模仿它的编码。

判断依据：本仓库的既有立场是「不为过度保守的安全策略加机制」，但这里不是安全策略，
是**数据完整性**——而完整性的正确落点是校验，不是猜测性修复。若 owner 认为「重提也解不了、
用户会卡死」，再退回 A（可以两条都做：A 修复 + 一条 debug 事件说明修复发生过）。

**需要 owner 拍板 A / B / A+B。**

### 验收

- 单测：转义样本 ⇒ 被拒（B）或被还原（A）；正常样本、含字面 `A` 的样本 ⇒ 不受影响。
- 若走 B，`docs/llm_agent_tool_protocol.md` 补一条出口校验说明。

## 八、P2｜headless 的权限拒绝被误判成瞬时故障

### 背景

这一条不是下游 patch 里的条目，是**顺着 0003 查出来的我们自己的缺陷**——而且它才是那条
patch 真正昂贵的部分：0003 的读授权对不对还有争议（见下一节的「单列 0003」），但「一次权限拒绝会被报成
一句与真因毫无关系的话」在我们这边是确定的。

agy 在 headless 下被权限拦住时的形状很特别：**退出码 0**、`response` 空串、最终步无 thinking、
事件流里一条 tool `ERROR`、stderr 上一句
`no output produced — a tool required the ... permission that headless mode cannot prompt for`。

而 `local_agent.py` 的 `if not content:` 分支（约 3566 行）对此只做一件事：抛
`LocalAgentTransientError(f"{display_name} event stream did not contain a final assistant message")`。
它**既不读 stderr，也不看事件流里有没有 tool `ERROR`，也不带 capsule 指针**——同一个文件里的
`_nonzero_exit` 至少还会附一句 `inspect events/stderr.log`，这条没有。

后果是三级放大：

1. transient ⇒ router 判定「这个 target 不行，换下一个」，于是**静默走完整条链**；
2. 链条走到尽头，用户看到的是**最后一环**的话。下游实测到的是
   `Provider GEMINI_PAID is disabled or has no selected API key`——一句关于 API key 的话，
   真因是一次文件读权限；
3. 产物侧没有任何东西指向真因，得去翻 agy 自己的
   `~/.gemini/antigravity-cli/brain/<conversation>/.system_generated/logs/transcript_full.jsonl`
   才能看出那次工具调用缺了结果步。

⚠ 这与 `docs/llm_local_agent_agy.md` §6.2 是同一形状——那次是 `read_url_content` 缺 permission，
症状同样是「整个 turn 结束、不产 assistant message」，driver 报的同样是这句
`did not contain a final assistant message`。**也就是说我们已经被同一个误判坑过一次**，
当时修的是缺失的那条 grant，没有修**分类**。

### 修法

在抛通用 transient 之前，先认这个形状：

1. 读 capsule 的 stderr，匹配 `permission` + `headless`（照 `_nonzero_exit` 的既有写法，
   小写子串匹配，不要正则去啃厂商措辞）；同时在 normalized 事件里找 tool `ERROR` 步，
   把**工具名**取出来。
2. 命中则抛一个**可区分**的错误，正文直说「agy 在 headless 下被 `<tool>` 的权限拦住，
   headless 没有弹窗通道」，并附 capsule 指针。
3. **分类改成 `LocalAgentUnavailableError` 而不是 transient。** 理由与既有的「未登录」一致：
   权限缺失不会在下一个 target 上自愈，它是配置问题，应当**可归因**地让这个后端出局，
   而不是让 router 静默把锅传给链尾。⚠ 这是行为变化——原本会 fallback 的一类失败现在仍会
   fallback（Unavailable 同样触发 API 链），但**用户看到的话变了**，这正是目的。
4. 未命中的情况保持原样，但给通用分支补上 capsule 指针——这是零风险的一行，
   而它本可以把下游那次排查从「翻 agy transcript」缩短成「看一眼 stderr」。

### 验收

- 单测：构造 exit 0 + 空 content + 带那句 stderr 的 capsule ⇒ 抛 Unavailable，
  正文含工具名与 capsule id；不带该 stderr 的空 content ⇒ 仍是 transient，且正文含 capsule 指针。
- ⚠ **不要用生产语料做回归基线**：`agy-workspace-read-boundary` 记着这个签名在 184 份生产
  agy exchange 里**零命中**，所以「跑一遍生产语料没变化」证明不了任何事。
- 同步 `docs/llm_local_agent_agy.md`（§6.2 旁边加一句：那次修的是 grant，分类是这次修的）。

## 九、明确不做的六条，及其理由

- **0001 `finalize_qwen_verification`**：下游把一个 FineSub 任务拆到三个容器、按秒租用加速卡，
  需要在廉价 CPU 容器上对着已有 aligned artifact 事后补跑 referee。我们没有这个部署形态，
  它是纯粹的加法（一个文件、只增不改），不构成上游缺陷。将来若做批次的跨机拆分再谈。
- **0002 runtime tool manifest**（aria2c / node / pot-provider）：下游没有自己的资源系统，
  只能借我们的 manifest 装东西。这三样是它的视频下载需求，不是我们的。
  ⚠ 值得单独留意的只有一句：它提到上游 0.5.0 已改用 BtbN 的 **gpl** 构建，所以它原来的
  lgpl 修正不再需要——这条是**对我们的确认，不是待办**。
- **0003 agy `--add-dir`**：不适用，理由见下面单列的一节——它的因果链在别人那里成立，在我们这里
  被一次真机测量否掉了。
- **0005 lock 整文件哈希**：下游 0.4.2 自己发行物的哈希。反向提醒一件我们的事：
  CLAUDE.md 已记「`_LEGACY_LOCK_FILE_DIGESTS` 下次真正重新生成锁时删掉」，与本条无关但同一片代码。
- **0006 Triton MSVC C11 猴补丁**：现象为真，但**我们已经明确决定不收**，理由写在
  `docs/separator-optimization.md`「档位探测：`cl.exe` 不等于工具链」一节末尾：靠匹配第三方
  codegen 的措辞、失败时 `except: pass`，Triton 一改措辞就静默失效，而静默失效意味着回到
  它本来要修的构建失败。**本轮不推翻该决定**；若将来要收，底线仍是按 Triton 版本 gate、
  补丁没打上时 `current_reporter().warning`，不允许静默。
- **0008 AOTI on POSIX**：`_activate_msvc` / `cxx_toolchain_available` 是**有意** Windows-shaped
  （docstring 里就这么写着），因为 AOTI 路径只在 Windows 上跑过。下游在 Linux 云端跑它，
  于是每次构建都抛「requires MSVC」、被它的 `vocal_accel.install` 接住降级为 eager，
  云上每个 ≥270s 的任务都在无加速下跑而无人察觉。这是它的移植需求，不是我们的缺陷。
  若将来本仓库要支持 Linux 生产链路，这份 patch 是现成的起点。

### 单列 0003：因果链成立，但结论对我们不成立

**下游给的因果链**（四步，每步在我们的代码里都有对应物）：

1. agy 1.1.20 起，CLI **自己**只对「注册 project 的工作区之内」放行读取，之外的每一次读都要弹权限窗。
2. headless（`-p`）没有弹窗通道。失败形态不是报错，而是：软拒绝该工具 → **整个 turn 就此结束、
   不产出 assistant message** → stderr 留一句 `a tool required the "read_file" permission that
   headless mode cannot prompt for` → **exit 0**。
3. driver 把「没有 final assistant message」判为 `LocalAgentTransientError`，router 丢掉这个 target
   往下走；链条走到尽头后用户看到的是最后一环的话（典型是
   `Provider GEMINI_PAID is disabled or has no selected API key`）——**与真因毫无关系**。
4. 而我们交给模型读的文件都在**注册 project 目录之外**：tool protocol 的 project 是
   `<domain>/.finesub-tool-<slot>`，块在 `<domain>/call-<id>`；native 检索的 project 是
   `<domain>/.finesub-native`，capsule 是它的兄弟。（media project 的 project 就是 domain 本身，
   从来不受影响。）

第 2 步与第 3 步在我们的栈上**确有其事**：`docs/llm_local_agent_agy.md` §6.2（2026-08-30，agy 1.1.22）
记着同一形状的故障——`read_url_content` 缺 permission、headless 无法弹窗、整个 turn 结束不产
assistant message，driver 报的正是 `did not contain a final assistant message`；修法是往 project
自己的 `permissionGrants` 写一条 `read_url(*)`（**绝不写用户全局 settings**）。

**但第 1 步与第 4 步合不上，这是实测结论**（2026-09-03，agy **1.1.25**，headless
`-p --sandbox --new-project`）：

- project 建在 `<domain>/.finesub-native`，读 `<domain>/call-1/block.txt`——即**项目父目录的
  兄弟子树**——**成功，无权限询问**。
- 同一会话读 `C:/Windows/win.ini`：`permission check failed for read_file ... user denied`。

也就是说 `view_file` 确实按路径把关，**但那道关不是「project 目录」**，它比 project 宽。
我们的两条 agy 路径都落在关内。`local_agent.py` 里 `AGY_NATIVE_PROJECT_DIRNAME` 上方那条注释
（项目嵌在 domain 之下而不是与之并排，正是为了让 `view_file` 还够得着）本来就是照这个边界设计的。

⚠ **这一节留在这里主要是为了钉住一个反复踩的推理错误**：「在 project 目录之外」**不等于**
「在工作区之外」。只看下游 patch 的措辞、或只看我们 2026-08-13（CLI **1.1.12**）那份更老的
边界记录，都会得出「该采纳 `--add-dir`」的结论——两次都错，而且错法一样。
判据只有一个：**在当前 agy 版本上真机读一次兄弟子树**。改 agy 的 project / capsule 布局之前
要重测，因为布局变了关的位置也会变。

#### 那他们是怎么撞上的

我们的反证有两条，强度不一样：**184 份生产 agy exchange 里该签名零命中**（最强，是真实负载），
以及 2026-09-03 的 1.1.25 单点探针。⚠ 探针有一处自陈的空白：**它的 cwd 未记录**。生产是
`cwd=capsule.root`（task 档）或 `<domain>/.conversations/<digest>`（assignment 档），两者都是
domain 下的叶目录，而块在 `<domain>/assignments/<id>`——若探针当时的 cwd 是 `<domain>` 本身，
它就没有复现生产的形状。生产语料补上了这个洞，但探针本身别当成复现过 cwd。

**下游作者本人的说法**（2026-09-04 经 owner 转达）：「agy 在 1.1.20 版本后只放行工作区内的
读取，之前**没配置文件**的话，就读不了了。」——这把下面的第 2 条顶成了首要假设：不是 agy 在
1.1.22→1.1.25 之间改回去了，而是**「有没有一份既存的配置/授权文件」决定了读能不能过**，
我们这边一直有，所以从来没撞上。

⚠ 「配置文件」有两种读法，**判据不同，别混**：

- **读法 A：agy 的 project 记录**（`~/.gemini/config/projects/<id>.json`）。若是这个，那我们的
  非复现有一个**结构性**解释而不只是机器历史：driver 每次都注册 project 并调
  `_grant_permissions()` 往该记录写 allow 规则，**记录缺失时它直接 fail closed**——也就是说
  我们的调用**按构造必然带着一份记录**。那么下游失败的路径就是记录**尚未写成或不存在**的那种
  （容器每次重建 domain、或记录写入与首次读发生竞争）。
- **读法 B：`~/.gemini` 的全局配置/受信目录**。若是这个，则是开发机的交互使用史兜住了我们，
  与代码无关。

**一个判据同时区分两者**：把 project 记录改名（只动记录，A），以及把整个 `~/.gemini` 挪开

## 十一、owner 决定（2026-09-04）

三条都已拍板。**这一节记的是选了什么、否掉了什么、以及每条留了哪个口子**——写下被否的方案
和否它的理由，是为了让复审能针对性地提更好的，而不是从头再推一遍。

### 决定一｜转义：A+B，B 是不变量、A 是恢复手段

**决定**：两个都做，但职责分开。

- **B（出口校验）是不变量**：`submit` 的 validator 拒绝转义文本。坏内容永远到不了 SRT，
  也到不了 `correction-windows.jsonl`。这条不能被绕过。
- **A（入口修复）是恢复手段**，并且**必须出声**：**每修复一帧**一条 stderr 记录，带解码个数。
  ⚠ 不是「每进程一条」——本节初稿那么写过，后来改了：产物记的是修复**之后**的文本，
  所以那行记录是「发生过改写」的唯一证据，限流等于把证据丢掉。

**为什么不是单独一个**：

- 只有 A：我们长期替第三方的 bug 背一段特判，它修好了我们也不会知道；而且修复是**静默改写
  模型发来的数据**，一旦判据错了，没有任何一层会说话。
- 只有 B：如果那个 CLI 每次都转义，重提也失败 → 窗口失败 → 用户当场拿不到字幕。B 把「静默错」
  换成「响亮失败」，那是进步，但不是我们能给的最好结果。
- A+B：A 让运行照常成功，B 保证坏内容进不了 SRT 与断点缓存。

⚠ **B 的独立性有边界，别把它说过头**（2026-09-04 修正）。两层**共用同一个判据**
（`text.looks_escaped`），所以 B 冗余的是 **A 那条代码路径**，不是**判据本身**：

| B 真正接得住的 | B 接不住的 |
| --- | --- |
| 回复**没走过** `agent_mcp_server`（REST 传输、replay 存档、将来别的传输面）——那些路径上 A 从未运行 | **判据本身漏判**。agy 若改成只转义一部分字符，回复不再是纯 ASCII，**A 和 B 一起瞎** |
| A 的递归漏掉某种参数嵌套形状，修复没落到那个字符串上 | — |

所以「agy 换一种损坏方式，A 匹配不上而 B 还在」这句话是**错的**，本文此前那么写过。
判据的盲区是两层共有的，它是第十二节其二那一项，也是四项里唯一真正的防线缺口。

**顺序**：B 先落（它是不变量，且不依赖 A），A 后落。

**留给复审的口子**：

1. **判据的形状**。现在是「纯 ASCII ∧ 含 `\uXXXX` ∧ 解出非 ASCII」。815/815 零误判是**一份素材**
   上的结果，不是定理。若有更稳的判据（例如比对 prompt 侧的语言分布），值得听。
   ⚠ **它的安全性其实取决于目标语言**，这一点值得写下来：中日文任务的回复几乎不可能是纯
   ASCII，所以「纯 ASCII」这一条自己就把误判面压没了；而**英文源、英文目标**的任务里纯
   ASCII 是常态，模型若在 `note` 里字面写下 `\u2019` 这样的东西，判据就会命中。
   今天不构成问题——A 跑在 B 前面，会把它解成那个字符，无害——但它意味着**B 单独存在时
   的误判面比 A+B 大**，若将来有人想去掉 A，这条得先解决。
2. **A 该放在哪一层**。现在打算放 `agent_mcp_server` 收帧处（下游也在那里），代价是它作用于
   **所有 driver 的所有工具参数**。放到 agy driver 那一侧会更窄，但 MCP server 是子进程、不认识
   是谁在调它——若有干净的窄化办法，比现在的方案好。
3. **B 触发后要不要自动降级到别的 target**。现在的打算是照常走重试/回退链；也可以论证「这个
   后端在这次任务里已经不可信」而直接换人。没定。

**⚠ 一处独立缺陷，无论 A/B 都该修**：validator 发现 `char_count` 对不上时的处置是
`normalized`——用自己算的值覆盖模型写的值然后放行。实测那次 **15 行全部对不上、比值全部 ≈3×**，
它一条都没升级。「个别行对不上」normalize 是合理的，「每行都对不上且同方向」不是。
这等于把一个免费的交叉校验扔了。

### 决定二｜manifest 不登记 pinned revision 的小文件：维持现状

**决定**：不做。

**代价对比**。要关的窗口需要**三件事同时成立**：下载恰好在两个文件之间被打断 ∧ 缺的是 manifest
未登记的小文件 ∧ 之后机器联不上网。前两件已经被 `offline_first` 的一次 `OSError` 联网重试化解，
只有第三件叠加上来才会让用户看到报错、需要手动删 snapshot 重跑。

而登记要付：与 manifest `_note` 写下的约定相反（HF 条目钉 revision、逐文件摘要只记 LFS 对象，
因为那才是镜像可能替换的部分）；每次 revision 变更人工重抄清单；`entry_digest()` 变化导致
**所有现存 marker 一次性变 stale、每台机器多跑一次 1.6 GB 摘要**；而且它并不真的关上窗口，
只是把边界往外挪——没登记的文件仍在窗口里。

**前提已被独立核实（2026-09-04）**：本地确实没有第二份文件清单可查——HF snapshot 目录不保存
文件列表，`refs/` 只记 commit。所以选项确实只有「登记」与「维持现状」两个，这条决定站在被核过
的前提上，不再只是「我没找到别的路」。

### 决定三｜尾部裁判的设备判断：~~修~~ **已实施后撤回（2026-09-04 当天）**

⚠⚠ **这条决定作废，代码已回到改动前。** 撤回的理由与「其二」那条密度下限是**同一个**——
本决定通篇建立在下面那句「代价只有速度：裁判在 CPU 与 GPU 上的输出逐字节相同」上，而**那句话
是读错了证据**（详见第四节验收里的更正）：`asr-align.md` 比的是 CPU-float32 对 CPU-bf16/fp16，
生产却是 **CUDA-bf16 对 CPU-float32**，仓库里没有任何一处证明后一对相等。

而尾部证据**不是惰性的**：`stabilization` 读它来决定噪声腿的删除要不要撤销，也就是**一行字幕
留不留**。所以这条改动是在默认输出路径上换一条数值路径，**换来的只有速度**——唯一的动机没了，
就没有东西可以称量了。

⚠ **要重开这条，先做「待标定」里那份对照**（CPU-float32 对 GPU-bf16 的决策一致率与字幕差异），
不要再引用那句 CPU 内部的比较。下面的原文保留，因为它记着那个陷阱本身仍然真实——只是修它的
代价此前被算错了。

---

**决定**：让尾部走 `referee_device()`，不再从解析后的 ASR 设备派生。

**为什么**：`device` 读到 "cpu" 有两种含义——用户要求用 CPU，或者 **CT2 用不了这张卡**。裁判是
transformers 模型，CT2 的结论对 torch 没有发言权。`referee_device` 的第 1 问（意图）与第 3 问
（裁判自己后端的能力）存在的全部理由就是拆开这两件事，而尾部这条路绕过了它们。
**这正是已经修过一次的同一个陷阱**：`referee_device` 的注释记着，把 `None` 读成「解析后的 ASR
设备」曾让裁判在一张 torch 完全能用的空闲卡旁边被钉在 CPU 上（owner review 2026-09-02）——
那次修的是另一条路，尾部从来没跟上。

**范围**：只补第 1/3 问。**第 5 问仍然不问**（理由见第四节末尾那条「有意不覆盖」，不变）。
`requested_device` 在那一点已在作用域内，改动很小。

**风险**：一张 torch 声称可用、实际有问题的卡，现在会被放上 torch 模型——但第 3 问
`cuda_usable()` 正是为此存在的守卫，另外两条路已经在依赖它。代价只有速度：裁判在 CPU 与 GPU
上的输出逐字节相同。

**曾留的口子已核实关闭**（2026-09-04）：尾部的第 2 问（策略，`profile.gpu`）与解码期间**是同一件
事**，尾部并不特殊——`gpu=False` 只出现在 `cpu` 档，而那一档按 [gpu-profiles.md](../gpu-profiles.md)
「档位是策略，不是能力」是**对整趟任务的承诺**，裁判是这趟任务的一部分。改动之前它也被满足，

### 原始分析（保留，因为处置的理由都在里面）


四项里**只有「其二」触到真正的防线缺口**，其余三项是成本与噪声的取舍。⚠ 但那个缺口的威胁
模型是**推测的**（见其二），所以「唯一的缺口」说的是结构，不是紧迫性。起点是**一次离线测量**，它同时服务其一与其二、不花配额——

⚠ 通读这一节之前先看决定一末尾那张表：**两层防线共用一个判据，因此共用它的盲区**。下面四项
里的优先级是从那个事实推出来的，不是从「哪条看起来更严重」。

### 其一｜`char_count` 的 `normalized`：先量，再改

**是什么**。`output_protocol._normalized_char_count`：模型报的字数与我们算的差超过
`2.0 + 0.20×实际` 时追加一条 warning，然后**无条件用我们算的值覆盖**，而那条 warning 没有任何
人消费。事故那次 15 行**全部**超差、比值**全部**约 3×、**方向一致**——不是噪声，是「我们量的
文本不是模型写的文本」的直接证据，而处置是把证据覆盖掉。

**为什么还开着**。「个别行对不上」与「每行都对不上且同方向」该不该同样处置，是个要定口径的
问题，而定口径需要一份我们没有的数据：**各家模型系统性数错字的基线率**。有的模型就是数不准
CJK，稳定少报三成。

| 修法 | 风险 |
| --- | --- |
| **A 系统性偏差直接判窗口无效** | ⚠ **误杀会数不准的模型**——基线率未知，阈值（多少比例的行、多大幅度、方向是否一致）全靠拍。而仓库原则要求放弃一致性证明时**预先**写下替代指标与门槛，看完数字再定不算验收。而且它防的是「说不出形状的未知污染」，已知那种已被 A+B 挡住 |
| **B 仍 normalize，系统性偏差升级成窗口级 warning** | 若基线率其实很高，就发了一条**每次运行都响、然后被所有人忽略**的警告——正是本仓库文档写过的那个失败模式（一个永远过不了的校验最后会被关掉，而不是被修好）。前置条件与修法 A 相同，但量错了的代价小得多：噪声 vs 误杀 |
| **C 不改行为，只把模型报的原值留进产物** | 动 `-annotated.csv` 的列契约，知识库材料会读旧产物；收益也只到「事后可审计」，当场防不住 |

**建议**：**先量，再改**。历史 exchange 日志够统计「每窗多少比例的行超差、方向是否一致」在各
模型上的分布，离线、不花配额。量完大概率落到修法 B。**不建议现在做修法 A。**

**结果（2026-09-04）**：量完了（`tools/escape_density/corpus_baseline.py`），落到**修法 B**，
已实施。⚠ **修法 C 不必单独做**——核实后它其实已经被满足：逐行 warning 的正文里本来就同时带着
模型报的值与本地算的值（`Row 2 char_count '16' does not match the computed value 45`），
而 `validation_warnings` 整份进窗口 artifact。当初被扔掉的**不是那两个数字，是它们合起来的
含义**，而那正是修法 B 补上的。

### 其二｜判据的形状：唯一的防线缺口

**是什么**。现在是「纯 ASCII ∧ 含 `\uXXXX` ∧ 解出非 ASCII」。

- **误判面**（把好的当坏的）：**取决于目标语言**。中日文任务的回复几乎不可能纯 ASCII，这一条
  自己就把误判压没了；英文源英文目标的任务里纯 ASCII 是常态，模型在 `note` 里字面写个 `\u2019`
  就会命中。今天无害——A 在 B 之前把它解开——但**B 单独存在时误判面比 A+B 大**。
- **漏判面**（把坏的当好的）：**「纯 ASCII」这个条件就是盲区本身**。只要回复里还剩一个非 ASCII
  字符，判据就不命中，两层一起放行。

⚠ **威胁模型是推测的，不是观测到的**（2026-09-04 复审指出）。手上唯一那份素材是
**815/815 全转义**；没有任何证据表明 agy 会只转义一部分。下面用「部分转义」称呼这个盲区的
形状，但它是**设想的失败形态**——排优先级时别把它当成已经发生过的事故。盲区本身是**结构性**
的（判据里有那个条件，就有那个洞），这一点与它会不会发生无关。

| 修法 | 堵不堵盲区 | 风险 |
| --- | --- | --- |
| **A 源/回复的非 ASCII 对照**（源段含非 ASCII 而回复纯 ASCII，本身就可疑） | **不堵**。它自己就含「回复纯 ASCII」这一条，任何保留该条件的判据都放过部分转义 | 低。⚠ 早先在这里写过「需要让 `output_protocol` 认识这次任务的语言」，**是多虑**：`validate_translated_csv_text` 本来就收 `source_segments`，用现有参数就能判，不引入新耦合。真正的代价只有「合法纯 ASCII 回复」的例外口径要标定（整窗 `discard`、或源本来就是英文） |
| **B 提高特异性**（保留纯 ASCII，另看反斜杠密度） | **不堵**，同上——它保留了那个条件 | 几乎消掉误判面，但在优化已经很好的那一半 |
| **B′ 去掉纯 ASCII 条件，改判转义密度**（815 个反斜杠全跟着 `u`，模型写不出这种密度） | **堵**。这是列表里唯一真正碰到盲区的一个 | ⚠ 密度阈值要**预先**标定（多少个、占正文多大比例），而我们只有一份全转义素材，标不出「部分转义长什么样」；⚠ **判据是 A 和 B 共用的**，所以它同时改变**入口修复**的行为——修复一段本来正常、只夹着几个转义的文本，改写合法内容的风险比现在高得多（比如一条真在讨论转义写法的 `note`） |
| **C 让 A 把「我修过」传给 B** | — | ⚠ **否决**。这会毁掉 B 的独立性：B 之所以是真正的后备，恰恰因为它不依赖 A 是否工作。让它依赖 A 的上报，两层就退化成一层加一条日志 |

**建议**：**做 A，不做 B′**，理由与其四同源——

- **A 便宜、无耦合、收益真实**：它把英文任务上的误判面压下去，而那正是 B 单独生效时最脆的地方。
  仍建议**先只观测不拒绝**（把命中写进产物、不影响判定），拿到「合法纯 ASCII 回复」的基线再
  接到 B 上；这与本仓库对 pacing scorer 的做法（phase 1 只观测、阈值后定）是同一套。
- **B′ 是唯一的堵洞手段，但现在动它是拿确定的代价换推测的收益**：阈值标不出来（没有部分转义
  的素材），而它会同时放宽入口修复的改写面。**写死触发条件：一旦真的观测到一次部分转义，
  B′ 就是该做的那一件事**——那时也才有素材去标阈值。
- **C 不做。**

### 其三｜入口修复放在哪一层：维持现状（**已结案，2026-09-04**）

**是什么**。A 在 `agent_mcp_server` 收帧处，**对所有 driver 的所有工具参数生效**——Codex、
Claude Code、dsh 都没有这个 bug，但都会过这段代码。结构性约束是：MCP server 是子进程，
**它不知道是谁在调它**，想按 driver 收窄就必须新增管道。

| 修法 | 风险 |
| --- | --- |
| **A 由 driver 传环境变量，只有 agy 置位** | ⚠ **多一个开关**，而 `docs/llm_agent_tool_protocol.md` §1 明写传输形态是**派生的、没有配置开关**；⚠ **会过期**——按「agy 有这个 bug」置位之后，agy 修好没人会去关它，而别的 CLI 长出同样的 bug 它也不会自动打开。判据是自解释的，开关不是 |
| **B 维持现状，靠判据的窄** | 影响半径是「所有 driver」：某个未来 driver 合法发出「看起来像转义」的文本会被改写。缓解是 A **出声**（每修复一帧一条 stderr，带个数），所以真发生了会留痕，不是无声改写 |

**建议**：**维持现状**。开关的两个风险（逆原则、会过期）比它消掉的风险大。

### 其四｜B 触发后要不要直接换 target：维持现状（**已结案，2026-09-04**，带触发条件）

**是什么**。B 现在返回校验失败，走正常的重试/拆窗/回退链。但**传输故障不会因为重试而好转**：
同一个 CLI 再答一次，还是转义。

| 修法 | 风险 |
| --- | --- |
| **A 命中 B 即判该后端本次任务不可用** | ⚠ **误判时过度反应**——判据一旦在英文任务上误命中（其二那个面），一个窗口就能把一个好好的后端在整个任务里判死；⚠ **需要新的信号通路**：校验结果现在不把「这是后端的锅」带给 router，加上它就是把输出契约与路由耦合，与其二的修法 C 是同一类耦合 |
| **B 维持现状** | 烧掉重试预算再失败（本地 agent 还要额外花会话预算）。但这条路径**只在 A 漏掉时才被走到**，也就是我们最不了解的情况 |

**建议**：**先不动**，并写死一条触发条件——**生产里真的看到 B 触发，就是重新评估这条的信号**，
而那时手上会有一份真实素材，比现在拍脑袋强。

### 离线基线测量（2026-09-04，116 份纠错 exchange）

计划里说「先量，再改」，这是那次测量。素材是本机 `out/` 下的历史产物，**离线、不花配额**；
只统计聚合量。93 份能解析出 CSV 行，覆盖 7 个模型（`gemini-3.7-flash` 43、`gemini-3.8-flash` 12、
`gpt-5.6-luna` 9、`claude-opus-5` 6、其余各 1–3）。

**其一｜`char_count` 偏差的基线**：

| 量 | 基线 | 事故那次 |
| --- | --- | --- |
| 单窗**最大**行不符比例 | **0.024** | 1.00 |
| `computed/reported` 比值范围 | **0.53 – 0.74** | ~2.81 |
| 比值 **> 1** 的样本 | **0 / 38** | 全部 |
| 有 ≥1 行不符的窗口 | 22 / 93 | — |

**两个维度各自独立就能分开**，这比预想的干净得多：

- **方向**：基线里模型一律**多报**字数（比值 < 1，38/38），事故是**少报** 3 倍。在这份语料里
  「比值 > 1」本身就是前所未见的。
  ⚠ **但这 38 个比值只来自两个模型**（`gemini-3.7-flash` 31 个、`gemini-3.8-flash` 7 个）：
  其余五个模型的窗口**零不符**，它们支持「不符很少见」，对**方向**没有任何贡献。所以
  「模型只会多报」是**这两个 Gemini 模型**的观察，不是七个模型的结论——一个系统性**少报**的
  模型会触发这条判据，而目前没有任何测量排除掉那种模型。
- **比例**：基线最多 2.4% 的行不符，事故 100%——约 40 倍的余量。

**其二｜纯 ASCII 回复的基线**：116 份里只有 1 份，而它是 `'\n\n12:13\n'`——8 个字符、
`validation_ok: False`，agy 那条已知的畸形空答案（约 23% 的空/退化回答，见记忆与
`docs/llm_local_agent_agy.md`），**不是合法的英文回复**。所以修法 A 在这份语料里的真实误判是 **0**。
⚠ **但语料里没有任何英文目标的任务**，所以它测不到英文那一侧——这条限制必须跟着数字一起记。

### ⚠ 测量推翻了「其二 修法 A」，改用密度下限

修法 A 的条件是「源段含非 ASCII」。**英译中**任务里源是 ASCII、目标是中文——CLI 一转义，回复
变成纯 ASCII，而源里没有非 ASCII，于是**修法 A 不报**。那是拿一个**响亮的误判**换一个**静默的
漏判**，方向与本文一以贯之的取舍正好相反。**修法 A 作废。**

替代它的**本来**是一条自称不需要语言假设的条件：转义密度下限。⚠ **那条也错了，实现之后被
自己的测量否掉**（见下一节的预注册阈值）——密度同样是源语言的函数，只是这一次的依赖藏得更深。
真正留下来的是**转义计数**：故障转义的是**每一个**非 ASCII 字符，所以它永远数得多；
一个模型在 `note` 里偶然写下的字面转义是 1–4 个。

⚠ 一节之内在同一个陷阱上栽了两次（修法 A 的「源含非 ASCII」、密度下限的「事故那次是 0.816」），
两次都是**拿一份中日文素材去标一个所有语言都要过的门**。第三次再想加条件时，先问它在英译中
的形状上是多少。

### 预注册的阈值（先写下来，再实现）

两条都在实现之前定死，理由是仓库原则：放弃一致性证明就要**预先**写下替代指标与门槛，
看完数字再定不算验收。

**其一（窗口级 warning，不是 error）**——同时满足才报：

| 条件 | 取值 | 基线余量 |
| --- | --- | --- |
| 不符行占该窗全部行的比例 | **≥ 1/3** | 基线最大 0.024，约 14 倍 |
| 不符行的 `computed/reported` **中位数** | **> 1** | 基线 38/38 全部 < 1，⚠ 但只来自两个 Gemini 模型 |

两条都要，因为它们分别对应「系统性」和「方向一致」。基线上**零命中**，事故上命中。
⚠ 报 warning **不改 normalize 行为**：字数照旧归一，只是不再把证据一起吞掉。

**其二（收紧转义判据，减少误判）**——原有三条之外再加**转义个数 ≥ 4**（事故 815 个；
偶发字面转义是 1–2 个）。

⚠ **原本还预注册了一条「转义占正文 ≥ 0.20」，实现之后被自己的测量否掉，已删除**
（2026-09-04，复审提出、独立复算确认）。密度 ≈ `6 × 非ASCII字数 / 转义后总长`，而分母里的
ASCII 体量由**源语言**决定——英文源在 `<singles>` 与 `<translated>` 里各抄一遍、note 也可能是
英文。实测（`tools/escape_density/density_probe.py`）：

| 形状 | 密度 |
| --- | ---: |
| 日→中，事故同形 | 0.859 |
| 英→中，典型源句 | 0.450 |
| 英→中，长源句 + 英文 note | 0.234 |
| 英→中，字幕行可能的最低形状（源 200 字符、译文 4 字、note 80 字符） | **0.072** |

⚠ **早先这里写的是「网格下界 0.015」，那个数不该用**（2026-09-04 复审指出，已复算）：
它出自「640 字符的一行源句译成两个汉字」，字幕行没有这种形状——用人造角落撑腰，正是本节
一直在批评的那类论证。

真正的论据不需要它：**同一份完整污染，换个源语言读数就差一个数量级**（日→中 0.859，
英→中典型 0.450，字幕行的最低形状 0.072）。0.20 这个门槛是照事故那次的 0.816 定的，
**隐含了「源语言是中日文」这个假设**——而那正是同一节刚刚以同样理由否掉修法 A 的错误。
⚠ 所以处置不是「降到 0.10」：问题不是门槛定低了，是**这个量根本不在测故障**，
换个数值只是把同一个坏指标挪个位置。整条删掉。

⚠ **随后计数下限也删了**（owner 2026-09-04，在本节其余部分写完之后）。它犯的是与密度下限
**同一个错**：两条量的都是「**这次任务长什么样**」，不是「**故障长什么样**」——密度量源语言，
计数量窗口大小。

计数那条的代价是一个**静默漏判**：故障产生的转义个数跟着内容走，所以**单行窗口配两字译文只有
两个转义**，低于 ≥4 就被放行，那一行字幕以 `\u597d\u7684` 交付。而它换来的保护——放过「一份纯
ASCII 回复里偶然写了一个字面转义」——在本管线里接近不可达：纠错的目标语言**固定是中文**
（`PROMPT_VERSION = "zh-subtitle-correction-csv-v82"`，没有目标语言旋钮），合法回复几乎不可能是
纯 ASCII。⚠ **拿一个响亮且几乎不发生的误判，去换一个静默且真实的漏判，方向是反的。**

**现在的判据只剩两条**：**纯 ASCII** ∧ **至少一个转义解出非 ASCII**。前者是唯一还在挡事的，
它同时是那个**共享盲区**（部分转义不命中；推测形态，只有 B′ 堵得住）；后者挡住「真想写
`\u0041` 这六个字符」的情形。

**接受的残余风险只剩一条，且是响亮的**：一份 ASCII 从头到尾、又带字面转义的合法回复会被拒。
由 `test_a_stray_literal_escape_now_costs_the_window` 记着。

⚠ **整帧判断的理由也随之变了，别照抄旧说法。** 它不再是「密度按字段算会半修好」——那个论证
随计数下限一起没了。现在的理由更根本：**「纯 ASCII」这个条件只有在整帧尺度上才有意义**。
一个帧里若还留着真的中文，就证明这个 CLI 没在转义，那么另一个字段里的字面转义就是模型想写的；
逐字段判会把它改掉。由 `test_a_frame_that_still_holds_real_non_ascii_is_left_alone` 钉着。

⚠ **修复的上报从「每进程一次」改成「每帧一次并带转义个数」**：exchange 产物记的是 harness
**收到**的东西，而那已经是修复后的文本——所以那行 stderr 是「发生过一次改写」的唯一记录，
个数让人分得出整窗污染（几十个）与一次说不准的改写（一个）。

**当时那两条风险陈述保留在下面**，因为其中「漏判」正是删掉计数下限的原因，而它附带的三条旁注
今天仍然成立：

- **误判，响亮**：一份合法回复若同时「纯 ASCII」且带 ≥4 个字面转义会被拒。
- **漏判，静默**：单行窗口 + 三字以内译文只有三个转义，低于下限 4。⚠ `<singles>` 块**会**把
  计数翻倍（它的行是同样九列、**含译文列**，不是「抄 ASCII 源文本所以不产生转义」），但四个
  variant 里只有 `basicA` 要求它、两个档位默认都不要求，所以那个翻倍靠不住。
  ⚠ 而**「拆窗重试会反复产生这种单行叶子」是错的**——`ContextGeometry.MAX_SPLITS = 1`
  且 `split_window_in_half` 对不足两行返回 None；单行窗口来自整条轨很短、轨末尾的余数、
  或一个两行窗口被拆一次。
