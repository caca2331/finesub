   2–2.5 万，按 catalog 的 300k 输入上限约 13 窗溢出（第二份素材的密度下约 23 分钟音频）；溢出或 CLI 自动 compact
   之后的质量没测过。一轮没想时的轮换点已有（[`llm_design_notes.md`「模型回答退化的判据与重试的决策记录」](llm_design_notes.md#模型回答退化的判据与重试的决策记录2026-10-1618)）。

   `--settings` 带一个读本任务授权的 `PreToolUse` hook；`--setting-sources ""` 下 hook 是否加载、`--print` 下是否触发都没验，先真机探。
   `--resume` 时新给的 `--tools` 会生效。今天的生产不受影响：续上的工具会话只有没交答案时的那一轮追问，任务与工具都是同一份。

连带：`resume` 的 handle 缓存仍挂在 `RoleClient` 上，没并入 run 作用域的会话注册表（owner 要求两者共用），和五处一起做。
接完按工具会话形态补跑一次 `resume` 臂。

## 知识库遥测卷积（`events` 表）

为什么压 `events`、不做版本 GC 见 [`llm_design_notes.md`「知识库遥测压缩与暂不做版本 GC 的决策记录」](llm_design_notes.md#知识库遥测压缩与暂不做版本-gc-的决策记录2026-09-02)。

**触发条件**：`report` 或 `push` 单次超过 5 秒，或文件超过 50 MB（按 2026-09-02 的速率约 1500 个任务之后）。到时的形态：

1. 新表 `event_rollups`，主键 `(node_id, item_id, kind, opportunity, matcher)`，字段是任务数、窗口数、首末 task_id、首末 rev。
   误触发判据、report 的按 matcher 转化率、bundle 的按节点计数，三个消费者要的都只是这些聚合，没有一个读单行 span。
2. 保留最近 K 个任务的原始行（逐窗视图与排查用；建议 20，实现前再定），更早的折进 rollup 后删除。
3. **幂等不能丢**：折掉的任务写进 `rolled_tasks(task_id)`，`signals.py` 的插入对已折任务直接跳过，否则重跑一次旧任务就双计。
   这是唯一要碰写路径的一处。
4. 入口：`maintain.py` 加子命令 `compact`，默认 dry-run 打印将折多少行、聚合前后是否一致，`--execute` 才写，写完 `VACUUM`；
   `report.py` 与 `exchange.py` 改为读 rollup 加原始行之和。
5. 验收：折叠前后 `report` 的聚合数字逐字节相等（声称语义不变的优化，按 README_DEV 必须逐位一致）；折两次等于折一次；
   已折任务重跑不改变任何计数。

## 搁置的小项

- **Codex 旧父会话 fork 的子会话不吃缓存**：游戏专名实验里，父会话建好约 7 小时后再 fork，每片多 1.5–2 万未缓存（运行缓存占比 61–75%，新父会话 79–81%），机理没核实；与 [`llm_agent_tool_protocol.md`](llm_agent_tool_protocol.md) 里「沿用同一个父会话不比重建贵」不符，要先在生产形态上量。读数在维护者的本地报告里。

还开着、但次要、没有触发证据的工作，主表不再列。每条一行：是什么、为什么搁置、什么情况下再看。攒得多了再拆成单独的文件（owner 2026-11-10）。

- **Codex 的 `incremental_tools` 关着**：0.164.0 起它让没带工具的调用把基础提示发两遍，driver 与 my-agent-dispatch 的 `none` 档都关掉了它（[`llm_local_agent.md`「当前实现与迁移注意事项」](llm_local_agent.md#14-当前实现与迁移注意事项)里关掉的 feature）。关着对 FineSub 没有损失，但它是 Codex 的默认路径，旧方式以后可能少人维护。再看：Codex 的发布说明里修了它（上游 [openai/codex#62723](https://github.com/openai/codex/issues/62723)），或这个开关被标成 deprecated / removed；升级时临时把它从 `CODEX_DISABLED_FEATURES` 拿掉、开新会话抓一次不带工具的 capsule 请求（零额度：起一个一律回 400 的本机服务器，把 Codex 的 provider 指过去；它还关着时抓，本来就只有一份），只剩一份基础提示就把它从 `CODEX_DISABLED_FEATURES` 里去掉。
- **Gemini 4 Hydrogen 的准备任务没比**：进组（[决策记录](llm_design_notes.md#gemini-4-hydrogen-进出厂模型组的决策记录2026-11-12)）只比了纠错与知识更新；准备任务在常用的四个开发窗上没有 3.8 Flash 的参照，要在当前代码上两个模型各跑一遍、读者对比。搁置：`research-default` 里它排在 3.6、3.8 之后，只在两者额度都用完时才接。再看：准备任务出现明显变差的反馈，或要把它排到准备任务组前面。
- **agy 的 `xhigh`**：driver 对 agy 一律把 `xhigh` 按 `high` 发（`_agy_effort`），当初 agy 没有这一档；1.4.11 起 Gemini 4 Hydrogen 的模型表列出 `xhigh`，别的模型没核。搁置：出厂映射到不了 `xhigh`，只有 `[llm].local_agent_reasoning_effort` 写它时才碰到。再看：有人要在 agy 上用 `xhigh`，先按模型核对 `--effort xhigh` 收不收。
- **视频多模态对质量的帮助**：`--media video` 相对 audio 对质量有没有帮助、值不值多出的输入成本（低分辨率每帧 71 token × 0.25 fps，`profiles.py` 的 `VIDEO_*`）。搁置：没有启动条件，主流程不依赖它。再看：有画面确实携带信息的素材（字幕外的画面文字、看图才懂的指代）时；做时每臂 n≥5 加同配置复跑当噪声基线，固定素材、知识库快照、prompt version、endpoint、模型与推理强度，同报质量、各项 token、重试与墙钟。
- **分块准备任务的并行**：超长素材的准备任务一块接一块跑（后块要前块的名字），`fast`、`agy-fast` 这类并行预设上块越多越慢（owner 2026-11-09「以后作为一项可选的 follow up」）。要做时第 1 块串行跑完，第 2 到 N 块并行、都带第 1 块的名字表与摘要，墙钟约两块，分歧照样先出现的为准；不取的两种做法见 [`llm_design_notes.md`「准备任务交给纠错的背景的决策记录」](llm_design_notes.md#准备任务交给纠错的背景的决策记录2026-11-08)。再看：并行预设上长素材的墙钟成了问题。
- **准备任务引用 `<extra_info>` 的原文而不是抄一遍**：转述用户要求（`user_requests`、专属背景里出自用户的）今天逐字照抄，长歌词会花输出 token；做法是给 `<extra_info>` 加行号，准备任务写 `{{E12-E20}}`、harness 原样展开、引用错了报错（owner 2026-11-08「以后」）。再看：长 `--extra-info` 的输出成本或截断成了问题。
- **中文只纠错时准备任务的背景写成导读腔、术语规则写译法**：2026-11-06 一份中文讲座里见到（「学术开拓」「家国情怀」，术语规则写「对译为抒情传统」，与纠错窗「外语照原样写」冲突），冷读与 Codex Sol 都指出；正常那一窗收到的背景同样是导读腔，证据不足没改。再看：`polished` 写成书面语的现场能归到背景上时；改法是只纠错时让摘要只列帮助辨认话题、指代、专名的事实，用平实短句，术语规则不写对译。
- **可选请求通道被用得太少**（owner 2026-09-30 低优先级）：2026-09-09 验收里任务式 21 次 run 只有 1 次真的请求；之后 flash-lite 与 2.5 Flash 共 4 次、8 个窗口都直接交付；样本小，代码里没有缓解，也没有现成的对照臂。再看：有一条确实依赖时效或冷门信息的素材，或怀疑因此劣化时；按 prompt-iterate 协议 A/B 两种改法（`local` 下要求首条回复先请求；prompt 里把「不认识的专名必须请求」写硬）。
- **垫词长度 `filler_max_chars` 按源文 `len()` 数**：「三行夹一个垫词」的合并要求垫词源文不超过 3 个字符（`llm/prompt_constants.py` 的 `BASE`，不随长度比例缩放），英文的 "uh-huh" 是 6，过不了；没量它在英文源上挡掉了多少。再看：英文源上见到因此没并的垫词；按加权字数或按语言给值都行。
- **efficiency 档的读速超线比出厂默认之前多**：3.5 Flash Lite、`basicA` 三窗合计的读速超线（`字/秒` 超过 9 且译文 10 字以上）基线 36 / 38 / 38、改后 50 / 52，量的是带辅助列的十列版本、现版没重量；拆出 `[不过度改写]` 的尝试已撤回（owner 2026-11-04：主要面向 quality 优化，efficiency 只做兼顾，以后适时再想办法）。再看：efficiency 用得多起来或有人反馈读不过来；先在现版上重量，方向是 efficiency 自己的通用规则补一句「别加料」，或按源的时长给 `basicA` 的译文字数上限。
- **Agent 直接编辑知识库**：agent 在隔离的 worktree 里直接改知识库，收取标准与人直接编辑一致（按收割 `knowledge/rendered/` 的同一套规则判收），验收对比 proposal / update 路的成功率与 token 效率；预留点见 [`llm_local_agent.md`「13. 长期基线与明确暂缓的能力」](llm_local_agent.md#13-长期基线与明确暂缓的能力)（owner 2026-10-01 低优先级）。搁置：proposal 路没有失败的证据。再看：proposal / update 路的成功率或 token 效率成了问题。
- **精修稿长短的提示（只提示、不写档位）**：带精修字幕的知识更新跑完，在报告里打一行「精修稿每行比这次交付长约 N%，要长一些可以给风格写 `[字幕长度] 偏长`」，不改库；量两份字幕同一素材上每行加权字数与秒数的 p90 之比（删掉的那条实测路的做法在分支 `feat/length-tier` 的 `dc9eb6f4`）。搁置：只帮人发现档位，收益很小。再看：有用户反映不知道有档位，或精修稿长短与风格档位长期不符。
- **纯拉丁词条按词边界匹配**：纯拉丁字母的词条按子串匹配，英文源上会命中词中片段；要的是两侧不能紧贴拉丁字母或数字（不能用 `\b`：「Apexやろう」会漏）（owner 2026-10-24：多语言知识库本次范围外）。搁置：没有误注入的样本，改了会动日语素材的注入集合。再看：英文素材上见到误注入；改前离线比一遍日语素材。
- **共享冲突里其余条目层字段交给 AI**（`entry_type`、`native_names` 等）：模型词表里没有改这些字段的 op，今天只能人工 `--dismiss` / `--resolve`。搁置：没有积压。再看：这类冲突成批出现；先加 op 与写入面限制（[`llm_design_notes.md`「知识库里只能人工的环节：先有会话能兑现的 op 与写入面限制才放开」](llm_design_notes.md#知识库里只能人工的环节先有会话能兑现的-op-与写入面限制才放开owner-2026-10-02)）。
