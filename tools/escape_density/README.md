# escape_density — 转义判据与 char_count 阈值的标定

两个一次性测量，支撑 `docs/plans/nonoka-downstream-findings-plan.md` 第十二节的两条阈值。
结论已经沉淀进代码（`finesub.text.looks_escaped` 与
`finesub.llm.output_protocol.SYSTEMATIC_CHAR_COUNT_SHARE`）与那份计划——⚠ **两条曾经存在的
转义阈值最后都被删了**，所以这里的数字读起来是「为什么没有阈值」而不是「阈值定在哪」；
脚本留在这里，
是因为**下次重新标定不该从头写**，而且一个不能复现的数字按 `docs/bench-discipline.md`
的口径本来就不算数。

## `corpus_baseline.py` — 历史产物的基线

扫 `out/**/exchanges/*correction*.md`，按模型统计两件事：

- **`char_count` 偏差**：每窗有多少比例的行超出容差、`computed/reported` 的分布与方向。
  2026-09-04 的读数（116 份、93 份可解析、7 个模型）：单窗最多 **2.4%** 的行不符，
  **38/38** 的比值 **< 1**（模型只会多报自己的长度）。事故那次是 **100%** 的行、比值约 **2.8**。
  ⚠ 那 38 个比值只来自**两个** Gemini 模型，其余五个模型的窗口零不符——它们支持「不符很少见」，
  对**方向**没有任何贡献。所以「模型只会多报」是这两个模型的观察，不是七个模型的结论。
- **纯 ASCII 回复的出现率**：116 份里只有 1 份，而它是 8 个字符的畸形空答案
  （`validation_ok: False`），不是合法回复。

⚠ 这份语料**全部是中日文目标**，所以它对英文目标的任务什么都没说。这条限制当时差点让
一个阈值定错，见下。

```bash
python -m tools.escape_density.corpus_baseline
```

## `density_probe.py` — 转义密度随源语言怎么变

按真实的 `OUTPUT_CSV_HEADER` 与 16 行窗口构造**完全被转义**的回复，量它的转义密度。

它存在的理由是一次**否掉了自己的阈值**的测量。判据原本除了计数还有一条密度下限
（0.20），依据是事故那次的 0.816。但密度 ≈ `6 × 非ASCII字数 / 转义后总长`，而分母里的
ASCII 体量由**源语言**决定——英文源在 `<singles>` 与 `<translated>` 里各抄一遍、note 也可能
是英文。实测：

| 形状 | 密度 |
| --- | ---: |
| 日→中，事故同形 | 0.859 |
| 英→中，典型源句 | 0.450 |
| 英→中，长源句 + 英文 note | 0.234 |
| 英→中，字幕行可能的最低形状（源 200 字符、译文 4 字、note 80 字符） | **0.072** |

⚠ **不要引用无界网格的 0.015**：那个角落是「640 字符的一行源句译成两个汉字」，字幕行没有这种
形状，拿它论证等于用人造角落撑腰。真正的论据是**同一份完整污染在不同源语言下读数差一个数量级**
（0.859 对 0.072），所以按一个语言对标出来的门槛在另一个语言对上必然错——不是「门槛定低了」，
是这个量根本不在测故障。

所以密度条件被整个删掉。⚠ **随后连计数下限也删了**（owner，2026-09-04）：那条 ≥4 的下限
本来是为了放过「一份纯 ASCII 回复里偶然写了一个字面转义」，代价却是**小窗口上的真故障被静默
放行**——单行窗口配两字译文只有两个转义，那一行字幕就以 `\u597d\u7684` 交付。

两条下限犯的是同一个错：**量的都是「这次任务长什么样」，不是「故障长什么样」**。密度量源语言，
计数量窗口大小。而本管线的纠错目标语言固定是中文（`PROMPT_VERSION`），所以合法回复几乎不可能
是纯 ASCII——那条下限保护的局面本就接近不可达，却拿真故障的静默漏判去换。

现在的判据只剩两条：**纯 ASCII** ∧ **至少一个转义解出非 ASCII**。

```bash
python -m tools.escape_density.density_probe
```
