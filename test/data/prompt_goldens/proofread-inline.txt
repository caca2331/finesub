=== api ===
你刚交的 `<translated>` 通过了本地校验。交卷之前再校对一遍：把它当成一段字幕成品，从头到尾重读，找出错误并改掉；不改字幕的划分。

下面「改什么」「不改」两节原是写给单独校对成品的人的，对你来说：
- 「识别原文」是 `<asr_result>` 里那一行的 ASR 原文；「纠错文」「译文」「把握」「备注」是你 `<translated>` 里那一行的 `corrected_text`、`translation`、`conf`、`note`；
- 「序号」是那一行的 `position`，合并行是它那一串源序号；
- 「资料」「翻译风格」是 system 指令与第一条 user 消息里给你的背景资料、知识库词条与翻译风格；「标题带『专名与术语』的段」对你是背景资料 JSON 里的 `entities`、`terminology` 两个列表与知识库词条里的专名，「识别常见的听错」是其中的 `asr_risks` 列表；
- `字/秒` 是译文的字数（英文字母、数字和标点算半个字）除以这一行在时间轴上的跨度（首源开始到末源结束）；超过线的行脚本已经点出来了，见后面的点名。

## 改什么

按要紧程度：
1. 意思译错：漏译、错译，或语气、褒贬、肯定与否定弄反（例如「さすがにそれはない」译成「果然不行」，原意是「这也太离谱了」）。译文与纠错文对不上时，先判断哪边对，再改错的那一边；错在纠错文的，按第 4 条处理。
2. 读不完：`字/秒` 超过 9、译文又在 10 个字以上的行，在不丢信息的前提下改短：删掉多余的修饰、重复和口头禅，换更短的说法；显示时间实在太短、怎么改都超过 9 的，在不丢信息的前提下尽量删短，允许仍然超线。改短时保留理解所需的动作对象、否定、条件、程度与推测；日文省略了、译文为了好懂补出来的必要成分也不能删（例如「能当面看到演员本人念这段台词真难得」不能删成「能当面看到真难得」）。改短不算「只是换一种说法」。不到 10 个字的行不改短：省不了几个字，显示得太短是时间轴的事，不归你管。
3. 专名：人名、称呼、作品里的专名与术语，与资料里定好的写法不符或前后写法不一致；资料自己说没核实（「未核实」「未查证」）的译名不算定好。原文的称呼不同（さん、ちゃん、様），译法跟着不同，不强行统一；同一个人、同一个称呼（名字与后缀都相同）前后译法不一致的，统一成用得多的那种。
4. 纠错文里的听错：只有一种读法说得通、而且与识别原文里对应的词读音相近的才改（改回识别原文也算）。资料（尤其「识别常见的听错」）和前后文是找这种读法的线索，本身不是改的理由，资料自己说没核实的条目更不是；译文是照纠错文译的，不能反过来拿它改纠错文。备注说要改成某个写法、纠错文却没改的，补上；备注只是猜测（如「疑为」「也可能是」，或这一行的 `把握` 列标了 `low` 或 `median`）的，照样要满足上面两个条件（只有一种读法说得通、读音相近）。你听不到音频，只凭文字拿不准的听错不改。纠错文与译文各自判断：把纠错文改对之后，译文本来就是这个意思的，译文不动。
5. 译文里残留的垫词、口吃、无意义的重复（台词本身的重复、带语气的叠词，以及翻译风格要保留的口癖、语气词，都保留）；相邻两行原文不同却译重了的，按各自的原文分开译。判断漏译、错译、译重之前，先把同一句话的几行连起来读：纠错时允许译文为了中文语序在相邻几行之间小幅错位，这不算错；确实要跨行修正时，把受影响的几行都写出来，免得补出重复的内容。
6. 与翻译风格明显不符的地方。

翻译风格与这里的通用规则（长度、读速）冲突时：用户的风格（`<style>` 里不叫「出厂默认」的那些，以及特殊翻译风格要求）写得非常明确的，按风格来；说得不那么肯定的，两边折中；出厂默认风格与长度、读速冲突时，按长度、读速来。资料里定好的专名与术语（标题带「专名与术语」的段里没标「未核实」的）照资料写，风格只管其余文字；风格明确说到这些专名时（如「人名一律用原文」「专名里的数字也写阿拉伯数字」），按风格来。

## 不改

- 字幕的划分：不合并、不拆开、不删行，行数和序号保持不变；纠错文、译文都不能改成空的，整行只剩垫词的照留。
- 只是换一种说法、不比原来更准也不更好读的地方。
- 拿不准的地方：意思上的错要有把握才改，听错只凭文字拿不准就不改。
- 改后的译文不比原来长；修第 1、3、5 条的错时除外（尽量简洁），第 6 条按上面「翻译风格与这里的通用规则（长度、读速）冲突时」那段定。
- 标点：除非错得影响理解，句末标点不改。

## 脚本点名的行

脚本只查两件事：读速（第 2 条）和资料里定好的专名在译文里有没有出现（第 3 条）。点名只是提示，不是校对的范围：意思译错、听错这些脚本查不出，没点名的行照样要读；点了名的行也不一定要改（例如译文用代词承接了前面的人名，或原文的专名本来就该按上下文译成别的说法）。
- 2（读速）：跨度 1.5 秒、16 个字，10.7 字/秒

## 输出

答案是一个 `<patch>` 块，块外不写说明文字。本地会把它叠到你刚交的 `<translated>` 上，再整份校验：
1. 第一行原样写 header：`type|position|spk|corrected_text|translation|conf|note`。
2. 只写改了的行。每行的 `type` 与 `position` 照抄原行，一个字也不改（合并行照抄那一串源序号）；要改的是 `corrected_text`、`translation`，`spk`、`conf` 照抄，`note` 按下一条重写。说话人这一轮不重判：`spk` 一律照抄，写着 `?` 的行、你现在看法不同的行也一样。
3. `note` 写「类别编号：理由」，类别是上面「改什么」的编号（1–6），一行改了几处时写最要紧的那个；理由一句话，里面不要用 `|`。例如：`2：原译 1.2 秒 14 个字，删掉重复的「真的」`。
4. 不写 `discard` 行，不合并、不拆开，也不写没改的行。没有要改的行时，`<patch>` 里只写 header 一行。
5. 不写 `<translated>`，其它块不必重交，本地沿用你刚才那份的。这一轮的答案以本条为准，代替 system 指令里交完整 `<translated>` 终稿的要求。

=== repair ===
你刚交的 `<patch>` 没能叠到你的 `<translated>` 上。本地查了你的 `<patch>`，再把它叠上去整份校验，报告的问题如下。叠之前整份是通过的，所以问题都出在你 `<patch>` 写到的行上：`<patch> row N` 是你 `<patch>` 里 header 之后的第 N 行，`Row N` 是叠好的整份里的第 N 行；报「缺源」多半是同一行格式出错连带的，那一行改好就不缺了。

- <patch> row 1 changes `conf` from `high` to `low`: the proofread turn changes text only.

改正后重交一份完整的 `<patch>`。本地只用这一份，上一份整份作废：
1. 上一份里的每一行改动都照写进来，出错的行改正之后也写；没写进来的行就不改了。
2. 写法照上一条消息的「输出」一节：第一行原样写 header `type|position|spk|corrected_text|translation|conf|note`，只写改了的行，`type` 与 `position` 照抄原行，`spk`、`conf` 也照抄。单元格里不留半角的 `|`：多出来的分隔符删掉，正文里要用竖线的写成全角 `｜`。
3. 仍然不写 `discard` 行，不合并、不拆开；块外不写说明文字。
